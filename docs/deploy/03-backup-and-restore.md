# Переносимая копия CRM и восстановление после переустановки Ubuntu

Инструкция позволяет сохранить **базу CRM, все вложения, исходный код точного production-коммита и файл секретов `.env`** в один зашифрованный архив на компьютере владельца. Этого достаточно, чтобы поднять CRM на чистом сервере и вернуть лиды и файлы.

> **Важно:** архив — это полный комплект восстановления **CRM**, но не образ всей виртуальной машины. В нём нет системного диска Ubuntu, SSH-ключей, настроек панели хостинга и сертификатов Let's Encrypt. Ubuntu настраивается заново по [`01-server-setup.md`](01-server-setup.md), сертификат выпускается заново. Если панель провайдера умеет делать снимок всей VPS, снимок можно сохранить дополнительно — но не вместо этого архива.
>
> Создание архива кратковременно останавливает `backend`, `worker` и `beat`, чтобы база и файлы попали в комплект согласованно. Команда запускается **владельцем со своего компьютера**. Она не удаляет Docker-тома и существующие серверные бэкапы.

## Что входит и что не входит

В зашифрованном архиве будут:

- `database.dump` — свежий дамп PostgreSQL в формате `custom`;
- `attachments.tar.gz` — всё содержимое тома вложений, включая миниатюры;
- `.env` — реальные секреты и настройки текущего сервера;
- `source.tar.gz` и данные в `MANIFEST.txt` — исходный код и точный Git-коммит, с которого была собрана текущая CRM;
- `SHA256SUMS` — контрольные суммы дампа, архива файлов и исходников.

Штатные ежедневные дампы и еженедельные архивы хранятся в Docker-томе `backups` **на том же VPS**, что и база и вложения. Они полезны для обычных ошибок, но не переживут потерю или чистую переустановку диска. Тома `valkeydata` (кеш и очередь фоновых задач) в комплект не включены: это восстанавливаемые служебные данные, а не лиды или файлы. Внешний вид и настройки CRM хранятся в коде и `.env`.

## 1. Создать и проверить зашифрованную копию

### Подготовить компьютер владельца

Нужен компьютер с `bash`, `ssh`, `tar`, `sha256sum` и программой [`age`](https://age-encryption.org/). В Ubuntu/WSL:

```bash
sudo apt update && sudo apt install -y age
```

На macOS с Homebrew:

```bash
brew install age coreutils
export PATH="$(brew --prefix coreutils)/libexec/gnubin:$PATH"
```

В Windows используйте WSL с Ubuntu или Git Bash с установленным `age`. SSH-алиас `crm` должен подключать пользователя `deploy` к текущему серверу; это тот же алиас, которым выполняется `ssh crm`.

### Запустить экспорт

Получите актуальный клон репозитория на своём компьютере и из его корня запустите:

```bash
./deploy/export-recovery-bundle.sh
```

По умолчанию файл появится в `~/crm-recovery/` с датой в имени. Можно задать путь и SSH-алиас явно:

```bash
./deploy/export-recovery-bundle.sh "$HOME/crm-recovery/crm-before-reinstall.tar.age" crm
```

Скрипт попросит ввести `SNAPSHOT` для подтверждения окна обслуживания. После экспорта `age` спросит парольную фразу дважды: для шифрования и для проверки, что архив расшифровывается. Используйте длинную уникальную фразу (например, несколько случайных слов) и сохраните её **в менеджере паролей отдельно от файла**. Не оставляйте поле пароля пустым: в таком случае `age` сгенерирует фразу, которую нужно будет отдельно сохранить.

Во время экспорта `.env`, дамп и вложения ненадолго находятся в закрытом временном каталоге на компьютере (`700`); скрипт удаляет его после работы. Удаление файла не гарантирует физическое стирание данных с SSD, поэтому запускайте экспорт на доверенном компьютере с шифрованием диска.

Скрипт проверяет, что не идёт `deploy.sh`, что production-клон чистый, PostgreSQL healthy и места хватает. Затем он:

1. сохраняет `.env` и исходный код текущего production-коммита;
2. останавливает только те из `beat`, `worker` и `backend`, которые работали до снимка;
3. делает дамп и архив вложений, проверяет дамп через `pg_restore --list` и целостность архивов;
4. запускает обратно ранее работавшие сервисы;
5. передаёт файлы на компьютер владельца по SSH, шифрует их паролем-фразой и проверяет, что архив расшифровывается и содержит все части;
6. удаляет только собственный временный каталог экспорта в `/tmp` после успешной проверки зашифрованного файла.

Скрипт всегда пытается запустить обратно сервисы, которые работали до снимка. Если SSH/передача прервётся после подготовки файлов, приложение уже должно быть поднято, а временная копия останется для повторной передачи. Если сам запуск сервисов завершится ошибкой, скрипт сообщит об этом, оставит временный каталог и напечатает его точный путь; проверьте `cd /opt/crm && docker compose ps` и не удаляйте копию до выяснения. Скрипт никогда не очищает `backups`, `pgdata`, `attachments` или другие Docker-тома.

Проверить состав архива можно ещё раз, не сохраняя расшифрованные файлы на диск:

```bash
BUNDLE="$(ls -1t "$HOME"/crm-recovery/*.tar.age | head -n 1)"
age -d -p "$BUNDLE" | tar -tf -
```

В списке должны быть `MANIFEST.txt`, `SHA256SUMS`, `database.dump`, `attachments.tar.gz`, `source.tar.gz` и `.env`. Парольную фразу нужно ввести ещё раз. После этого скопируйте зашифрованный `.tar.age` **минимум ещё в одно независимое место вне VPS** — например, на отдельный зашифрованный диск и в защищённое облачное хранилище. Не кладите его в репозиторий Git, не отправляйте незашифрованным письмом и не храните парольную фразу рядом с файлом.

### Отдельный снимок VPS (по возможности)

Если панель хостинга предлагает снимок/образ всей VPS, его можно сделать перед переустановкой и сохранить отдельно. Это дополнительная страховка для системных настроек, а не замена переносимому архиву: снимок на том же аккаунте провайдера не защищает от потери аккаунта или самого провайдера. Интерфейс и наличие этой функции зависят от тарифа; команды ниже её не вызывают.

## 2. Перед чистой переустановкой

**Не начинайте переустановку, пока не выполнены все пункты:**

- есть проверенный `.tar.age` вне production-сервера;
- есть ещё одна независимая копия этого зашифрованного файла;
- парольная фраза сохранена отдельно и владелец может её ввести;
- список содержимого архива открывается командой выше;
- известно, какой сервер, IP и домен нужно восстановить.

Сам экспорт проверяет читаемость PostgreSQL-дампа и архива вложений, но это не заменяет полноценную репетицию запуска на отдельной чистой VPS. Если нужна максимальная уверенность до переустановки, сначала пройдите раздел 3 на отдельном тестовом сервере. Production в рамках этой работы не переустанавливался и не проверялся.

После выполнения чек-листа переустановите/создайте сервер с Ubuntu 26.04 LTS и пройдите [`01-server-setup.md`](01-server-setup.md). Если у нового сервера другой IP, сначала обновите DNS и используйте новый адрес в шагах настройки SSH и TLS. Для смены SSH host key локальная команда из инструкции: `ssh-keygen -R <IP-АДРЕС>`.

Далее используйте [`02-deploy.md`](02-deploy.md) только для подготовки каталога и репозитория, **но не запускайте его обычную первичную установку**: не создавайте новый `.env`, не запускайте миграцию пустой базы, не создавайте администратора и не загружайте demo-данные. Вместо этого выполните следующий раздел.

## 3. Восстановить CRM на новом сервере

Ниже команды выполняются частично на компьютере владельца и частично на новом сервере под `deploy`. Они рассчитаны на чистый сервер с настроенным `ssh crm` и путь проекта `/opt/crm`.

### 3.1. Передать архив на новый сервер, не оставляя незашифрованную копию на компьютере

На компьютере владельца укажите точный файл (путь нужно заменить на своё имя архива):

```bash
BUNDLE="$HOME/crm-recovery/crm-before-reinstall.tar.age"
SSH_HOST="crm"
```

Создайте закрытый временный каталог на новом сервере:

```bash
RESTORE_DIR="$(ssh -T "$SSH_HOST" 'umask 077; mktemp -d "$HOME/crm-recovery-restore.XXXXXXXXXX"')"
printf 'Временный каталог восстановления: %s\n' "$RESTORE_DIR"
```

Расшифруйте архив локально и отправьте его по защищённому SSH-каналу прямо в этот каталог:

```bash
age -d -p "$BUNDLE" | ssh -T "$SSH_HOST" "tar -xf - -C '$RESTORE_DIR'"
```

Проверьте, что все части на месте и контрольные суммы совпадают:

```bash
ssh "$SSH_HOST" "cd '$RESTORE_DIR' && ls -lh && sha256sum --check SHA256SUMS && tar -tzf attachments.tar.gz >/dev/null && tar -tzf source.tar.gz >/dev/null"
```

### 3.2. Загрузить точную версию приложения и секреты

Из того же локального терминала подключитесь к новому серверу и оставайтесь в этом SSH-сеансе для шагов 3.2–3.4:

```bash
ssh "$SSH_HOST"
```

На сервере под `deploy` найдите каталог, куда только что передали архив, и прочитайте точный production-коммит:

```bash
set -euo pipefail
RESTORE_DIR="$(ls -dt "$HOME"/crm-recovery-restore.* 2>/dev/null | head -n 1)"
test -n "$RESTORE_DIR" || { echo "Каталог восстановления не найден" >&2; exit 1; }
SOURCE_COMMIT="$(sed -n 's/^source_commit=//p' "$RESTORE_DIR/MANIFEST.txt")"
[[ "$SOURCE_COMMIT" =~ ^[0-9a-f]{40}$ ]] || { echo "Хеш коммита в манифесте некорректен" >&2; exit 1; }
printf 'Каталог: %s\nКоммит: %s\n' "$RESTORE_DIR" "$SOURCE_COMMIT"
```

Если `/opt/crm` уже создан этапом 1, сохраните его, как требует шаг 2 из [`02-deploy.md`](02-deploy.md), затем клонируйте рабочую ветку и переключитесь на сохранённый коммит:

```bash
sudo mv /opt/crm /opt/crm.stage1
sudo mkdir -p /opt/crm && sudo chown deploy:deploy /opt/crm
git clone -b arena/900b2a73-crm https://github.com/Roses1s/crm.git /opt/crm
git -C /opt/crm checkout "$SOURCE_COMMIT"
```

Если используемая рабочая ветка репозитория изменилась после написания этой инструкции, клонируйте ветку, указанную в `source_branch` файла `MANIFEST.txt`; проверяйте, что `$SOURCE_COMMIT` существует в ней. Архив `source.tar.gz` содержит код точного production-коммита как запасной источник, но обычный путь восстановления — Git-клон с историей.

Верните исходный `.env`, не генерируя новые `SECRET_KEY` и `POSTGRES_PASSWORD`:

```bash
cp "$RESTORE_DIR/.env" /opt/crm/.env
chmod 600 /opt/crm/.env
cd /opt/crm && docker compose config -q
```

`SECRET_KEY` и пароль PostgreSQL должны остаться прежними: первый нужен для подписи токенов, второй — контейнерам для подключения к базе. Если домен изменился, проверьте `CORS_ORIGINS` в `.env` и адрес `SITE_URL`, если он переопределяется для `deploy.sh`; при смене подсети сервера сверьте `CRM_PROXY_SUBNET` и адреса proxy. При неизменном домене и подсети не меняйте эти значения и остальные секреты без отдельной причины.

Если этап 1 поднял временный nginx, остановите только этот установочный стек до запуска полного CRM. Команда без `-v` не удаляет тома:

```bash
cd /opt/crm.stage1 && docker compose down
```

### 3.3. Создать новые пустые Docker-тома и вернуть данные

Сначала соберите только образы приложения и поднимите пустые PostgreSQL/Valkey. На этом шаге API, worker и nginx ещё не запускаются:

```bash
cd /opt/crm
docker compose build backend frontend
docker compose up -d postgres valkey
docker compose ps
docker compose exec -T postgres sh -ceu 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Перед восстановлением база должна быть пустой. Посмотрите список таблиц:

```bash
docker compose exec -T postgres sh -ceu 'psql -X -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\\dt"'
```

Для новой базы ожидается `Did not find any relations.` Если таблицы уже есть, остановитесь и выясните почему — **не запускайте восстановление поверх заполненной базы**.

Загрузите PostgreSQL-дамп:

```bash
docker compose exec -T postgres sh -ceu 'pg_restore --no-owner --no-privileges --exit-on-error --dbname "$POSTGRES_DB" --username "$POSTGRES_USER"' < "$RESTORE_DIR/database.dump"
```

Верните файлы и миниатюры в Docker-том `attachments`:

```bash
docker compose run --rm --no-deps --interactive --no-TTY worker python -c '
import sys, tarfile
with tarfile.open(fileobj=sys.stdin.buffer, mode="r|gz") as archive:
    archive.extractall("/var/lib/crm", filter="data")
' < "$RESTORE_DIR/attachments.tar.gz"
```

Проверьте количество главных записей в восстановленной базе и наличие каталога файлов:

```bash
docker compose exec -T postgres sh -ceu 'psql -X -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT (SELECT count(*) FROM users) AS users, (SELECT count(*) FROM leads) AS leads, (SELECT count(*) FROM shipments) AS shipments, (SELECT count(*) FROM attachments) AS attachments;"'
docker compose run --rm --no-deps worker python -c 'import os; p="/var/lib/crm/attachments"; print("attachments files:", sum(len(files) for _, _, files in os.walk(p)))'
```

Числа `users`, `leads`, `shipments` и `attachments` должны совпасть со строкой `record_counts_users_leads_shipments_attachments` в `MANIFEST.txt`. Число файлов может быть больше числа записей вложений, потому что у изображения есть отдельная миниатюра.

### 3.4. Запустить полный стек и проверить

После успешного восстановления запустите безопасный сценарий деплоя **без скачивания другой версии и без пересборки образов**:

```bash
cd /opt/crm && ./deploy.sh --skip-pull --no-build
```

Он проверит базу, создаст локальный предвыкаточный дамп уже восстановленных данных, применит необходимые миграции и поднимет приложение. Не запускайте `createsuperuser` или `seed`: пользователи и данные уже находятся в восстановленной базе.

Проверки:

```bash
cd /opt/crm && docker compose ps
curl -s https://crmdetroid.ru/health
docker compose exec backend alembic current
```

Ожидаются здоровые контейнеры, `{"status":"ok"}` от `/health` и текущая ревизия Alembic. Затем войдите существующей учётной записью, откройте несколько старых лидов и проверьте их вложения/миниатюры. Для дополнительной проверки созданного локального дампа используйте штатный тест:

```bash
cd /opt/crm && ./deploy/restore-test.sh
```

Он восстанавливает свежий дамп во временную базу `crm_restore_test`, сверяет количества записей и удаляет только эту временную базу. Запускайте его на новом сервере только если база с таким именем не содержит нужных данных.

После полной проверки каталог `$RESTORE_DIR` на новом сервере содержит открытый `.env`, дамп и архив вложений. Удалять эту временную копию можно только после того, как CRM проверена и зашифрованный архив остаётся доступен в независимом хранилище. Если владелец решил убрать именно эту временную папку, команда запросит подтверждение и не затронет Docker-тома:

```bash
rm -rI -- "$RESTORE_DIR"
```

Не выполняйте `docker compose down -v`, `docker volume prune` или `docker system prune --volumes` — они могут удалить восстановленные данные.

## 4. Проверки, выполненные в репозитории, и границы

Скрипты проверены на синтаксис Bash и в безопасных локальных проверках. Полноценный production-экспорт и восстановление здесь не запускались: для них необходимы SSH-доступ владельца, Docker и PostgreSQL. Экспорт автоматически проверит содержимое дампа и целостность архивов, а `deploy/restore-test.sh` проверит восстановление базы на новом сервере. Проверка реального входа и вложений остаётся обязательной после восстановления.
