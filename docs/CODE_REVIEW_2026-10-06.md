## Новые находки (в коде, появившемся после 03.10)

### Б-26 🟡 Итоги таблицы заявок считаются выгрузкой всех строк в Python

`_filter_totals` (`backend/app/services/shipments.py`): чтобы посчитать суммы
«Маржа» и «Всего» по фильтру, запрос выгружает **все** строки фильтра
(четыре колонки денег) и суммирует циклом в Python — на **каждый** запрос
списка, при каждом клике по пагинации и каждой смене фильтра.

Почему сделано так — понятно и написано в докстринге: итог обязан сходиться
с колонками до копейки, а `visible_margin` — функция Python. Но цена:
100 заявок — незаметно; 5 000 — уже десятки мегабайт и сотни миллисекунд;
50 000 — каждая страница списка ощутимо бьёт и по базе, и по памяти воркера.
Общий тренд проекта — «список отдаёт страницу, а не всю базу» (пагинация,
`lead_pager` без выгрузки идентификаторов) — здесь сломан.

**Фикс:** повторить формулу `visible_margin` SQL-выражением `CASE WHEN … END`
и считать `SELECT SUM(...)` тем же запросом — сумма сойдётся до копейки,
потому что формула та же, а строк в памяти не будет ни одной. Альтернатива —
хранить посчитанную маржу колонкой (меньше гибкости, больше простоты).

### Б-27 🟢 Листалка в карточке лида и лиды без ответственного

`lead_pager` сужает диапазон листания условием
`Lead.assigned_to_id == lead.assigned_to_id`. Если у лида нет ответственного
(`NULL`), сравнение с `NULL` в SQL всегда ложно — счётчик покажет «0 из 0»
или «— из 0», хотя карточка открыта. По коду лиды без ответственного почти
невозможны (`create_lead` назначает создателя), но путь существует
(PATCH от админа). Стоит либо запретить `assigned_to_id = null` в PATCH,
либо обработать случай явно.

### Т-08 🟢 Ставка вычета маржи задублирована в бэкенде и фронтенде

`MARGIN_DEDUCTION_RATE = 0.25` живёт и в `models/shipment.py`, и в
`ShipmentFormPage.tsx`. Дублирование осознанное (есть комментарий), но при
смене ставки придётся помнить про два места — а расхождение молча даст
разные цифры в таблице и в форме. Минимальный фикс — одной константой в
`/api/v1/launcher` или в settings-эндпоинте; кардинальный — считать маржу
только на сервере.

### И-10 🟢 Список бэкапов дважды делает stat() по каждому файлу

`_scan_backups` (`api/v1/admin.py`): один `stat()` в сортировке по mtime,
второй — при сборе размера. На десятках файлов это ничто, но пишется в один
проход элементарно. Косметика.

## Что сделано хорошо

- **Аутентификация — образцовая для проекта такого размера.** Access-токен
  только в памяти вкладки, refresh в HttpOnly-куке, ротация со счётчиком
  использованных токенов, однопоточное продление сессии (`refreshInFlight`),
  поколение сессии против «воскрешения» после logout, graceful-окно 15 секунд.
  Каждый шаг объяснён комментарием.
- **Кеш спроектирован осторожно:** кешируются только глобальные справочники,
  ключ строится по пути и query (с объяснением, почему это нельзя применять
  к персональным данным), инвалидация молча не роняет основную операцию,
  fallback на in-memory при недоступном Valkey.
- **Пагинация и «листалка» лида** считают позицию и соседей запросами с
  `LIMIT`, без выгрузки всех идентификаторов; порядок листания совпадает с
  доской, диапазон сужен доской ответственного — чужие номера не утекают.
- **CI воспроизводим и содержателен:** зависимости по lock-файлу с хешами,
  `alembic check` ловит забытые миграции, `snapshot.py --check` не даёт
  протухнуть паспорту, `pip-audit` блокирующий, отдельная джоба на реальном
  PostgreSQL 18.
- **Воркер:** резервные копии базы (ежедневно) и вложений (еженедельно),
  удержание по дням, пароль pg_dump не попадает в аргументы процесса,
  уборка журнала входов и потерянных файлов. Все задачи на месте.
- **Фронтенд:** `ApiError` с кодами, единая точка повтора при 401 для
  всех трёх клиентов (json/upload/blob), кеш блобов с вытеснением по памяти,
  предупреждения о несохранённых данных, отказ браузерного HTTP-кеша с
  внятным объяснением.
- **Документация кода** — редкий случай, когда комментарии читаются как
  продолжение дизайна: каждый неочевидный выбор снабжён причиной («почему
  нельзя проще»).
