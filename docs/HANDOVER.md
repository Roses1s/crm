## Задача

Изучить публичные статические файлы CRM на Odoo как визуальный и поведенческий
образец для собственной, небольшой дизайн-системы CRM Detroid. Первый фокус —
карточка лида и правый чаттер; чужие CSS и JavaScript в проект не переносятся.

**Начато:** 30.09.2026 · **от коммита:** `132bcd2`

## План по шагам

- [ ] Шаг 1 — скачать во временный каталог и безопасно разобрать manifest, CSS
  и JavaScript: только чтение, без запуска и без добавления файлов в репозиторий.
- [ ] Шаг 2 — сопоставить образец с нашей карточкой лида и чаттером; записать
  карту различий и целевые собственные токены/компоненты.
- [ ] Шаг 3 — реализовать согласованные визуальные блоки малыми независимыми
  коммитами: каркас карточки, затем форма/статусбар, затем детали чаттера.
- [ ] Шаг 4 — после каждого блока прогонять типы, тесты и сборку; визуально
  сверять с образцом на мониторе владельца 1920×1080, масштаб 100%.
- [ ] Шаг 5 — обновить документацию, закрыть эстафету, отправить изменения и
  дождаться проверок GitHub.

## Где идёт работа

На этапе анализа файлы проекта не меняются, кроме этой эстафеты. Предполагаемые
файлы следующих этапов:

- `frontend/src/index.css`
- `frontend/src/shared/ui/odoo-form.tsx`, `frontend/src/shared/ui/chatter.tsx`
- `frontend/src/features/crm/LeadFormPage.tsx`
- тесты затронутых компонентов, `docs/STATUS.md`

## Договорённости из чата

Публичные `manifest`, `web.assets_web_dark.min.css` и
`web.assets_web_dark.min.js` CRM на Odoo используются только для анализа.
Запрещено подключать, выполнять или копировать их код и стили в CRM Detroid.
Цель — написать собственные короткие стили и компоненты, оптимизированные под
текущую CRM. Не переделывать другие разделы без отдельного запроса владельца.

## Чем проверять

```bash
cd frontend && npx tsc -b && npm test && npm run build
```

## Хвосты и грабли

- Минифицированный JavaScript не запускать: он рассчитан на чужие API,
  зависимости и авторизацию. Разрешено только текстовое чтение.
- Сторонние файлы держать только в `/tmp`, не добавлять в Git и не включать в
  Docker-образ.
- После аналитических этапов не менять внешний вид «по догадке»: сначала
  показать владельцу карту отличий и согласовать очередной небольшой блок.
