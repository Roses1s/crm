## Предыдущая закрытая задача: исправление четырёх P0 глубокого код-ревью

Владелец ответил «продолжай» после отдельного запроса согласования P0. Все
четыре пакета сделаны в `arena/01a0fd83-crm` отдельными проверенными коммитами.
Отчёт-основание: [`CODE_REVIEW_2026-10-02.md`](CODE_REVIEW_2026-10-02.md).
Целевой production: **4 ГБ RAM / 15 ГБ диска**.

Текущий прогресс:

1. **P0.1 cache isolation — готово, коммит `7ef89aa`.** `QueryClient` вынесен
   в `shared/api/query-client.ts`; logout/новый login синхронно отменяют запросы
   и полностью очищают Query/Mutation cache. Поколение сессии не даёт позднему
   refresh воскресить токен после logout. Регресс-тест воспроизводит A → logout
   → B и проверяет, что B не видит данные A.
2. **P0.2 неизменяемая history/status — готово, коммит `149aaef`.** Поле
   `status` удалено из общего `ShipmentUpdate`, неизвестные поля PATCH получают
   422; history нельзя удалить в API; frontend показывает edit/delete только у
   notes. Поведение notes не ужесточалось по автору, чтобы не менять отдельно
   не согласованное бизнес-правило.
3. **P0.3 целостность переноса заявки — готово, коммит `d4e0079`.** Новый лид
   проходит строгую проверку доступа; shipment, timeline и attachments
   переносятся одной транзакцией с блокировкой строки. Миграция
   `b4f7c9d2e6a1` сначала исправляет и повторно считает существующие
   расхождения, затем добавляет отложенные составные FK. Ничего не удаляет;
   downgrade намеренно не возвращает повреждённые lead_id. Воспроизведение на
   старой SQLite-схеме исправило 2/2 специально рассинхронизированные строки;
   clean upgrade, `alembic check` и полные проверки прошли. Реальное число
   исправленных production-строк станет известно из журнала миграции.
4. **P0.4 deploy migration guard — готово, коммит `824abd9`.** `deploy.sh`
   проверяет место с запасом 2 ГБ, после сборки создаёт и валидирует свежий
   `crm-pre-deploy-*.dump`, останавливает пишущие процессы и запускает миграцию
   новым образом отдельным шагом. API при обычном старте миграции больше не
   применяет. Автоматический и ручной rollback сравнивают текущую ревизию БД с
   Alembic head предыдущего backend-образа; при различии старый код не
   запускается. Шесть shell-регрессий проходят.

Локально пройден весь доступный набор: Ruff/format/mypy, 138 backend-прогонов;
чистый Alembic upgrade/check и перенос специально рассинхронизированных данных;
ESLint/Prettier/`tsc`, 62 frontend-теста и build; `bash -n`. Первый CI на
PostgreSQL обнаружил недопустимый `FOR UPDATE` nullable joined-таблиц; коммит
`3bb5abc` сузил блокировку до строки `shipments`. Итоговый GitHub Actions
`37053499064` зелёный: 4/4 задания, включая PostgreSQL и Docker. Всё отправлено
только в `origin arena/01a0fd83-crm`; на production эти исправления уехали
03.10.2026 вместе с остальным накопленным кодом. Деплой выполняет только
владелец вручную.

## Рабочие приёмы (проверены, экономят время)

### Проверки перед коммитом

```bash
cd backend && .venv/bin/ruff check . && .venv/bin/ruff format --check . \
  && .venv/bin/mypy app && .venv/bin/python -m pytest && .venv/bin/alembic check
cd ../frontend && npm run lint && npm run format:check && npx tsc -b && npm test \
  && npm run build
```

`.venv` и `node_modules` песочница не сохраняет — пересоздать:

```bash
cd backend && python -m venv .venv && .venv/bin/pip install -e ".[dev]"
cd ../frontend && npm install
```

### Локальная история откатилась (на GitHub всё цело)

Признак: `git log` показывает один коммит, `git status` — десятки чужих
изменений. Лечится так (файлы при этом целы):

```bash
git fetch origin arena/01a0fe2c-crm
git reset FETCH_HEAD      # mixed: история догоняет, файлы не трогаются
git status --short
```

`merge --ff-only` в этой ситуации не сработает — рабочее дерево грязное.
`reset --hard` не применять никогда.

### Предпросмотр интерфейса без Docker

Бэкенд на SQLite (кеш уходит в память, лимитер выключен), фронтенд —
`npm run dev`, он проксирует `/api` на бэкенд. Демо-вход:
`admin@example.com` / `Preview123`, карточка — `/crm/leads/1`.

### Дамп базы перед рискованной миграцией

Каталога `/opt/crm/backups` на хосте НЕТ — бэкапы живут в docker-томе,
поэтому ручной дамп пишем в домашнюю папку:

```bash
docker exec crm-postgres pg_dump -U crm crm | gzip > ~/dump.sql.gz
gunzip -c ~/dump.sql.gz | grep -c "CREATE TABLE"     # проверка, что не пустой
gunzip -c ~/dump.sql.gz | docker exec -i crm-postgres psql -U crm -d crm   # возврат
```

### Если CI красный, а логи не открываются

У GitHub периодически отказывает хранилище логов (`gh run view --log` отдаёт
EOF). Номер и имя упавшего шага всё равно видно:

```bash
gh run view <id> --json jobs \
  -q '.jobs[] | select(.conclusion=="failure") | .steps[] | "\(.number) \(.name): \(.conclusion)"'
```

ssh crm /opt/crm/deploy.sh

## Паспорт проекта (`docs/SNAPSHOT.md`) — как это работает

Факты о проекте больше не пишут руками: их собирает `scripts/snapshot.py`
прямо из кода (роутеры, сервисы, модели и таблицы, миграции, фоновые задачи,
страницы интерфейса, количество тестов, шаги CI, контейнеры стека).

```bash
python scripts/snapshot.py          # пересобрать
python scripts/snapshot.py --check  # проверить, что не протух (это делает CI)
```

Шаг CI «Паспорт проекта не протух» падает, если код изменили, а паспорт не
пересобрали. Чинится одной командой выше.

Правила, которые нельзя нарушать при правках скрипта:

* только стандартная библиотека (скрипт запускается в любой джобе CI);
* никакой изменчивой информации — хешей коммитов, дат, версии на проде:
  иначе паспорт устаревал бы при каждом коммите и CI был бы вечно красным;
* разбор исходников регулярными выражениями, без импорта приложения.

Мастер-промт (`docs/MASTER_PROMPT.md`) теперь «тонкий»: в нём только правила
и порядок действий, фактов нет — он ссылается на паспорт. Обновлять промт при
изменениях проекта больше не нужно.
