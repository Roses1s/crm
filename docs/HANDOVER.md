## Нет активной задачи

01.10.2026, последняя закрытая задача этой сессии — **6 пунктов по заявкам
и тегам**, план был согласован заранее через уточняющие вопросы владельцу:

1. **Тост «Сохранено»** — `ToastProvider` (`shared/ui/toast.tsx`), подключён в
   корне (`app/providers.tsx`). Зелёная плашка справа сверху, исчезает сама
   через 2,5 сек; вызывается при успешном сохранении лида/заявки — и вручную,
   и автосохранением.
2. **Поиск в списке заявок** — строка поиска в шапке `ShipmentsPage` (раньше
   был только фильтр по статусу). Бэкенд: `GET /shipments?search=` ищет по
   номеру заявки, названию лида и перевозчика (`app/services/shipments.py`),
   спецсимволы `%`/`_` экранируются. Поиск на фронте дебаунсится на 300мс и
   пишет адресную строку с `replace` — как на «Лидах»/«Клиентах» (сразу после
   первой реализации поиск уходил на каждое нажатие клавиши и забивал историю
   браузера; поправлено код-ревью тем же днём).
3. **Вся строка списка заявок кликабельна** — клик в любом месте строки ведёт
   в карточку (`onClick` на `<tr>`), а ячейка номера — настоящий `<Link>`
   (клавиатурный фокус, открытие в новой вкладке, копирование ссылки). Первая
   версия делала это через `role="link"` на `<tr>` без вложенной ссылки —
   код-ревью поправило на более доступный вариант.
4. **Номер заявки вместо имени клиента в заголовке** — новое поле `number`
   у `Shipment` (миграция `ebb7a6f2080f`), по умолчанию = id при создании,
   дальше редактируется как обычное текстовое поле в заголовке формы (как
   название лида в `LeadFormPage`). Используется как колонка «Номер» везде:
   список заявок, вкладка заявок у лида.
5. **Вкладка «Заявки» у лида** — добавлены колонки «Дата создания» и
   «Перевозчик», статус переведён на русский. Словарь статусов и форматер
   даты вынесены в общий `features/shipments/shipment-status.ts` (раньше были
   продублированы только в `ShipmentsPage.tsx`).
6. **Баг тегов: цвет при редактировании не сохранялся** — нашли причиной не
   бэкенд (PATCH работал верно), а саму форму редактирования: клик по цвету
   только менял черновик, реальное сохранение требовало отдельного клика
   «Сохранить», а клик мимо списка тихо отбрасывал выбор без предупреждения —
   воспринималось как «цвет не меняется». Исправлено: цвет (пресет или свой
   HEX) применяется сразу по клику (`TagsField.tsx`, `pickEditColor`); имя
   тега по-прежнему требует явного подтверждения кнопкой. Есть регресс-тест
   `TagsField.test.tsx`. Код-ревью тем же днём доделало и кнопку «Отмена» —
   раньше она просто закрывала панель, а уже автосохранённый цвет оставался
   применённым; теперь «Отмена» откатывает цвет назад к тому, что было у
   тега до открытия редактора.

После реализации этих 6 пунктов (коммит `842d989`) владелец попросил провести

## Рабочие приёмы (проверены, экономят время)

### Проверки перед коммитом

```bash
cd backend && .venv/bin/ruff check . && .venv/bin/ruff format --check . \
  && .venv/bin/mypy app && .venv/bin/python -m pytest && .venv/bin/alembic check
cd ../frontend && npm run lint && npm run format:check && npx tsc -b && npm test \
  && npm run build
```

`.venv` и `node_modules` песочница не сохраняет — пересоздать:

```bash
cd backend && python -m venv .venv && .venv/bin/pip install -e ".[dev]"
cd ../frontend && npm install
```

### Локальная история откатилась (на GitHub всё цело)

Признак: `git log` показывает один коммит, `git status` — десятки чужих
изменений. Лечится так (файлы при этом целы):

```bash
git fetch origin arena/01a0f5c2-crm
git reset FETCH_HEAD      # mixed: история догоняет, файлы не трогаются
git status --short
```

`merge --ff-only` в этой ситуации не сработает — рабочее дерево грязное.
`reset --hard` не применять никогда.

### Предпросмотр интерфейса без Docker

Бэкенд на SQLite (кеш уходит в память, лимитер выключен), фронтенд —
`npm run dev`, он проксирует `/api` на бэкенд. Демо-вход:
`admin@example.com` / `Preview123`, карточка — `/crm/leads/1`.

### Дамп базы перед рискованной миграцией

Каталога `/opt/crm/backups` на хосте НЕТ — бэкапы живут в docker-томе,
поэтому ручной дамп пишем в домашнюю папку:

```bash
docker exec crm-postgres pg_dump -U crm crm | gzip > ~/dump.sql.gz
gunzip -c ~/dump.sql.gz | grep -c "CREATE TABLE"     # проверка, что не пустой
gunzip -c ~/dump.sql.gz | docker exec -i crm-postgres psql -U crm -d crm   # возврат
```

### Если CI красный, а логи не открываются

У GitHub периодически отказывает хранилище логов (`gh run view --log` отдаёт
EOF). Номер и имя упавшего шага всё равно видно:

```bash
gh run view <id> --json jobs \
  -q '.jobs[] | select(.conclusion=="failure") | .steps[] | "\(.number) \(.name): \(.conclusion)"'
```

## Паспорт проекта (`docs/SNAPSHOT.md`) — как это работает

Факты о проекте больше не пишут руками: их собирает `scripts/snapshot.py`
прямо из кода (роутеры, сервисы, модели и таблицы, миграции, фоновые задачи,
страницы интерфейса, количество тестов, шаги CI, контейнеры стека).

```bash
python scripts/snapshot.py          # пересобрать
python scripts/snapshot.py --check  # проверить, что не протух (это делает CI)
```

Шаг CI «Паспорт проекта не протух» падает, если код изменили, а паспорт не
пересобрали. Чинится одной командой выше.

Правила, которые нельзя нарушать при правках скрипта:

* только стандартная библиотека (скрипт запускается в любой джобе CI);
* никакой изменчивой информации — хешей коммитов, дат, версии на проде:
  иначе паспорт устаревал бы при каждом коммите и CI был бы вечно красным;
* разбор исходников регулярными выражениями, без импорта приложения.

Мастер-промт (`docs/MASTER_PROMPT.md`) теперь «тонкий»: в нём только правила
и порядок действий, фактов нет — он ссылается на паспорт. Обновлять промт при
изменениях проекта больше не нужно.
