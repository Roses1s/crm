## P0 из код-ревью: PostgreSQL в CI + реальный IP клиента за прокси

По итогам код-ревью (см. `docs/REVIEW.md`) взялись за самые срочные пункты (P0).

**1. CI теперь проверяет бэкенд и на настоящем PostgreSQL.** Раньше все тесты и
миграции в GitHub Actions шли только на SQLite — из-за этого один раз в прод
уехала миграция с SQLite-only функцией (`json_valid`) и уронила деплой. Добавлена
отдельная джоба «Бэкенд на PostgreSQL — миграции и тесты» (`.github/workflows/checks.yml`):
поднимает `postgres:18-alpine` (как в проде), ставит Python 3.13 (как в проде),
прогоняет `alembic upgrade head` и весь набор тестов на реальной базе. Быстрая
SQLite-джоба осталась для мгновенной обратной связи. В `backend/tests/conftest.py`
добавлена поддержка переменной `TEST_DATABASE_URL`: без неё тесты идут на SQLite
в памяти (как раньше), с ней — на указанной базе (в CI это PostgreSQL);
фикстура `engine` перед каждым тестом пересоздаёт схему на чистом листе.

**2. Приложение снова видит реальный IP клиента за nginx.** В
`backend/gunicorn.conf.py` добавлено `forwarded_allow_ips` (по умолчанию `*`,
можно сузить через `GUNICORN_FORWARDED_ALLOW_IPS`). Бэкенд стоит за обратным
прокси в отдельной docker-сети и снаружи напрямую недоступен, поэтому доверять
заголовкам `X-Forwarded-*` от nginx безопасно. Без этой настройки uvicorn видел
IP docker-шлюза вместо клиента, и ограничение частоты запросов и журнал аудита
считали всех одним адресом.

Локально: SQLite-тесты (70) зелёные, `ruff`/`ruff format` чистые, YAML валиден.
Прогон тестов на PostgreSQL из песочницы невозможен (нет БД) — его выполняет CI.

## P1: перенастройка под сервер 4 ГБ (было 2 ГБ)

Владелец докупил память: теперь на VPS 4 ГБ RAM. Раньше лимиты контейнеров были
подогнаны ровно под 2 ГБ (сумма 1792 МБ) и не давали приложению использовать
память. Пересчитали `docker-compose.yml` под 4 ГБ — контейнерам ~3 ГБ, системе
и swap остаётся ~1 ГБ:

| Контейнер | Было | Стало |
|---|---|---|
| postgres | 512 МБ | **1024 МБ** + тюнинг |
| backend (API) | 448 МБ | **896 МБ**, воркеров 2 → **3** |
| worker | 320 МБ | **448 МБ** |
| valkey | 160 МБ | **256 МБ** |
| beat | 160 МБ | 160 МБ |
| frontend | 96 МБ | **128 МБ** |
| nginx | 96 МБ | **128 МБ** |
| **Итого** | 1792 МБ | **3040 МБ** |

PostgreSQL получил флаги под 1 ГБ памяти (раньше шёл на умолчаниях, где
`shared_buffers` всего 128 МБ): `shared_buffers=256MB`,
`effective_cache_size=768MB`, `work_mem=16MB`, `maintenance_work_mem=128MB`,
`max_connections=120` (запас под 3 воркера × пул). Воркеров Gunicorn 2 → 3
(`GUNICORN_WORKERS` в compose и `.env.example`; запасное значение в
`gunicorn.conf.py` тоже поднято до 3). Valkey намеренно без `maxmemory`-эвикции:
он ещё и брокер Celery, вытеснение ключей потеряло бы задачи.

Изменения применяются при следующем деплое (`ssh crm /opt/crm/deploy.sh`).
Swap на 2 ГБ желателен как страховка независимо от объёма RAM (инструкция —
`docs/deploy/01-server-setup.md`, раздел 1.5).

## P1: устранение блокирующего ввода-вывода в асинхронных ручках

В асинхронном приложении любой синхронный файловый вызов «замораживает» весь
воркер: пока один запрос пишет файл или обходит диск, остальные пользователи
ждут. Вынесли такие операции в пул потоков (`starlette.concurrency.run_in_threadpool`,
идёт с FastAPI — новых зависимостей нет):

- `backend/app/api/v1/attachments.py`:
  - `_save_upload` — создание папки, открытие/запись/закрытие файла и удаление
    недописанного файла теперь идут в потоке; чтение из запроса и раньше было
    асинхронным. Добавлена надёжная очистка: при любом сбое (превышен лимит,
    обрыв соединения) частично записанный файл удаляется.
  - `disk_usage` стала async и обходит каталог вложений (`rglob` + `stat`) в
    потоке; тяжёлый синхронный код вынесен в `_scan_disk_usage`.
- `backend/app/api/v1/admin.py`: ручка `/admin/backups` больше не блокирует
  цикл — чтение каталога бэкапов вынесено в `_scan_backups` (пул потоков),
  `disk_usage()` вызывается через `await`.

Тесты: существующий `test_too_big_file_is_rejected` проверяет очистку
недописанного файла (новый путь `except`); добавлен
`test_backups_report_counts_uploaded_files` — сводка по месту на диске считает
реально загруженный файл. Всего бэкенд: 71 тест, `ruff`/`mypy` чистые.
Изменения применяются при следующем деплое.

## P1: включён кеш глобальных справочников (был «мёртвым»)

`fastapi-cache2` был настроен (Valkey с откатом на память), но декоратор `@cache`
нигде не стоял — кеш не работал. Включили его ТОЛЬКО для глобальных справочников,
одинаковых для всех пользователей и редко меняющихся: список тегов (`/crm/tags`)
и перевозчиков (`/carriers`). Пользовательские данные (лиды, воронки, заявки)
сознательно НЕ кешируем — это риск утечки между аккаунтами и лишняя
рассинхронизация.

Ключевая тонкость: стандартный ключ кеша fastapi-cache учитывает все аргументы
функции, включая внедрённые зависимости (сессию БД, пользователя), чей `repr`
меняется каждый запрос — из-за этого кеш никогда бы не срабатывал. Добавили свой
`public_key_builder` (`backend/app/core/cache.py`), который строит ключ только по
пути и query-параметрам. Он безопасен исключительно для глобальных данных.

Инвалидация: при создании/удалении тега и создании/изменении перевозчика
вызывается `invalidate(namespace)` — кеш соответствующего справочника
сбрасывается, устаревший список не показывается. TTL как запасной предохранитель —
`cache_ttl_seconds` (60 с).

Тесты (`backend/tests/test_cache.py`, 3 шт.): второй одинаковый запрос отдаётся из
кеша (заголовок `X-FastAPI-Cache: HIT`); после изменения справочника список сразу
обновляется (`MISS`); разные `?only_active` кешируются раздельно. Всего бэкенд:
74 теста, `ruff`/`mypy` чистые. Изменения применяются при следующем деплое.

## P1: пароль базы больше не виден в списке процессов (pg_dump)

Ночной бэкап вызывал `pg_dump`, передавая полный URL с паролем последним
аргументом. Такой аргумент виден в списке процессов (`ps aux`) любому на сервере
и может утечь в логи. Исправлено в `backend/app/worker/tasks.py`: добавлен
хелпер `_pg_dump_command`, который разбирает DSN и передаёт параметры подключения
отдельными флагами (`--host/--port/--username/--dbname`), а пароль — только через
переменную окружения `PGPASSWORD` (её понимает libpq). В аргументах пароля больше
нет. Работает и когда настройки заданы через `DATABASE_URL`, и когда через
отдельные `POSTGRES_*`.

Тест `test_pg_dump_command_keeps_password_out_of_argv` проверяет, что пароля нет
ни в одном аргументе команды и что он присутствует только в `PGPASSWORD`.
Всего бэкенд: 75 тестов. Изменения применяются при следующем деплое.

## P2: безопасность зависимостей + прод-паритет CI

- **Dependabot** (`.github/dependabot.yml`): раз в неделю присылает pull request'ы
  с обновлениями зависимостей — отдельно бэкенд (pip), фронтенд (npm) и сами
  GitHub Actions. Плюс автоматические обновления безопасности.
- **pip-audit** в CI (шаг «Аудит зависимостей на уязвимости» в джобе бэкенда):
  проверяет Python-зависимости на известные уязвимости. Шаг ИНФОРМАЦИОННЫЙ
  (`continue-on-error: true`) — показывает уязвимости в логе, но не роняет сборку:
  разовый сбой сети при запросе к базе advisory или свежий advisory без
  исправления не должны блокировать разработку. Плановую починку делает
  Dependabot. (Локально pip-audit чист; в CI шаг один раз падал при блокирующем
  режиме — детали в тот момент были недоступны из-за сбоя хранилища логов GitHub.)
- **Python 3.13 в основной джобе бэкенда** (был 3.11): теперь и быстрая
  SQLite-джоба, и джоба на PostgreSQL идут на той же версии, что и прод
  (`backend/Dockerfile: python:3.13-slim`). Полный прод-паритет по версии Python.

Изменения касаются только CI и автоматизации — на прод не влияют.

### Уточнение по Python 3.13 в CI

Первая попытка перевести и основную (быструю) джобу бэкенда на 3.13 упала на шаге
mypy — статическая проверка под интерпретатором 3.13 с чуть иначе разрешёнными
версиями зависимостей (в бэкенде нет lock-файла). Воспроизвести локально не
удалось (в песочнице только 3.11, интерпретатор 3.13 не скачать), а логи того
прогона GitHub временно не отдавал. При этом СРЕДА ВЫПОЛНЕНИЯ на 3.13 полностью
зелёная — джоба `backend-postgres` гоняет pytest и миграции на 3.13.

Решение: быстрые статические проверки (ruff/mypy) и юнит-тесты остаются на
стабильной 3.11 (mypy закреплён на цель 3.11 в pyproject — прогон воспроизводим),
а прод-паритет среды выполнения (Python 3.13 + PostgreSQL) обеспечивает джоба
`backend-postgres`. Это стандартная раскладка: линт/типы/юнит на фиксированной
версии, интеграция — на прод-версии.

## P2 #3 — слой сервисов в бэкенде

Бизнес-логику вынесли из роутеров в отдельный пакет `backend/app/services/`.
Разделение ответственности:

- `app/api/v1/*.py` — **только HTTP**: путь, параметры запроса, коды ответов,
  `response_model`. Тело обработчика — одна строка «вызвать сервис».
- `app/services/*.py` — **вся логика**: работа с базой, проверки прав
  («чужой лид не существует»), запись в ленту чаттера, файлы на диске.

Что уже перенесено:

| Сервис | Что содержит |
| --- | --- |
| `app/services/leads.py` | доступ (`visible_only`, `get_lead_or_404`), фильтры списка, CRUD лида, лента чаттера, передача лида другому продавцу, переключатель «N / M» |
| `app/services/shipments.py` | доступ к заявке, список, CRUD, смена статуса с записью в ленту, лента заявки, `STAGE_LABELS` |
| `app/services/attachments.py` | белый список расширений, потоковая запись на диск с лимитом, вложения лида и заявки, скачивание, удаление с проверкой прав, подсчёт места на диске |

Поведение API не менялось ни на байт: все прежние тесты проходят без правок,
пути и ответы те же. Это чисто внутренняя перестройка — пользователь разницы
не увидит, но добавлять новую логику и писать на неё тесты стало проще.

Для совместимости старые имена (`get_lead_or_404`, `disk_usage`,
`STAGE_LABELS`) переэкспортируются из прежних модулей роутеров, чтобы не
ломать соседние импорты.

Не тронуты (логики мало, смысла выносить нет): `auth.py`, `stages.py`,
`tags.py`, `carriers.py`, `users.py`, `health.py`, `launcher.py`, `admin.py`.

## P3 — начато

### `alembic check` в CI

Новый шаг в обеих джобах бэкенда: после прогона миграций `alembic check`
сравнивает модели в коде со схемой базы. Падает, если модель изменили, а
миграцию создать забыли — раньше такую ошибку заметили бы только на проде.

Чтобы проверка не давала ложных срабатываний, в `backend/alembic/env.py`
отключено сравнение значений по умолчанию на стороне базы
(`compare_server_default=False`): при добавлении обязательных колонок миграция
ставит `server_default=''` только для заполнения существующих строк, а в модели
его намеренно нет. Сравнение типов (`compare_type=True`) осталось включённым.

### Лимит попыток входа на уровне nginx

`deploy/nginx/conf.d/00-common.conf` — зона `login`: 20 попыток входа в минуту
с одного IP-адреса, ответ при превышении — 429 (а не 503 по умолчанию).
`deploy/nginx/conf.d/crmdetroid.ru.conf` — отдельная локация
`= /api/v1/auth/login` с `limit_req zone=login burst=10 nodelay`.

Это второй рубеж: ограничение входа есть и в самом приложении (10/мин,
`RATE_LIMIT_LOGIN`), но nginx отсекает перебор раньше — запрос не доходит до
бэкенда, базы и Valkey. Лимит действует ТОЛЬКО на адрес входа, остальной API
не затронут.

Проверить конфиг на сервере перед применением:

```
docker compose exec nginx nginx -t
```

### Автопродление сертификата

Проверять нечего: уже настроено и проверено ранее — `certbot.timer` на хосте
плюс deploy-hook `deploy/scripts/reload-nginx.sh`, который шлёт контейнеру

### Выход из системы действительно завершает сессию (чёрный список токенов)

Раньше «Выход» только стирал куку. Сам обновляющий токен оставался
действительным до конца срока: если его успели перехватить, копией можно было
продлевать чужую сессию.

Что сделано:

- новая таблица `revoked_tokens` (миграция `20261001_1200_revoked_tokens.py`,
  ревизия `e5f6a7b8c9d0`): идентификатор токена `jti` + дата истечения;
- при выходе `jti` записывается в эту таблицу;
- ручка обновления `/api/v1/auth/refresh` сверяется со списком и отвечает 401
  «Сессия завершена»;
- еженедельная задача воркера `cleanup_revoked_tokens` (воскресенье, 04:45)
  удаляет записи, срок которых уже истёк, — таблица не растёт.

Тесты: `test_stolen_refresh_token_is_useless_after_logout` (украденную куку
возвращают на место после выхода — 401) и `test_logout_without_cookie_is_ok`.

При деплое миграция применяется автоматически, как обычно.

### Сценарные тесты интерфейса (вместо Playwright)

Настоящий браузерный e2e (Playwright) в этой среде сделать не вышло: браузеры
не скачиваются (сеть песочницы блокирует загрузку Chromium), а писать тесты,
которые нельзя ни разу запустить локально, — значит гадать вслепую.

Сделано то же по сути, но проверяемо: **сценарные тесты**. Подменяется только
сеть (`fetch`), всё остальное настоящее — хуки, HTTP-клиент, кеш запросов,
маршрутизация. Проверяется весь путь «клик → запрос → ответ → экран».

- `frontend/src/test/fake-api.ts` — поддельный сервер: таблица маршрутов,
  журнал запросов, помощник `page()` для ответов со списком. Неописанный адрес
  отвечает 404 с понятным текстом, чтобы забытый маршрут было сразу видно.
- `frontend/src/features/auth/login-flow.test.tsx` — вход: верные данные
  (запрос ушёл, токен сохранён) и неверный пароль (сообщение, токена нет).
- `frontend/src/features/crm/kanban-flow.test.tsx` — доска: загрузка этапов и
  раскладка карточек, поиск уходит в запрос, меню карточки ведёт на её адрес,
  подпись для скринридера на месте.
- `frontend/src/features/shipments/shipments-flow.test.tsx` — заявки: таблица
  с маршрутом/клиентом/перевозчиком, пустой список, отбор по этапу.

Запуск обычный: `npm test` (всего 36 тестов). Отдельной команды и отдельной
джобы в CI не нужно — они идут вместе с остальными.

Если когда-нибудь понадобится настоящий браузерный e2e, делать его лучше
сразу в CI (на runner'е GitHub браузеры ставятся без проблем).

### Чистка старых колонок заявки (city_loading / city_unloading)

Города погрузки и выгрузки давно хранятся списком тегов (`loading_cities` /
`unloading_cities`). Одиночные `city_loading` / `city_unloading` остались от
первой версии заявки: интерфейс их не показывает и не заполняет, они лишь
подставлялись в маршрут как запасной вариант.

Миграция `20261001_1300_drop_legacy_cities.py` (ревизия `f6a7b8c9d0e1`):

1. **сначала переносит** данные — если список городов пуст, а старое поле
   заполнено, город переезжает в список;
2. **только потом** удаляет обе колонки.

Проверено на копии схемы: заявка со старым городом получает
`loading_cities = ["Челябинск"]`, заявка с уже заполненными тегами не
меняется, колонки исчезают. Остальные «старые на вид» поля (адреса, контакты
погрузки/выгрузки, тип транспорта, вес, объём, комментарий) НЕ трогали — они
живые, используются в карточке заявки.

Заодно поля убраны из схем API, типов фронтенда и начальных данных (`cli.py`),
а свойство `route` собирает маршрут только из городов-тегов.

### Lock-файл зависимостей бэкенда

`backend/requirements-dev.lock` — точные версии всех библиотек (включая
зависимости зависимостей) с криптографическими хешами. Основная джоба CI
ставит окружение строго по нему:

```
pip install --require-hashes -r requirements-dev.lock
pip install -e . --no-deps
```

Зачем: раньше каждый прогон тянул свежие версии, и новый релиз чужой
библиотеки мог внезапно уронить сборку (именно это и случилось в P2 #2 на
Python 3.13). Теперь прогон воспроизводим, а обновления приходят управляемо —
через Dependabot.

Обновить lock-файл после правки зависимостей в `pyproject.toml`:

```
cd backend && pip install pip-tools
pip-compile --generate-hashes --extra dev --output-file requirements-dev.lock pyproject.toml
```

Файл собран на Python 3.11 — той же версии, что и основная джоба. Джоба
`backend-postgres` (Python 3.13, прод-паритет) ставит зависимости БЕЗ lock:
так видно, что проект продолжает работать и на свежих версиях, но её падение
не связано с воспроизводимостью.
