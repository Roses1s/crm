# Максимально глубокое код-ревью CRM Detroid

**Дата:** 02.10.2026  
**Проверенный коммит:** `716be63d725e`  
**Ветка:** `arena/01a0fd83-crm`  
**Целевой сервер:** 4 ГБ RAM, 15 ГБ диска  
**Режим работы:** сначала отчёт по неизменённому коду; исправления P0 — только после отдельного согласования с владельцем.

> Этот документ описывает состояние кода на указанном коммите. В ходе ревью
> production-код не менялся. Временные тесты-воспроизведения после запуска удалены.

## Короткий вывод

Проект заметно зрелее обычного MVP: есть понятное разделение FastAPI-роутов и
сервисов, строгая типизация, линейные миграции, PostgreSQL-проверка в CI,
ограничения контейнеров под конкретный VPS, резервные копии, healthcheck,
структурные логи, безопасная схема access/refresh-токенов и хорошие комментарии
«почему так сделано».

При более глубокой проверке найдены четыре группы риска уровня P0:

1. браузерный кеш TanStack Query не очищается между пользователями и реально
   показывает второму сотруднику данные первого;
2. перенос заявки на другой лид меняет только `shipments.lead_id`, но не
   `timeline_entries.lead_id` и `attachments.lead_id`: права расходятся, а
   последующее удаление старого лида удаляет историю и файлы уже перенесённой
   заявки;
3. системную историю можно удалить, а статус заявки можно изменить через
   обычный PATCH без записи в историю — аудит действий нельзя считать
   неизменяемым;
4. автоматический rollback образов после уже применённой миграции не откатывает
   схему БД и способен поднять старый код на несовместимой новой схеме.

Из внешней сети без учётной записи прямой способ эксплуатации не найден.
Основные критичные дефекты требуют либо валидной сессии, либо общей рабочей
станции, либо сбоя деплоя. Но последствия — раскрытие данных между сотрудниками,
потеря файлов/истории, недостоверный аудит и простой production — достаточно
серьёзны для P0.

# 2. Архитектура и границы слоёв

## Положительное

- Анализ 52 runtime-модулей и 154 внутренних import-рёбер не обнаружил ни
  одного runtime-цикла.
- Нижние слои не зависят от `app.api`.
- Домены лидов, заявок, вложений, клиентов и этапов в основном имеют
  `api → services → models/schemas`.
- Session lifecycle корректный: сессия создаётся на запрос и закрывается через
  dependency; общий `AsyncSession` между запросами не переиспользуется.
- Pydantic-схемы отделены от ORM, ответы сериализуются централизованно.

## A-01. 🟡 Warning — архитектура доменов неоднородна

**Где:** `backend/app/api/v1/admin.py`, `auth.py`, `stages.py`, `tags.py`,
`loss_reasons.py`.

В лиды/заявки/вложения бизнес-логика вынесена в services, но перечисленные
роутеры сами выполняют `select`, меняют модели и делают `commit`. В `admin.py`
находятся перенос лидов, создание/изменение пользователей и агрегация
безопасности. В `stages.py` и справочниках — проверки владения и мутации.

**Последствия:**

- инварианты сложнее переиспользовать из другого endpoint или Celery;
- транзакции и права проверяются разными способами;
- глубокие дефекты действительно сконцентрировались там, где роутер и
  бизнес-операция слиты: «последний администратор», гонка начальной доски,
  неограниченная агрегация попыток входа.

**Рекомендация:** не вводить repository-слой ради самого слоя. Для текущего
масштаба достаточно постепенно перенести операции в
`services/users.py`, `services/auth.py`, `services/security.py` и оставить в
роутерах только HTTP-параметры/response model. SQLAlchemy-запросы могут остаться
в сервисах; отдельные repositories нужны только если появится второй источник
данных или много повторяющихся запросов.

## A-02. 🟡 Warning — сервисы сами делают `commit`, поэтому их трудно собрать в одну атомарную операцию

**Где:** `services/leads.py`, `shipments.py`, `attachments.py`, роутеры
справочников.

Почти каждая функция завершает собственную транзакцию. Сейчас это удобно для
простых endpoint, но вызов нескольких сервисных операций нельзя безопасно
объединить: первая уже записала данные, вторая может упасть. Работа с файлами и
БД особенно чувствительна к этой границе.

**Рекомендация:** transaction boundary держать на уровне одного use case:
сервисы меняют объекты и вызывают `flush`, а один orchestrator/endpoint делает
`commit`. На ошибке dependency выполняет rollback. Не требуется переписывать
весь проект сразу — начать с P0-переноса заявки и файловых операций.

## A-03. 🟡 Warning — frontend и backend вручную дублируют контракт

**Где:** `backend/app/schemas/*`, `frontend/src/shared/types/index.ts`,
`frontend/src/shared/api/hooks.ts`.

Типы API написаны вручную. Уже есть расхождение: backend хранит и отдаёт
`customer_address`, `customer_signer`, `loading_time_to`,
`unloading_time_to`, но форма заявки их не загружает и не редактирует.
`ShipmentPayload` знает эти поля, `FormState` — нет.

**Рекомендация:** либо явно удалить неиспользуемые поля отдельной миграцией
после решения владельца, либо показать их в UI. Для предотвращения повторения —
генерировать TypeScript-типы из OpenAPI или добавить contract-тест,
сравнивающий обязательные поля backend-схем и frontend fixtures.

# 3. Backend, SQLAlchemy и целостность данных

## B-01. 🔴 Critical — перенос заявки между лидами рассинхронизирует три таблицы и права доступа

**Где:** `schemas/shipment.py:98`, `services/shipments.py:128-139`,
`models/timeline.py`.

`ShipmentUpdate` разрешает менять `lead_id`. `update_shipment` просто делает
`setattr(shipment, "lead_id", value)`. При этом:

- новый лид не проверяется через `get_lead_or_404`;
- `TimelineEntry.lead_id` старых записей остаётся прежним;
- `Attachment.lead_id` старых файлов остаётся прежним;
- в БД нет ограничения «lead_id дочерней записи совпадает с lead_id заявки».

**Подтверждённые последствия:**

1. менеджер может указать ID чужого лида; API принимает его, после чего заявка
   исчезает у отправителя и оказывается у другого сотрудника;
2. новый владелец видит timeline заявки, но не может скачать старые вложения,
   потому что download проверяет старый `Attachment.lead_id`;
3. прежний владелец сохраняет прямой доступ к файлам через старый lead ID;
4. удаление старого лида каскадно удаляет timeline/attachment rows и физические
   файлы, хотя сама заявка уже относится к новому лиду;
5. новые события после переноса получают новый lead ID, то есть одна timeline
   физически раскалывается между двумя лидами.

Это одновременно дефект авторизации, ссылочной целостности и риск необратимой
потери данных.

**Рекомендация P0:**

```python
async with session.begin():
    shipment = await get_shipment_for_update(...)
    target = await get_lead_or_404(session, payload.lead_id, user)
    shipment.lead_id = target.id
    await session.execute(
        update(TimelineEntry)
        .where(TimelineEntry.shipment_id == shipment.id)
        .values(lead_id=target.id)
    )
    await session.execute(
        update(Attachment)
        .where(Attachment.shipment_id == shipment.id)
        .values(lead_id=target.id)
    )
```

Дополнительно добавить БД-защиту: unique `(shipments.id, shipments.lead_id)` и
составные FK `(shipment_id, lead_id)` у timeline/attachments. Перед миграцией
нужно найти и исправить уже существующие расхождения, с бэкапом и явной
проверкой количества строк.

## B-02. 🔴 Critical — системная история удаляема, а смену статуса можно провести без истории

**Где:** `schemas/shipment.py:99`, `services/shipments.py:128-163,228-233`,
`services/leads.py:416-423`, `shared/ui/chatter.tsx:526-550`.

Есть специальный endpoint `/shipments/{id}/status`, который создаёт запись
history. Но поле `status` одновременно входит в обычный `ShipmentUpdate`, а
обычный PATCH не пишет timeline. Оба DELETE endpoint ленты удаляют запись без
проверки `EntryType`; frontend показывает кнопку удаления и для history.
Редактирование запрещено для history, удаление — нет.

Кроме того, текущий владелец карточки может редактировать любое примечание,
даже созданное другим автором до передачи лида.

**Последствия:** пользователь с обычной ролью может переписать фактическое
состояние заявки и удалить доказательство изменения. Журнал остаётся красивым,
но не является надёжным аудитом.

**Рекомендация P0:**

- удалить `status` из `ShipmentUpdate`; менять его только через специальный
  use case;
- запретить удаление `EntryType.history` на backend независимо от UI;
- решить правило для notes: только автор или администратор, либо soft-delete с
  `deleted_at/deleted_by`;
- убрать кнопку удаления history на frontend;
- тестировать, что status всегда создаёт ровно одну запись истории и что
  history нельзя PATCH/DELETE.

## B-03. 🟡 Warning — `create_lead` не проверяет соответствие этапа и владельца

**Где:** `services/leads.py:133-143`.

В update такая проверка уже есть через `stage_on_board`, но create принимает
произвольный существующий `stage_id`. Менеджеру `assigned_to_id` заменяется на
его ID, однако этап остаётся чужим. Подтверждено API-тестом.

**Последствие:** карточка существует в БД, но не попадает ни на одну корректную
личную доску.

**Рекомендация:** сначала определить итогового владельца, затем вызвать
`stage_on_board(session, payload.stage_id, owner_id)`. Для администратора также
проверять, что назначаемый пользователь существует и активен.

## B-04. 🟡 Warning — система позволяет остаться без администратора

**Где:** `api/v1/admin.py:97-111`, `schemas/user.py`.

Удалить себя endpoint не позволяет, но последний администратор может изменить
себе `role=manager` или `is_active=false`. Тест подтвердил успешный ответ.
После завершения текущей access-сессии административного доступа не останется;
восстановление потребует ручного SQL на сервере.

**Рекомендация:** в одной транзакции и с блокировкой проверять, что после
изменения остаётся хотя бы один активный admin. Учесть гонку двух администраторов,
которые одновременно понижают себя; простой предварительный `COUNT` без lock
недостаточен.

## B-05. 🟡 Warning — PATCH-схемы принимают `null` для NOT NULL колонок

**Где:** `LeadUpdate`, `ShipmentUpdate`, `StageUpdate`, `UserUpdate`.

Паттерн `field: str | None = None` нужен для «поле можно не передать», но он же
принимает явный JSON `null`. Затем `exclude_unset=True` сохраняет этот `null` в
NOT NULL колонку. В лучшем случае получается 409 с неверным текстом «запись уже
существует», в худшем для необработанного DBAPI/DataError — 500.

Особенно опасны `ShipmentUpdate.status`, `lead_id`, `created_at`, налоговые
ставки, строковые поля; `LeadUpdate.name/inn/stage_id`; `UserUpdate.role` и
`is_active`.

**Рекомендация:** отдельно различать «UNSET» и `None`: обязательные в БД поля
при явном `null` должны получать 422. Nullable business-поля (цены, даты,
email) можно очищать `null`. Добавить параметризованные contract-тесты для
каждого PATCH.

## B-06. 🟡 Warning — API не полностью отражает ограничения PostgreSQL

**Где:** `schemas/shipment.py`, `models/shipment.py`, `schemas/crm.py`.

Примеры:

- `Numeric(10,2)`/`Numeric(10,3)` имеют `ge=0`, но нет `max_digits` и
  `decimal_places`;
- строки `String(40/50/100/255)` часто не имеют `max_length` в Pydantic;
- время погрузки/выгрузки хранится как произвольная строка;
- не проверяется `date_from <= date_to` и `time_from <= time_to`;
- массивы городов/типов кузова не имеют разумных ограничений длины.

SQLite-тесты часть этих ограничений не эмулируют. На PostgreSQL пользователь
может получить 500/409 вместо понятного 422 или сохранить логически
противоречивый диапазон.

**Рекомендация:** привести Pydantic constraints к моделям БД, добавить
`model_validator` диапазонов и PostgreSQL-тесты на границы Numeric/String.

## B-07. 🟡 Warning — неизвестные tag IDs молча отбрасываются

**Где:** `services/tags.py:11-14`.

`fetch_tags` возвращает все найденные записи, но не сравнивает их количество с
уникальным набором ID. Опечатка, удалённый тег или чужой stale cache приводят к
успешному 200, хотя часть запроса не выполнена.

**Рекомендация:** нормализовать IDs, получить теги, вычислить missing IDs и
вернуть 422/404 с кодом `tags_not_found`. Дубли либо отклонять, либо явно
дедуплицировать.

## B-08. 🟡 Warning — причина проигрыша может исчезнуть у проигранного лида

**Где:** FK `Lead.loss_reason_id` с `ON DELETE SET NULL`, endpoint удаления
причины.

Лид переводится в проигрыш только с обязательной причиной, но администратор
может затем удалить причину. Получается `is_archived=true` и
`loss_reason_id=NULL`. Timeline хранит текст, но сама timeline тоже сейчас
удаляема.

**Рекомендация:** не удалять используемые причины физически: `is_active=false`
или 409 при наличии ссылок. После очистки текущих данных добавить DB
CheckConstraint для согласованности `is_archived/loss_reason_id`.

## B-09. 🟡 Warning — создание начальных этапов подвержено гонке

**Где:** `services/stages.py::ensure_default_stages`.

Алгоритм «SELECT пусто → INSERT набор» не защищён уникальным ограничением. Два
первых одновременных запроса нового пользователя могут создать две одинаковые
доски. Это реально возможно при нескольких вкладках или повторе запроса через
proxy.

**Рекомендация:** создавать доску в транзакции создания пользователя либо
ввести unique `(owner_id, name)`/защиту блокировкой и корректно обработать
`IntegrityError`. Добавить PostgreSQL concurrency-тест.

## B-10. 🟡 Warning — файловая система и БД обновляются неатомарно

**Где:** `services/attachments.py:151-164,268-270`,
`services/leads.py:290-305`.

- upload сначала полностью пишет файл, затем делает DB commit; ошибка commit
  оставляет файл без строки;
- delete attachment сначала удаляет файл, затем commit; ошибка commit оставляет
  строку, но данные уже потеряны;
- permanent lead delete сначала удаляет строки, затем файлы; ошибка unlink
  оставляет файлы без строк;
- cleanup удаляет только DB-строки отсутствующих файлов, но не ищет файлы без
  DB-строк.

**Рекомендация:** временное имя + DB transaction + атомарный `rename`, либо
корзина с возможностью вернуть файл при rollback. Добавить двусторонний
reconciler и тесты с искусственной ошибкой commit/unlink. Не выполнять обычный
`Path.unlink` прямо в event loop.

## B-11. 🟡 Warning — глобальная eager-loading стратегия перегружает запросы заявок

**Где:** relationships `Shipment.lead lazy="joined"`, вложенные
`Lead.stage/assigned_to/loss_reason lazy="joined"`, теги `selectin`.

Скомпилированный обычный `select(Shipment)` выбирает около 70 колонок и делает
JOIN к leads, stages, users и loss_reasons. Для списка заявок реально нужны
только короткие поля, имя лида и продавца. Дополнительно может загружаться
коллекция тегов лида, которая в `ShipmentListItem` не используется.

Это не классический N+1 — запросов мало, — но это систематический over-fetch.
На лимите 200 строк он увеличивает память API, трафик БД и время сериализации.

**Рекомендация:** relationships по умолчанию `lazy="raise"/"select"`, а
конкретные endpoint явно задают `joinedload/selectinload/load_only`. Для списка
заявок лучше projection-запрос ровно под `ShipmentListItem`.

## B-12. 🟡 Warning — timeline и журнал входов растут без срока хранения

**Где:** `lead_timeline`, `shipment_timeline`, `LoginAttempt`,
`admin.login_attempts`.

Timeline возвращается целиком без `limit/cursor`. `login_attempts` никогда не
очищается, а административная сводка группирует всю историю, хотя возвращает
только 50 групп. Индекс по `created_at` не заменяет retention.

**Последствия:** растущие ответы, память браузера/API, всё более дорогая
агрегация и рост БД/бэкапов на диске 15 ГБ.

**Рекомендация:** cursor pagination timeline; срок хранения попыток входа
(например, согласованные 90/180 дней) и периодическая пакетная очистка; составные
индексы под реальные фильтры после `EXPLAIN ANALYZE` на копии production.

## B-13. 🟢 Suggestion — поиск с `%строка%` не масштабируется

Поиск лидов/заявок использует leading wildcard `ILIKE '%...%'`; B-tree индексы
не помогут. На текущих сотнях записей это нормально. При росте до десятков
тысяч строк следует добавить `pg_trgm` GIN индексы только после измерения, а не
заранее.

## B-14. 🟢 Suggestion — Alembic намеренно не сравнивает server defaults

`compare_server_default=False` устраняет шум от исторических миграций, но
одновременно делает `alembic check` слепым к случайному изменению defaults.
Линейная цепочка и типы сейчас корректны. На будущее лучше нормализовать
исторические defaults отдельной миграцией и включить сравнение либо покрыть
важные defaults schema-тестом.

# 4. Безопасность, auth и RBAC

## Положительное

- access-токен хранится только в памяти, refresh — HttpOnly, Secure в production,
  SameSite=Lax и узкий cookie path;
- JWT разделяет `access`/`refresh`, имеет `jti` и срок жизни;
- секрет production проверяется fail-fast, localhost CORS запрещается;
- CORS — явный allowlist, `allow_credentials` не сочетается с `*`;
- docs/OpenAPI закрыты в production и дополнительно закрыты Nginx;
- login rate limit есть на Nginx и в приложении;
- файлы получают случайные storage names, path traversal удаляется через
  `Path(...).name`, SVG/HTML не входят в allowlist;
- CSP, HSTS, `nosniff`, frame restrictions и современный TLS настроены;
- поиск типовых private keys/API tokens в tracked files ничего не нашёл;
- `.env` корректно игнорируется.

## S-01. 🔴 Critical — TanStack Query cache раскрывает данные предыдущей сессии

**Где:** `frontend/src/app/providers.tsx:7`,
`shared/api/hooks.ts:89`, `shared/api/client.ts:60`.

Один singleton `QueryClient` живёт всё время жизни SPA. Logout/неудачный refresh
очищают только access token. Query keys (`me`, `leads`, `shipments`, timeline,
attachments, launcher) не содержат user/session ID. `me` считается свежим 5
минут, другие данные — 30 секунд.

**Воспроизведение:** после загрузки `admin + admin-secret-lead`, выхода и входа
менеджером тот же экран показал admin-данные. Mock fetch получил по одному
запросу `/auth/me` и `/crm/leads`: от имени менеджера новые запросы не ушли.
На общей рабочей станции это реальная межпользовательская утечка.

**Рекомендация P0:** при любом переходе сессии делать `cancelQueries()` и
`queryClient.clear()` до отображения новой сессии. Надёжнее дополнительно
создавать новый QueryClient на поколение сессии или включать stable user ID в
ключи. Нужны тесты:

1. A → logout → B не видит ни одного объекта A;
2. 401/refresh failure очищает кеш;
3. незавершённый запрос A не может после входа B снова наполнить общий кеш.

## S-02. 🟡 Warning — старый refresh-токен остаётся рабочим после ротации и logout

**Где:** `api/v1/auth.py:42-50,102-131,134-165`.

Каждый refresh выдаёт новый токен, но старый не отзывается. Logout отзывает
только токен из текущей cookie. Временный тест: старый токен сохранён, выполнен
refresh, затем logout с новым токеном; повтор старого токена вернул 200 и новый
access token.

**Последствие:** украденная старая копия живёт до 14 дней и переживает обычный
выход владельца.

**Рекомендация:** refresh rotation с token family: при каждом refresh старый
`jti` атомарно помечается использованным, выдаётся новый; повтор использованного
`jti` отзывает всю family. Это соответствует рекомендации OWASP использовать
sender-constrained refresh tokens либо rotation с обнаружением reuse:
<https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html>.

## S-03. 🟡 Warning — bcrypt молча игнорирует часть длинного пароля после 72 байт

**Где:** `core/security.py`, `schemas/user.py`.

Схема разрешает до 128 символов, но bcrypt учитывает только первые 72 **байта**.
Два разных пароля с одинаковыми первыми 72 байтами успешно прошли один хеш.
Для Unicode лимит достигается раньше 72 символов.

**Рекомендация:** предпочтительно мигрировать новые хеши на Argon2id через
`pwdlib`, сохранив verify-and-rehash старых bcrypt-хешей при входе. Более
локальный вариант — предварительный SHA-256/HMAC + bcrypt с явным marker/version.
Просто обрезать пароль нельзя; минимум — отклонять ввод длиннее 72 UTF-8 байт с
понятной ошибкой.

## S-04. 🟡 Warning — существующий и несуществующий email имеют разное время проверки

**Где:** `auth.py:65-72`.

Для отсутствующего пользователя дорогой bcrypt verify не выполняется из-за
short-circuit. Текст ответа одинаковый, но время позволяет статистически
проверять наличие email. Два rate limiter снижают риск, но не устраняют его.

**Рекомендация:** один раз подготовить корректный dummy password hash и всегда
вызывать verify — с реальным или dummy hash. Не логировать полный введённый
email на уровне, доступном широкому кругу.

## S-05. 🟡 Warning — попытка входа отключённого пользователя записывается как успешная

`ok` означает только «пароль совпал». `LoginAttempt(successful=ok)` коммитится
до проверки `user.is_active`; затем endpoint возвращает 403. Поэтому журнал
считает такой вход успешным, хотя сессия не выдана.

**Рекомендация:** различать `credentials_valid` и реальный `login_success`, либо
ставить `successful = ok and user.is_active`. Решить, должен ли ответ раскрывать
состояние disabled account; безопаснее оставить общий 401.

## S-06. 🟡 Warning — публичный readiness возвращает внутренний текст исключений

**Где:** `api/v1/health.py:31,39`.

В ответ попадает `str(exc)` от PostgreSQL/Valkey. Он может раскрыть внутренние
hostnames, порты, имя БД и детали драйвера. Общий exception handler специально
скрывает такие сведения, readiness его обходит.

**Рекомендация:** клиенту возвращать только `"ok"/"error"`, полный exception
писать структурированно в server log с request ID. Добавить короткие connect/read
timeouts.

## S-07. 🟢 Suggestion — сеть с именем `internal` технически не является Docker internal network

В Compose есть сеть `internal`, но нет свойства `internal: true`. Postgres и
Valkey не имеют published ports — снаружи они действительно недоступны, это
хорошо. Однако комментарий «без выхода наружу» неверен: обычный bridge имеет
egress.

**Рекомендация:** если worker/Postgres/Valkey не нужен интернет, добавить
`internal: true` после проверки маршрутизации. Backend остаётся также в `edge`,
поэтому его egress это само по себе не ограничит.

## S-08. 🟢 Suggestion — Gunicorn доверяет proxy-заголовкам от любого адреса

`forwarded_allow_ips="*"` безопасен только пока backend нельзя достичь в обход
Nginx. Сейчас порт не опубликован, поэтому непосредственной дыры нет. Для
hardening лучше доверять подсети/адресу reverse proxy или явно зафиксировать это
как топологический инвариант и тестировать Compose.

# 5. Frontend, React, Query, Router, a11y и производительность

## Положительное

- TypeScript strict, no-unused и fallthrough checks включены;
- Query keys централизованы;
- optimistic updates имеют snapshot/rollback/invalidate;
- auth token не хранится в localStorage;
- редкие модули lazy-loaded;
- поиск заявок debounce 300 мс и хранит состояние в URL;
- строки таблицы содержат настоящие ссылки для клавиатуры/Ctrl-click;
- drag-and-drop имеет отдельные flow-тесты;
- Tailwind-тема и UI-примитивы собраны централизованно.

## F-01. 🟡 Warning — UI игнорирует серверную пагинацию и молча скрывает записи

**Где:** `hooks.ts:36,265,666`.

- лиды загружаются с `page_size=200`;
- заявки — 200;
- клиенты — 500;
- hook возвращает только `results`, отбрасывая `count/next/previous`;
- `ControlPanel` показывает `results.length`, то есть число загруженных, а не
  общее число.

**Последствие:** 201-й лид/заявка или 501-й клиент не будет виден, и UI не
сообщит, что список обрезан. Для CRM это уже риск бизнес-данных, а не только
оптимизация.

**Рекомендация:** сохранить полный `Page<T>` в hook и реализовать
`useInfiniteQuery`/серверный pager. Канбану — cursor или paging по колонкам;
таблицам — явные страницы. До полной реализации хотя бы показывать
«загружено 200 из N» и кнопку «загрузить ещё».

## F-02. 🟡 Warning — карточка заранее скачивает все небольшие изображения в память

**Где:** `chatter.tsx:26,49`, `file-preview-utils.ts`.

Каждый `AttachmentThumb` сразу вызывает authenticated blob download. Timeline и
вложения тоже не пагинируются. Лимит 5 МБ применяется к каждому изображению, а
не к сумме. Например, 100 файлов по 5 МБ дают до 500 МБ blob-данных плюс decode
memory браузера.

**Рекомендация:** IntersectionObserver/lazy thumbnail, серверная миниатюра или
скачивание только при раскрытии секции; pagination timeline; ограничить
одновременные fetch. Object URL продолжать обязательно revoke при unmount.

## F-03. 🟡 Warning — четыре backend-поля заявки отсутствуют в форме

`customer_address`, `customer_signer`, `loading_time_to`,
`unloading_time_to` есть в ORM/Pydantic/API type, но не входят в `emptyForm`, не
загружаются и не отправляются формой. Пользователь не может увидеть или
исправить данные, созданные через API/старую версию.

**Рекомендация:** требуется продуктовое решение: вернуть поля в UI или удалить
их из API/БД безопасной миграцией. Не оставлять третий вариант «хранятся, но
невидимы».

## F-04. 🟡 Warning — CRM и dnd-kit входят даже в начальный login bundle

`KanbanPage` и `LeadFormPage` импортированы статически. Поэтому login/launcher
сразу получают основной chunk 382 КБ raw и dnd chunk около 50,8 КБ raw, хотя
канбан ещё не открыт. Общий начальный объём около 167 КБ gzip приемлем для
настольной CRM, но split можно сделать лучше.

**Рекомендация:** lazy-load оба CRM route так же, как shipments/customers/admin.
Добавить bundle budget в CI, например предупреждение при main > 130 КБ gzip и
initial > 180 КБ gzip; конкретные пороги сначала согласовать по текущему baseline.

## F-05. 🟡 Warning — большинство модальных окон не являются доступными dialog

`UserFormDialog`, `DeleteLeadDialog`, `LoseLeadDialog`, `TransferDialog`, быстрые
формы и диалог колонки — это визуальные overlays без `role="dialog"`,
`aria-modal`, связи с заголовком, focus trap, возврата фокуса и общего Escape.
Реализации дублируются по features. File preview и mobile nav сделаны лучше, но
единого dialog primitive нет.

**Рекомендация:** общий `shared/ui/dialog.tsx` на нативном `<dialog>` или
проверенной headless-библиотеке; тесты keyboard-only: открыть, Tab не выходит,
Escape закрывает, фокус возвращается на кнопку.

## F-06. 🟡 Warning — действия timeline невидимы при клавиатурном фокусе

Контейнер действий имеет `opacity-0 group-hover:opacity-100`, но нет
`group-focus-within`/`focus-visible`. Tab может поставить фокус на невидимую
кнопку. На touch hover-only UX также непредсказуем.

**Рекомендация:** показывать на `group-focus-within`, обеспечить видимую рамку
`focus-visible`, на touch/узких экранах показывать действия постоянно или через
явное меню.

## F-07. 🟢 Suggestion — QueryClient логирует ошибки, но UI не всегда различает loading/error/empty

Глобальный `console.error` полезен разработчику, но часть страниц при ошибке
может показать пустой список, визуально неотличимый от отсутствия данных.
Нужны единые компоненты `QueryError/Retry`, особенно для списков и карточек.

# 6. Docker, Nginx, Gunicorn, Celery и сервер 4 ГБ / 15 ГБ

## 6.1. Память

Лимиты контейнеров суммарно: PostgreSQL 1024 + backend 896 + worker 448 +
Valkey 256 + beat 160 + frontend 128 + edge Nginx 128 = **3040 МиБ**. На 4 ГБ
остаётся примерно 1 ГБ под kernel, Docker и краткие всплески; 2 ГБ swap описаны
в инструкции. Для обычной нагрузки одной компании конфигурация разумна.

Риск остаётся в пике: PostgreSQL `work_mem=16MB` выделяется на операцию
sort/hash, а не один раз на сервер; до 120 соединений теоретически способны
превысить лимит контейнера. API может открыть до 90 соединений
`3 × (10 + 20)`, Celery — ещё около 15. Сейчас это скорее запасной риск, а не
подтверждённый bottleneck.

**Рекомендация:** не увеличивать workers/pools без load test и пересчёта. Для
текущего малого VPS рассмотреть более консервативные pool overflow/work_mem после
замера p95 запросов и числа одновременных пользователей.

## I-01. 🔴 Critical — автоматический rollback образов не согласован с миграциями БД

**Где:** `deploy.sh:170-180,246-260`, backend command в Compose.

Новый backend при старте выполняет `alembic upgrade head`. Если миграция прошла,
но приложение/Nginx затем не стало healthy, `deploy.sh` автоматически возвращает
предыдущие образы. Схема при этом остаётся новой. В истории уже есть
несовместимые миграции с удалением таблиц/колонок, поэтому старый код может не
работать на новой схеме. Скрипт предупреждает о миграциях только в конце
успешного деплоя — после аварийного rollback решение уже принято автоматически.

Также скрипт сам не создаёт pre-deploy dump и не проверяет свободное место; это
оставлено ручной инструкции.

**Рекомендация P0:**

1. до изменения контейнеров проверить свободное место и создать/проверить
   локальный pre-deploy dump;
2. запускать миграцию отдельным явным шагом с журналом текущей/новой revision;
3. применять expand/contract: релиз N добавляет совместимое, релиз N+1
   переключает код, только N+2 удаляет старое;
4. автоматический rollback разрешать только если миграции не применялись или
   явно backward-compatible;
5. если новая схема уже применена — выдавать понятную остановку и процедуру,
   а не обещать, что старый образ безопасен.

Откат миграции нельзя автоматизировать вслепую: downgrade может удалять новые
данные. Это должно остаться осознанной операцией владельца с бэкапом.

## I-02. 🟡 Warning — диск 15 ГБ не имеет жёсткой quota/low-disk защиты

Вложения до 25 МБ, текущие файлы, четыре еженедельных архива вложений, 14
дампов БД, PostgreSQL, Valkey AOF, Docker layers/build cache и логи делят один
небольшой диск. Многие JPG/PDF/XLSX уже сжаты, поэтому `tar.gz` может быть почти
размером исходного набора: один файл фактически присутствует в active storage
и до четырёх раз в архивах.

Нет общего лимита на пользователя/лида/все вложения и нет отказа upload/backup
при низком свободном месте. `/admin/backups` показывает место только после
ручного открытия.

**Рекомендация:** согласовать минимальный резерв (например, не принимать upload
и не начинать files backup ниже 2–3 ГБ), показывать понятную admin-ошибку,
проверять место в `deploy.sh`, удалять временный/неуспешный архив. Конкретный
порог определить после замера фактического размера pgdata/backups; внешнее
хранилище в рамках этого ревью не предлагается.

## I-03. 🟡 Warning — production собирается не из lock-файла

`backend/Dockerfile` выполняет `pip install .`, а `pyproject.toml` задаёт нижние
границы с `>=`. Один и тот же git-коммит, пересобранный через месяц, может
получить другие FastAPI/SQLAlchemy/Gunicorn/Uvicorn. Быстрый CI использует
hash-locked `requirements-dev.lock`, но production image — нет.
`backend-postgres` CI тоже ставит `.[dev]` без lock, то есть проверяет «сегодняшний
latest», но не гарантирует воспроизводимость будущего rebuild.

**Рекомендация:** отдельный hash-locked production requirements файл и
`pip install --require-hashes`; приложение ставить `--no-deps`. Обновлять lock
осознанным PR вместе с CI.

## I-04. 🟡 Warning — `uvicorn.workers.UvicornWorker` официально deprecated

Импорт в текущем окружении уже выдаёт `DeprecationWarning`. Uvicorn рекомендует
отдельный пакет `uvicorn-worker`; старый модуль планируется удалить:
<https://www.uvicorn.org/deployment/>.

**Рекомендация:** добавить и зафиксировать `uvicorn-worker`, заменить class на
`uvicorn_worker.UvicornWorker`, собрать образ и проверить graceful restart,
forwarded headers и healthcheck.

## I-05. 🟡 Warning — оба runtime используют устаревшую ветку Nginx 1.27

`frontend/Dockerfile` и edge service используют `nginx:1.27-alpine`. На дату
ревью официальный актуальный mainline образ — 1.31.x:
<https://hub.docker.com/_/nginx>. Старый mutable tag не получает преимущества
новой ветки; локального image scan не было, поэтому утверждать конкретную CVE
нельзя.

**Рекомендация:** протестировать и обновить оба места минимум до одного
актуального patch tag, затем закрепить digest или автоматическое контролируемое
обновление. После обновления проверить `nginx -t`, TLS, CSP, proxy upload и
healthcheck.

## I-06. 🟡 Warning — healthchecks проверяют liveness, а не реальную готовность

Backend Docker health и внешний `deploy.sh` вызывают `/health`, который всегда
отвечает 200, пока жив Python-процесс. Уже существующий `/health/ready`
проверяет БД и Valkey, но не используется. Деплой может быть объявлен успешным,
хотя запросы к данным не работают.

**Рекомендация:** Docker/deploy readiness направить на безопасный endpoint без
утечки exception details. Liveness оставить отдельным, чтобы временный сбой БД
не создавал бесконечный restart storm.

## I-07. 🟢 Suggestion — mutable major tags не дают полной воспроизводимости образов

`python:3.13-slim`, `node:22-alpine`, `postgres:18-alpine`, `valkey:8-alpine` и
Nginx tags меняются со временем. Для security patches это удобно, но rollback и
расследование сложнее. Компромисс: pin patch + digest и обновлять Dependabot/
Renovate; либо хотя бы записывать digests собранного релиза в deploy log.

## I-08. 🟢 Suggestion — часть документации всё ещё говорит о сервере 2 ГБ

`docker-compose.yml` у worker пишет «на 2 ГБ»,
`docs/deploy/01-server-setup.md` в итоговой таблице указывает 1,9 ГБ RAM + 2 ГБ
swap, `docs/PROJECT.md` в troubleshooting упоминает сборку на 2 ГБ. Реальный
сервер подтверждён как 4 ГБ.

**Рекомендация:** после согласования исправлений привести комментарии и итоговые
таблицы к 4 ГБ, не удаляя полезную историческую подсказку про swap.

# 7. Тестирование и CI/CD

## Положительное

- SQLite suite быстрый, отдельный job повторяет миграции и тесты на PostgreSQL 18;
- `alembic upgrade head` и `alembic check` запускаются в CI;
- Ruff, format, mypy, ESLint, Prettier, tsc, Vitest и production build обязательны;
- Docker Compose config и оба image build проверяются;
- project snapshot защищён от рассинхронизации;
- Dependabot настроен для pip/npm/actions;
- GitHub Actions уже используют актуальные major на дату ревью;
- npm/pip audits есть и сейчас не находят известных уязвимостей.

## T-01. 🟡 Warning — coverage измеряется вручную и не защищает CI

Backend pytest config не включает coverage/fail-under. Frontend не имеет
coverage script/threshold. Текущие цифры: backend branch 73%; frontend lines
51,72%, branches 50,09%, functions 38,57%.

Низкое покрытие само по себе не доказывает плохой код, но именно непокрытые
границы дали P0: смена сессии, перенос FK, неизменяемость history, последний
admin.

**Рекомендация:** начать с текущего baseline без требования 90%: не позволять
покрытию уменьшаться, а для критичных services/auth требовать выше общего.
Важно считать все frontend files (`coverage.all=true`), иначе отчёт завышается.

## T-02. 🟡 Warning — нет тестов реального lifecycle/Valkey/Celery/concurrency

Test fixtures создают таблицы из ORM metadata и не запускают lifespan
приложения. Поэтому не проверяются:

- init/close cache и fallback между тремя workers;
- реальный SlowAPI storage;
- Celery broker/result routing, beat schedule и task timeouts;
- одновременное создание default stages;
- повтор/падение backup task;
- двухфазные ошибки файл ↔ БД.

**Рекомендация:** небольшой integration job с Valkey и lifespan, Celery eager
не заменяет хотя бы один smoke через настоящий broker. Concurrency-инварианты
проверять на PostgreSQL.

## T-03. 🟡 Warning — нет browser E2E для основных бизнес-потоков

jsdom не проверяет настоящий drag-and-drop, focus trap, blob preview/download,
cookie attributes, browser navigation и responsive layout. Минимальный
Playwright smoke должен покрыть:

1. login → канбан → открыть/создать лид;
2. создать заявку → сменить статус → проверить историю;
3. logout A → login B → нет данных A;
4. клавиатурное открытие/закрытие dialog;
5. upload/download небольшого файла.

## T-04. 🟢 Suggestion — passing test suites создают много шума в stderr/warnings

Frontend пишет React `not wrapped in act(...)` и jsdom
`Not implemented: navigation to another Document`. Backend даёт 222 warnings:
основная масса — повторяющийся `InsecureKeyLengthWarning` из-за 11-байтного
тестового JWT secret; ещё есть deprecated Starlette-названия HTTP 413/422.
Production secret защищён отдельным валидатором, поэтому это не production-
уязвимость, но такой объём шума скрывает новое полезное предупреждение.

**Рекомендация:** дать тестам ключ не короче 32 байт, заменить deprecated
константы, исправить frontend act/navigation mocks и считать неожиданный
`console.error` ошибкой теста.

## T-05. 🟡 Warning — security audits информационные и контейнеры не сканируются

`pip-audit`/`npm audit` имеют `continue-on-error: true`; даже high advisory не
блокирует релиз. Image/OS packages (`nginx`, Alpine/Debian, postgresql-client)
не проверяются Trivy/Grype. Сегодня известные package vulnerabilities не
найдены, но процесс не остановит будущую критичную находку.

**Рекомендация:** registry/network failures можно оставить informational, но
подтверждённый High/Critical должен блокировать после согласованного allowlist с
датой истечения. Добавить image scan после Docker build.

## T-06. 🟢 Suggestion — restore test остаётся только ручным

Скрипт восстановления есть и документирован — это лучше, чем просто создавать
непроверяемые дампы. Но CI не поднимает временный PostgreSQL, не восстанавливает
последовательность dump и не выполняет smoke query. Автоматизировать можно на
искусственном CI dump без production-данных; production restore drill оставить
ручным и осознанным.

# 8. ТОП-10 проблем

1. 🔴 **Query cache между сессиями** — второй сотрудник видит свежие данные
   первого без нового запроса.
2. 🔴 **Перенос заявки меняет только `shipments.lead_id`** — права на файлы
   расходятся, удаление старого лида уничтожает историю/файлы новой заявки.
3. 🔴 **Timeline не является аудитом** — history удаляется, статус меняется в
   обход специального endpoint без события.
4. 🔴 **Rollback после миграции** — старый образ автоматически запускается на
   потенциально несовместимой новой схеме.
5. 🟡 **Последний admin может понизить/отключить себя** — административная
   блокировка всей CRM.
6. 🟡 **Refresh replay** — старый refresh переживает ротацию и logout до 14 дней.
7. 🟡 **bcrypt 72 bytes** — разные длинные пароли считаются одинаковыми.
8. 🟡 **Нет дискового предохранителя на 15 ГБ** — вложения и четыре их архива
   способны заполнить диск и остановить БД/деплой.
9. 🟡 **Frontend отбрасывает pagination metadata** — записи после 200/500
   молча исчезают из интерфейса.
10. 🟡 **Production runtime невоспроизводим/устаревает** — backend ставится по
    `>=`, Nginx 1.27 устарел, встроенный UvicornWorker deprecated.

Пункты 5–10 важны, но не должны задерживать точечное закрытие P0 1–4.

# 9. Roadmap P0–P3

## P0 — согласовать и исправить до следующего рискованного релиза

### P0.1. Изоляция browser cache по сессии

- централизованный session transition;
- cancel + clear QueryClient на logout, refresh failure и перед login другого
  пользователя;
- защита от late response старой сессии;
- regression-тест A → B.

### P0.2. Атомарный перенос заявки и ремонт существующих данных

- проверить право на новый лид;
- в одной транзакции обновить shipment, timeline и attachment lead IDs;
- найти расхождения в существующей БД и показать владельцу количество;
- миграция с составными FK только после переноса и проверки данных;
- тесты доступа к старым/новым вложениям и удаления старого лида.

### P0.3. Неизменяемая системная история

- status только через `set_status`;
- history нельзя редактировать/удалять;
- правило авторства для notes;
- frontend не предлагает запрещённое действие;
- regression-тесты API и UI.

### P0.4. Безопасный deploy при миграциях

- preflight свободного места и pre-deploy dump;
- отдельный migration step;
- журнал revisions;
- не выполнять слепой image rollback после несовместимой миграции;
- expand/contract правило для будущих удалений колонок.

## P1 — ближайшая итерация безопасности и целостности

- защита последнего активного admin с concurrency;
- refresh token family/reuse detection;
- Argon2id или явная защита bcrypt 72 bytes;
- validate stage ownership при create lead;
- запрет явного `null` для NOT NULL PATCH;
- строгие tag IDs, Numeric/String/range validators;
- fail-safe delete loss reasons;
- disk low-water mark и retention `login_attempts`;
- production dependency lock;
- переход на `uvicorn-worker` и актуальный Nginx;
- readiness без утечки внутренних исключений.

## P2 — производительность, UX и поддерживаемость

- реальная pagination/infinite query для лидов, заявок, клиентов и timeline;
- lazy thumbnails и ограничение параллельных blob download;
- projection queries/load-only вместо глобального eager over-fetch;
- двухстороннее согласование файлов и БД;
- защита гонки default stages;
- решение по четырём невидимым полям заявки;
- общий доступный Dialog и keyboard UX timeline;
- lazy-load CRM route и bundle budget;
- постепенный перенос SQL/commit из routers в services;
- индексы только по результату `EXPLAIN ANALYZE`.

## P3 — усиление процесса

- coverage baseline/gates;
- Playwright smoke;
- integration Valkey/Celery/lifespan;
- image scan и блокирующий High/Critical security gate;
- CI restore smoke на искусственном dump;
- очистить test stderr;
- привести 2 ГБ комментарии/таблицы к фактическим 4 ГБ;
- записывать image digests в журнал релиза.

# 10. Предлагаемый порядок согласования P0

Чтобы не смешивать четыре разных риска в один большой опасный релиз,
рекомендуется четыре небольших набора изменений:

1. **Frontend cache isolation** — без миграции, самый быстрый и безопасный fix.
2. **Audit invariants** — backend + frontend + тесты, без изменения данных.
3. **Shipment consistency** — сначала read-only диагностика production, затем
   перенос данных и миграция с constraints; это единственный P0, где особенно
   важны бэкап и подтверждение количества затронутых строк.
4. **Deploy migration guard** — shell/docs/Compose, тестирование на временном
   стеке; не запускать впервые вслепую на production.

До отдельного ответа владельца эти исправления в код не вносятся.

# 11. Финальное заключение

CRM имеет хорошую основу: код читаемый, слои в основном понятны, CI сильный,
миграции проходят с нуля, текущие package audits чистые, runtime рассчитан под
4 ГБ лучше, чем у большинства небольших проектов. Поэтому найденные проблемы
не требуют переписывания системы.

Главная тема ревью — **границы контекста**:

- граница пользовательской сессии в браузере;
- граница агрегата «заявка + её история + её файлы»;
- граница между изменяемой заметкой и системным аудитом;
- граница между версией приложения и версией схемы БД.

Точечное усиление этих четырёх границ даст больший эффект, чем широкий
рефакторинг, смена фреймворка или увеличение числа тестов без приоритета.
