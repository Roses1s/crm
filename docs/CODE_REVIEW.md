## 1. Архитектура и структура

🟢 **Хорошо**: чёткое разделение `api/v1` (HTTP) → `services` (бизнес-логика)
→ `models`/`schemas`. Роутеры почти не содержат логики, сервисы не знают про
FastAPI. Нет циклических импортов между доменами (проверено `grep` по
`from app.services... import` — зависимости идут в одну сторону:
attachments/shipments → leads, никогда наоборот).

🟡 **Предупреждение — межмодульная связь через реэкспорт.**
`app/api/v1/leads.py` в конце файла делает:
```python
__all__ = ["User", "get_lead_or_404", "router", "visible_only"]
```
и `attachments.py`/`shipments.py` импортируют `get_lead_or_404`/`visible_only`
не из `services.leads` напрямую, а частично из роутера. Это смешивает HTTP-слой
и слой доступа: роутер стал неявной точкой реэкспорта бизнес-функций.
Рекомендация: импортировать `get_lead_or_404`/`visible_only` только из
`app.services.leads` везде, убрать `__all__`-реэкспорт из роутера — он не нужен
ни одному потребителю, которого нельзя было бы переключить на прямой импорт.

🟡 **Предупреждение — валидатор ИНН дублируется между Lead и Carrier без переиспользования.**
`LeadBase.validate_inn` проверяет длину и контрольную сумму ФНС. У `Carrier`
(`schemas/carrier.py`) и `LeadUpdate` этой проверки либо нет вообще
(`CarrierCreate.inn` — только `min_length/max_length`, без вызова
`_inn_checksum_ok`), либо она подключена хаком:
```python
_validate_inn = field_validator("inn")(LeadBase.validate_inn.__func__)  # type: ignore[attr-defined]
```
Рекомендация: вынести `_inn_checksum_ok` и `validate_inn` в отдельный модуль
`app/schemas/validators.py` и переиспользовать как обычную функцию в
`field_validator` трёх мест (Lead create/update, Carrier create/update) — без
`.__func__`-трюка и без `# type: ignore`.

## 2. Backend

### 🔴 Критично — `User.leads` с `lazy="selectin"` грузит лиды пользователя на КАЖДЫЙ аутентифицированный запрос

`app/models/user.py`:
```python
leads: Mapped[list[Lead]] = relationship(back_populates="assigned_to", lazy="selectin")
```
`lazy="selectin"` — это не «ленивая» загрузка в обычном смысле, а указание
SQLAlchemy **всегда** догружать коллекцию отдельным `SELECT ... WHERE
assigned_to_id IN (...)` при любой загрузке `User`. А `User` грузится в
`get_current_user()` (`app/api/deps.py`) через `session.get(User, user_id)` —
**на каждый запрос с Bearer-токеном**, то есть практически на каждый HTTP-вызов
в системе.

Проверено эмпирически (SQLite, echo=True): один `session.get(User, id)`
реально порождает не один, а **три** запроса:
```
1) SELECT * FROM users WHERE id = ?
2) SELECT leads.*, stages_1.*, users_1.*, loss_reasons_1.*
   FROM leads
   LEFT OUTER JOIN stages AS stages_1 ON ...
   LEFT OUTER JOIN users AS users_1 ON ...
   LEFT OUTER JOIN loss_reasons AS loss_reasons_1 ON ...
   WHERE leads.assigned_to_id IN (?)
3) SELECT lead_tags.lead_id, tags.* FROM lead_tags JOIN tags ... WHERE lead_tags.lead_id IN (...)
```
Запрос №2 раздувается ещё сильнее из-за `lazy="joined"` на `Lead.stage`,
`Lead.assigned_to`, `Lead.loss_reason` — то есть загружаются вообще все лиды
менеджера вместе с тремя джойнами на каждый, плюс (№3) теги каждого лида. При
этом результат **нигде не используется**: `UserRead` (`schemas/user.py`) не
отдаёт `leads`, и по всему бэкенду `grep -rn "\.leads\b"` не находит ни одного
обращения к `user.leads`/`current_user.leads`. Коллекция существует только
как обратная сторона `back_populates` и никому не нужна.

Для менеджера с сотней активных лидов это означает: **каждый** клик в
интерфейсе (открыть заявку, зайти в админку, посмотреть профиль) тянет за
собой лишний тяжёлый запрос с тройным джойном плюс запрос тегов — нагрузка
растёт линейно с числом лидов пользователя, хотя сам запрос к этим данным
не имеет отношения.

**Рекомендация** — убрать лишнюю нагрузку и одновременно защититься от
случайного обращения к коллекции в будущем:
```python
# app/models/user.py
leads: Mapped[list[Lead]] = relationship(
    back_populates="assigned_to",
    lazy="raise",   # обращение из кода — явная ошибка на этапе разработки,
                     # а не молчаливый лишний SELECT на каждый запрос
)
```
`lazy="raise"` — идиоматичный способ SQLAlchemy зафиксировать «эта связь не
должна лениво грузиться нигде»: если когда-нибудь кто-то напишет
`user.leads`, тест/запрос упадёт сразу с понятной ошибкой, а не тихо добавит
третий SELECT на каждый HTTP-вызов.

### 🔴 Критично — `PATCH /crm/leads/{id}` принимает `stage_id` с чужой доски без проверки владельца

Личные канбан-доски — ключевая архитектурная особенность проекта (у каждого
сотрудника свой набор `Stage`, `Stage.owner_id` обязателен). Код в нескольких
местах явно защищает этот инвариант:
- `DELETE /crm/stages/{id}` проверяет, что `fallback_stage_id` принадлежит
  той же доске (`fallback.owner_id != stage.owner_id` → 404);
- `POST /crm/stages/reorder` отвергает набор этапов с разных досок;
- `transfer_lead`/`restore_lead` специально вызывают `board_stage_for()`,
  чтобы найти валидный этап **на доске получателя**, а не доверять
  произвольному `stage_id`.

Но обычный `PATCH /crm/leads/{id}` (`services/leads.py::update_lead`) —
именно та ручка, которой пользуется перетаскивание карточки в канбане
(`useMoveLead` на фронтенде) — этого не делает:
```python
new_stage = data.get("stage_id")
if new_stage is not None and new_stage != lead.stage_id:
    old_name = lead.stage.name if lead.stage else "—"
    new_stage_obj = await session.get(type(lead.stage), new_stage)   # только за именем для ленты!
    ...
for key, value in data.items():
    setattr(lead, key, value)                                        # stage_id проставляется как есть
```
Нет проверки `new_stage_obj.owner_id == lead.assigned_to_id`. Подтверждено
тестом (httpx + реальные роуты, без моков):
```python
async def test_update_lead_accepts_foreign_stage(auth_client, seeded, session):
    manager = seeded["manager"]
    lead = seeded["lead"]           # лид админа, этап на доске админа
    foreign = Stage(name="Чужой", sequence=1, color="red", owner_id=manager.id)
    session.add(foreign); await session.commit(); await session.refresh(foreign)

    resp = await auth_client.patch(f"/api/v1/crm/leads/{lead.id}",
                                    json={"stage_id": foreign.id})
    assert resp.status_code == 200          # фактически так и отвечает
    assert resp.json()["stage_id"] == foreign.id
```
Тест прошёл: сервер молча принял `stage_id` с доски другого пользователя.
Практический эффект — лид получает `stage_id`, которого нет среди этапов
доски своего владельца, и **пропадает из любого канбана** (ни на своей доске,
ни на чужой он не отрисуется, так как колонки фильтруются по
`Stage.owner_id`). Через обычный UI такое не произойдёт (фронтенд всегда
берёт `stage_id` из `useStages()` своей доски), но это чисто клиентская
гарантия: сам API не проверяет инвариант, на котором держится вся схема
персональных досок. Любой баг на фронте, будущий клиент API (мобильное
приложение, интеграция) или прямой вызов с валидным токеном могут тихо
сломать данные без единой ошибки сервера.

**Рекомендация** — переиспользовать ровно ту же проверку, что уже есть в
`owned_stage()` (`api/v1/stages.py`), в `update_lead`:
```python
# services/leads.py
from app.api.v1.stages import owned_stage  # или вынести owned_stage в services/stages.py

async def update_lead(session, user, lead_id, payload):
    lead = await get_lead_or_404(session, lead_id, user)
    data = payload.model_dump(exclude_unset=True)
    tag_ids = data.pop("tag_ids", None)

    new_stage = data.get("stage_id")
    if new_stage is not None and new_stage != lead.stage_id:
        new_stage_obj = await session.get(Stage, new_stage)
        if new_stage_obj is None or new_stage_obj.owner_id != lead.assigned_to_id:
            raise AppError(
                "Этап должен принадлежать доске того же сотрудника",
                code="stage_wrong_board",
            )
        ...
```
(Функцию `owned_stage` стоит сразу вынести из `api/v1/stages.py` в
`services/stages.py` — сейчас это ещё один случай бизнес-логики, живущей в
HTTP-слое, см. раздел 1.)

### 🟡 Предупреждение — нет защитного валидатора `SECRET_KEY` для продакшена

```python
# core/config.py
secret_key: str = "dev-secret-change-me"
```
`.env.example` корректно просит сгенерировать `openssl rand -hex 32` и
`.env` не коммитится — процессная защита есть. Но в коде нет programmatic
guard: если кто-то забудет переопределить переменную (или скопирует старый
`.env` без неё) в контейнере с `ENVIRONMENT=production`, приложение тихо
стартует с дефолтным 21-байтовым ключом, которым подписываются все JWT.
Короткий ключ `dev-secret-change-me` — публично известная строка из
репозитория, то есть фактически отсутствие подписи.

**Рекомендация** — fail-fast валидатор в `Settings`:
```python
from pydantic import model_validator

class Settings(BaseSettings):
    ...
    @model_validator(mode="after")
    def _secret_key_is_safe_in_production(self) -> "Settings":
        if self.is_production and (
            self.secret_key == "dev-secret-change-me" or len(self.secret_key) < 32
        ):
            raise ValueError(
                "SECRET_KEY не задан или слишком короткий для production "
                "(нужно >=32 байт, сгенерировать: openssl rand -hex 32)"
            )
        return self
```
Так некорректная конфигурация роняет контейнер при старте (это сразу видно в
`docker compose logs`), а не подписывает токены предсказуемым ключом.

### 🟡 Предупреждение — бюджет соединений с БД подобран впритык

`db_pool_size=10` + `db_max_overflow=20` на воркер × `GUNICORN_WORKERS=3`
(в проде) = до 90 соединений от API, плюс Celery worker (свой синхронный
движок с дефолтным `QueuePool`, ещё ~15), итого до ~105 против
`max_connections=120`, заданных в `docker-compose.yml` для Postgres. Это
работает, но запас всего ~15 соединений — если когда-нибудь поднимут
`GUNICORN_WORKERS` (например, при переезде на более мощный сервер) без
пересчёта `db_pool_size`, можно упереться в `max_connections` именно в пике
нагрузки, а не при разработке. Нигде в коде/документации нет явной формулы
"сколько воркеров — сколько max_connections нужно".

**Рекомендация**: зафиксировать формулу в комментарии рядом с обеими
настройками (`docker-compose.yml` и `config.py`) — например,
`max_connections >= GUNICORN_WORKERS * (db_pool_size + db_max_overflow) + запас_для_celery_и_alembic`
— и/или снизить `db_max_overflow` до более консервативного значения, раз
штатная нагрузка CRM для одной компании не требует всплесков в 20
дополнительных соединений на воркер.

### 🟡 Предупреждение — у валюты/веса в заявке нет защиты от отрицательных значений

`ShipmentBase`/`ShipmentUpdate`: `customer_price`, `carrier_price`,
`cargo_weight`, `cargo_volume`, `capacity` — все `Decimal | None` без `ge=0`.
Ничто не мешает сохранить отрицательную цену или вес через API (исключая
UI-ограничения, которых со стороны сервера не видно).

**Рекомендация**:
```python
customer_price: Decimal | None = Field(default=None, ge=0)
carrier_price: Decimal | None = Field(default=None, ge=0)
cargo_weight: Decimal | None = Field(default=None, ge=0)
cargo_volume: Decimal | None = Field(default=None, ge=0)
capacity: Decimal | None = Field(default=None, ge=0)
```

### 🟢 Предложение — просроченный default для `Tag.color`

```python
# models/crm.py
class Tag(Base, TimestampMixin):
    ...
    color: Mapped[str] = mapped_column(String(20), default="blue", nullable=False)
```
Миграция `20261001_1600_generic_tags.py` перевела все цвета тегов на HEX, а
`TagCreate.color` в схеме теперь по умолчанию `"#3B82F6"` с regex-валидацией
`^#[0-9a-fA-F]{6}$`. Но ORM-уровневый default в модели остался со старых
времён именованных цветов ("blue") — если когда-нибудь тег будет создан
в обход Pydantic-схемы (сид-скрипт, консоль, будущая миграция данных), он
получит значение, не проходящее собственную же валидацию тега. Сейчас не
стреляет только потому, что единственный путь создания тега — через
`TagCreate`, которая всегда передаёт цвет явно. Стоит привести в
соответствие: `default="#3B82F6"`.

### 🟢 Предложение — `Carrier.inn` без контрольной суммы и уникальности

В отличие от `Lead.inn` (контрольная сумма ФНС на уровне схемы + CHECK на
длину на уровне БД), у `Carrier.inn` нет ни проверки чек-суммы, ни
уникального индекса, ни `CheckConstraint` на длину. Так как раздел
перевозчиков по вашему решению (п.1 истории задач) сейчас сознательно не
дорабатывается, это не блокер, но стоит учесть при следующей итерации по
перевозчикам — заодно с переиспользованием общего валидатора ИНН
(см. находку в разделе «Архитектура»).

## 3. Frontend

🟢 **Хорошо**: ключи TanStack Query централизованы в одном объекте `keys`,
оптимистичные обновления (`useMoveLead`, `useUpdateLeadPriority`,
`useReorderStages`) реализованы по канону — `onMutate`/snapshot/`onError`
rollback/`onSuccess` invalidate. Ленивая загрузка редко посещаемых разделов
(`admin/*`, `customers`, `shipments`, `accounting`) через `React.lazy`,
ручной `manualChunks` в Vite для react/dnd-kit/react-query. `tsconfig` в
строгом режиме (`strict`, `noUnusedLocals`, `noUnusedParameters`,
`noFallthroughCasesInSwitch`). Access-токен — только в памяти, через
`useSyncExternalStore`, без localStorage; refresh — HttpOnly-кука.

🟡 **Предупреждение — `apiUpload`/`apiBlob` не продлевают сессию при 401, в отличие от `api()`.**

`client.ts::api()` при 401 один раз пробует `refreshSession()` и повторяет
запрос — пользователь не замечает, что токен истёк. `apiUpload` (загрузка
вложений) и `apiBlob` (скачивание/просмотр вложений) этой логики не
повторяют — они просто используют текущий токен из памяти и при 401 отдают
`ApiError` без retry. Если access-токен (живёт 30 минут) истёк ровно в
момент загрузки большого файла или открытия вложения, пользователь получит
необъяснимую ошибку вместо тихого продления сессии, как во всех остальных
запросах приложения.

**Рекомендация** — вынести общий «403/401 → refresh → retry один раз» в
отдельную обёртку и использовать её в обеих функциях:
```ts
async function withRefreshRetry<T>(run: (token: string | null) => Promise<Response>): Promise<T> {
  let response = await run(getAccessToken());
  if (response.status === 401 && (await refreshSession())) {
    response = await run(getAccessToken());
  }
  ...
}
```

🟢 **Предложение — на фронтенде нет клиентской защиты admin-маршрутов по роли.**

`RequireAuth` проверяет только факт входа, не роль; `/admin/*` открыт в
роутере любому аутентифицированному пользователю — реальная проверка прав
целиком на бэкенде (это прямо документировано в комментарии `RequireAuth`
как сознательное решение: «проверку прав делает бэкенд»). Это нормально с
точки зрения безопасности (сервер — источник истины), но UX от этого
страдает: менеджер, перейдя на `/admin/users`, получит либо пустой экран,
либо серию 403 из каждого запроса, вместо мгновенного редиректа. Стоит
добавить лёгкую проверку `user.role === "admin"` в `AdminLayout` просто для
UX (не как замену серверной проверке).

🟢 **Предложение — нет `npm audit`/эквивалента в CI для фронтенда.**

В CI (`.github/workflows/checks.yml`) аудит уязвимостей (`pip-audit`) есть
только для backend. У фронтенда (58 файлов, десятки npm-зависимостей,
включая транзитивные) проверки известных CVE нет вообще — зависимости
обновляются только тогда, когда Dependabot/человек сам заметит. Стоит
добавить шаг (по аналогии с backend — информационный, `continue-on-error`,
чтобы не блокировать мердж из-за внешнего реестра):
```yaml
- name: Аудит зависимостей фронтенда
  continue-on-error: true
  run: npm audit --audit-level=high
```

## 4. Инфраструктура / DevOps

🟢 **Хорошо**: docker-compose целиком продуман под целевой VPS — лимиты
памяти на каждый контейнер (сумма ~2.97 ГБ при заявленных в
`.env.example`/комментариях 4 ГБ, что оставляет разумный запас под хост и
Docker daemon), ротация логов (`max-size: 10m`, `max-file: 3`), healthcheck
на каждый сервис кроме `beat` (обоснованно — нечего проверять), сеть
разделена на `internal`/`edge`, наружу торчит только nginx. Postgres
настроен не «по умолчанию» (`shared_buffers=256MB`,
`effective_cache_size=768MB`, `work_mem=16MB`) — видно, что тюнинг
осознанный, а не скопирован бездумно.

> Примечание по вводным задачи: формулировка запроса называла целевой сервер
> «2 ГБ RAM / 15 ГБ диск», но в самом репозитории (`docker-compose.yml`,
> `.env.example`) последовательно фигурирует **4 ГБ RAM** («на VPS с 4 ГБ
> памяти держим 3 [воркера] (на 2 ГБ было 2)») — то есть, по всей видимости,
> сервер уже был один раз расширен с 2 до 4 ГБ, и конфигурация это
> отражает. Ревью ниже исходит из текущего состояния репозитория (4 ГБ) как
> источника истины.

🟡 **Предупреждение — в CSP остались неиспользуемые разрешения на Google Fonts.**

`deploy/nginx/snippets/security-headers.conf`:
```
style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
font-src 'self' https://fonts.gstatic.com data:;
```
Комментарий тут же объясняет это подключением шрифта Inter из Google Fonts —
но по `docs/PROJECT.md` этот шрифт убрали 30.09.2026 в пользу системного
стека, и в коде (`index.html`, `index.css`, `public/*`) ни единого упоминания
`fonts.googleapis.com`/`fonts.gstatic.com` уже нет (проверено `grep` по всему
`frontend/`). CSP — это белый список «что разрешено», и расширять его сверх
реально нужного — всегда лишняя поверхность атаки (пусть и небольшая, так
как `script-src` этих доменов не включает). Нужно убрать более неиспользуемые
исключения:
```
style-src 'self' 'unsafe-inline';
font-src 'self' data:;
```

🟡 **Предупреждение — CI не проверяет, что Docker-образы вообще собираются.**

Джобы `backend`/`backend-postgres`/`frontend` в `.github/workflows/checks.yml`
гоняют линтеры/типы/тесты/`vite build`, но нигде не делают `docker build` ни
для `backend/Dockerfile`, ни для `frontend/Dockerfile`, не валидируют
`docker-compose.yml` (`docker compose config`). Учитывая, что бэкенд-образ
тянет `postgresql-client-18` из внешнего APT-репозитория пакетом
(`apt.postgresql.org`), поломка в этом шаге (смена URL, протухший GPG-ключ)
обнаружится только в момент деплоя на сервер, а не на пуше в ветку.

**Рекомендация** — лёгкая джоба:
```yaml
  docker-build:
    name: Образы собираются
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build ./backend -t crm-backend:ci
      - run: docker build ./frontend -t crm-frontend:ci
      - run: docker compose config -q
```

🟢 **Предложение — `pre-commit` завязан на абсолютный путь `backend/.venv/bin/mypy`.**

Хуки `mypy`/`pytest`/`tsc` в `.pre-commit-config.yaml` используют
`language: system` и жёстко заданный путь до локального venv разработчика —
если у кого-то venv лежит не в `backend/.venv` (например, `uv venv` создаёт
`.venv` в другом месте по умолчанию только при запуске из каталога
`backend/`, но это легко нарушить), хук просто не найдёт исполняемый файл и
либо упадёт с невнятной ошибкой, либо (хуже) тихо пропустится в зависимости
от настроек. Для аккуратности лучше использовать `repo: local` с явным
`language: python` и `additional_dependencies`, либо хотя бы echo-проверку
существования файла с понятным сообщением. Не критично, так как CI всё
равно является source of truth.

## 5. Безопасность

Общий фон хороший и нетипично зрелый для проекта такого масштаба: JWT с
коротким access/длинным refresh в HttpOnly-куке с `secure`+`samesite=lax`,
отзыв refresh-токенов через чёрный список (`revoked_tokens`), двойной рубеж
rate-limit на логин (nginx `limit_req` + `slowapi` в приложении — защита не
дублирует зря, а именно эшелонируется, что явно прокомментировано в коде),
белый список расширений для вложений (блокирует `.svg`/`.html`, исключая
XSS через собственный домен), `pg_dump` без пароля в аргументах командной
строки (через `PGPASSWORD`), централизованная обработка исключений без утечки
деталей (`IntegrityError` → общий 409, `exc.orig` только в лог),
`server_tokens off`, полный набор security-заголовков включая CSP,
`X-Frame-Options`, HSTS. Из новых находок, не покрытых другими разделами:

🔴 **См. раздел «Backend», находка №2** (отсутствие проверки владельца
`stage_id` в `update_lead`) — это, по сути, брешь в авторизации
(IDOR-подобная): уровень данных, на который может влиять менеджер через
легитимный токен, выходит за пределы собственной доски, хоть напрямую
прочитать чужие данные так и нельзя (сам лид по-прежнему защищён
`visible_only`).

🟡 **Предупреждение — `forwarded_allow_ips = "*"` в Gunicorn по умолчанию.**
```python
forwarded_allow_ips = os.getenv("GUNICORN_FORWARDED_ALLOW_IPS", "*")
```
Комментарий в коде верно объясняет, зачем это нужно (бэкенд физически
недостижим, кроме как через nginx, в закрытой docker-сети) — в текущей
топологии риска нет. Но это значение «доверяй любому», а не «доверяй nginx»:
если когда-нибудь появится путь к backend в обход nginx (например, отладочный
`docker compose exec` с проброшенным портом, или ещё один reverse-proxy
добавят в `edge`-сеть), `X-Forwarded-For` от любого источника будет
приниматься как есть — а на нём завязаны rate-limit и аудит by-IP. Стоит
сузить до IP docker-сети nginx (`172.x.x.x/16` или алиас `crm-nginx`), если
Gunicorn/uvicorn это поддерживают, либо явно задокументировать риск как
принятый (аналогично тому, как задокументирован риск с бэкапами на одном
диске с БД в PROJECT.md §11).

🟢 **Предложение**: `CORS_ORIGINS` по умолчанию в `config.py` —
`["http://localhost:5173"]`, а `.env.example` переопределяет на
`["https://crmdetroid.ru"]`. Корректно, но стоит добавить тот же
model_validator, что и для `SECRET_KEY` — запрет на `localhost`-origin при
`ENVIRONMENT=production`, чтобы ошибка конфигурации (забытый `.env`) была
видна сразу при старте, а не как загадочный CORS-реджект в браузере у
живых пользователей.

## 6. Качество кода

🟢 **Хорошо**: ruff + ruff-format + mypy strict на backend, eslint + prettier
+ tsc strict на frontend, pre-commit hooks, `.gitignore` аккуратен (`.env`,
`*.db`, кеши инструментов, `node_modules`/`dist`/`.venv` — ничего лишнего не
коммитится). Комментарии в коде почти всегда объясняют «почему», а не
«что» — редкое и ценное качество (`# Строго по lock-файлу...`,
`# populate_existing перезаписывает уже загруженные связи...`) — это
реально экономит время ревьюеру и будущим разработчикам.

🟡 Раздел «Архитектура» уже отметил дублирование/хак с валидатором ИНН между
`Lead`/`Carrier`/`LeadUpdate` — классическое нарушение DRY, которое к тому же
потребовало `# type: ignore[attr-defined]`, то есть разработчик сам знал, что
решение не идеально типобезопасно.

🟢 Автогенерируемый `docs/SNAPSHOT.md` с CI-гардом «паспорт проекта не
протух» — отличная практика, редко встречается даже в зрелых командах.

## 7. Производительность

🔴 См. «Backend» находку №1 (`User.leads` + `lazy="selectin"`) — главная
находка этого раздела, конкретный измеримый N+1-подобный оверхед на каждый
запрос.

🟡 **Предупреждение — `cleanup_orphan_attachments` читает ВСЮ таблицу `attachments` в память.**
```python
attachments = list(session.execute(select(Attachment)).scalars())
for attachment in attachments:
    if attachment.storage_path and not Path(attachment.storage_path).exists():
        session.delete(attachment)
```
При текущем масштабе (CRM одной компании) это неощутимо, но задача растёт
линейно с числом вложений без постраничной обработки — а по `docs/PROJECT.md`
порог пересмотра подхода к вложениям уже зафиксирован (~1 ГБ/диск <3 ГБ).
Стоит на том же пороге пересмотреть и эту задачу — выбирать только
`storage_path` (не всю строку) и обрабатывать пачками (`yield_per`), а не
материализовывать весь список сразу.

🟢 Остальная работа с БД — качественная: `selectinload`/`lazy="joined"` для
отображаемых в списках связей (`Lead.stage`, `Lead.assigned_to`,
`Lead.tags`), курсор-независимая, но осмысленно построенная пагинация
«N / M» (`lead_pager`) считает позицию через `COUNT`/`LIMIT 1`, а не
выгружает все id в память — в коде прямо прокомментировано, что это
сознательное исправление прежнего подхода.

## 8. Тестирование

🟢 **Хорошо**: 109 pytest-функций + 48 Vitest-тестов + 3 «flow»-интеграционных
файла (`docs/SNAPSHOT.md`). Тесты backend гоняются и на SQLite (быстро,
каждый PR), и повторно на настоящем PostgreSQL в CI — это ловит именно те
расхождения диалектов, которые чаще всего пропускают в проектах с одной
тестовой БД. `alembic check` в CI гарантирует, что модели и миграции не
разъезжаются. Фикстура `seeded` в `conftest.py` даёт реалистичный минимальный
набор данных (админ, менеджер, два этапа на разных досках, тег, перевозчик).

🟡 **Предупреждение — у находок №1 и №2 из раздела «Backend» не было тестов,
хотя оба инварианта (неиспользуемая связь, владение этапом) по духу кода
важны для авторов** (сравните с тем, насколько тщательно протестирован сам
`delete_stage` с `fallback_stage_id` — там есть явная проверка владельца и,
скорее всего, тест на неё). Это не «тестов мало вообще», а конкретный пробел:
нет теста вида «нельзя через PATCH лида проставить чужой stage_id» — хотя
ровно такой тест есть по смыслу для `delete_stage`. Рекомендация — добавить
тест-регрессию сразу вместе с фиксом из находки №2.

🟢 Предложение — нет e2e-слоя (Playwright/Cypress) поверх реального браузера.
Для CRM такого размера с 3 «flow»-тестами на уровне API+React Testing Library
это разумный компромисс (дешевле поддерживать), но стоит держать в уме как
кандидата на будущее, если UI-регрессии (например, в dnd-kit канбане) станут
источником багов, которые не ловит текущий уровень тестов.

## Итоговая оценка: **8.2 / 10**

**Обоснование.** Это заметно более зрелый проект, чем типичный MVP:
осознанная архитектура (роутеры/сервисы/модели), документированные
компромиссы вместо случайных решений, тюнинг инфраструктуры под конкретное
железо, двухуровневая защита от перебора паролей, разумная модель доступа
(видимость по ролям, 404 вместо 403 для чужих лидов), зрелый CI (SQLite +
Postgres, миграции, snapshot-гард, мypy strict). Это не «курсовая работа» —
видно, что над проектом думали, а не просто писали код, который проходит
тесты.

Снижают оценку: два конкретных и воспроизводимых дефекта критичного уровня
(неконтролируемый лишний запрос на каждый HTTP-вызов и дыра в проверке
владения этапом при редактировании лида) — оба тихие, не проявляются в
обычном использовании UI, но оба бьют ровно по тем вещам, которые проект
явно позиционирует как свои сильные стороны (производительность на слабом
железе и целостность личных досок). Плюс россыпь предупреждений
уровня «не доведено до конца после рефакторинга» (CSP с мёртвыми
разрешениями, default цвета тега, нет guard на SECRET_KEY) — характерно для
проекта, который очень быстро итерировался (19 миграций за 3 дня).

## Топ-10 критичных проблем к немедленному исправлению

1. 🔴 `User.leads` (`lazy="selectin"`) — лишний тяжёлый запрос на каждый
   аутентифицированный HTTP-запрos. Исправление — одна строка (`lazy="raise"`).
2. 🔴 `update_lead` не проверяет, что новый `stage_id` принадлежит доске
   владельца лида — дыра в инварианте персональных досок.
3. 🟡 Нет fail-fast проверки `SECRET_KEY` на дефолтное/слишком короткое
   значение при `ENVIRONMENT=production`.
4. 🟡 CSP содержит неиспользуемые разрешения на `fonts.googleapis.com`/
   `fonts.gstatic.com` — рудимент после отказа от Google Fonts.
5. 🟡 Бюджет соединений с Postgres (`pool_size × overflow × workers`) близок
   к `max_connections=120` без зафиксированной формулы пересчёта.
6. 🟡 У цен/веса в заявке (`customer_price`, `cargo_weight` и т.д.) нет
   валидации на неотрицательность.
7. 🟡 `apiUpload`/`apiBlob` на фронтенде не продлевают сессию при истёкшем
   access-токене, в отличие от обычных запросов через `api()`.
8. 🟡 В CI нет аудита уязвимостей npm-зависимостей (есть только для backend).
9. 🟡 В CI нет проверки, что Docker-образы вообще собираются
   (`docker build`), несмотря на внешнюю APT-зависимость в образе backend.
10. 🟢 `Tag.color` в модели хранит устаревший default `"blue"` вместо HEX,
    хотя вся остальная система тегов уже переведена на HEX-цвета.
