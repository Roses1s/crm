# Мастер-промт для передачи проекта новому агенту

Скопируйте блок ниже целиком и отправьте первым сообщением любому новому агенту.
Промт не зависит ни от того, что менялось в проекте после его написания, ни от
имени ветки: агент сам определит ветку, на которой его запустили, прочитает
документацию и сверит текущее состояние по git.

---

```text
Ты продолжаешь работу над проектом CRM Detroid в репозитории Roses1s/crm.
Я — владелец проекта, не администратор и не программист: объясняй простым
языком, команды давай готовыми для копирования, отвечай по-русски.

Коротко о проекте: CRM для транспортной компании (лиды, канбан-воронка,
заявки на перевозку, перевозчики, активности, отчёты). Продакшен работает на
https://crmdetroid.ru — VPS с Ubuntu 26.04, 2 ГБ памяти, 15 ГБ диска. Стек:
FastAPI + PostgreSQL 18 + Valkey + Celery, React 19 + Vite 6 + Tailwind v4,
всё в Docker Compose из семи контейнеров. Каталог /opt/crm на сервере — это
клон репозитория, обновление одной командой: ssh crm /opt/crm/deploy.sh

ГЛАВНОЕ ПРО ВЕТКУ (читай первым делом):

Рабочая ветка проекта — ТА, НА КОТОРОЙ ТЫ СЕЙЧАС НАХОДИШЬСЯ. Определи её
первой же командой и дальше подставляй её имя всюду вместо <ВЕТКА>:

   git rev-parse --abbrev-ref HEAD

Эта ветка становится единственной основной и рабочей на всю сессию. Имя ветки,
записанное в документации (AGENTS.md, docs/PROJECT.md, docs/STATUS.md,
docs/deploy/02-deploy.md), может быть старым — это нормально: площадка заводит
под каждую новую сессию свою ветку. Если имя не совпадает с текущим:

- НЕ переключайся на ветку из документации и не создавай её;
- работай в текущей ветке;
- в конце сессии замени имя ветки в документации на актуальное
  (простая текстовая замена по всем файлам) и напомни мне одной командой
  переключить клон на сервере:
  ssh crm "cd /opt/crm && git fetch origin <ВЕТКА> && git checkout -B <ВЕТКА> --track origin/<ВЕТКА> && git log --oneline -1"

ПЕРЕД ЛЮБЫМИ ДЕЙСТВИЯМИ выполни четыре шага:

1. Прочитай документацию в таком порядке:
   - AGENTS.md — правила работы, пять самых частых граблей
   - docs/PROJECT.md — полный контекст: архитектура, доменная модель, API,
     эксплуатация, подводные камни (раздел 9), журнал решений (раздел 10)
   - docs/STATUS.md — на каком этапе проект сейчас
   - docs/HANDOVER.md — что делалось прямо перед тобой и не доделано

2. Проверь, не изменилось ли что-то после последней отметки в STATUS.md
   (в нём указан «последний учтённый коммит»):

   git fetch origin <ВЕТКА>
   git log --oneline <хеш_из_STATUS>..FETCH_HEAD
   git diff --stat <хеш_из_STATUS>..FETCH_HEAD
   git status --short

   Если список коммитов пуст — документация актуальна, работай по ней.
   Если нет — прочитай новые коммиты и учти их, документация могла отстать.
   Если хеша из STATUS.md нет в истории (бывает при мелкой копии репозитория) —
   сравни с предыдущим коммитом текущей ветки и скажи мне об этом.

3. Убедись, что рабочая копия совпадает с GitHub. В этой песочнице локальная
   git-история иногда откатывается к первому коммиту, хотя на GitHub всё цело.
   Признак: git log показывает один коммит или git ls-files — два файла.
   Лечится так:

   git fetch origin <ВЕТКА>
   git reset FETCH_HEAD        # индекс и HEAD на удалённое состояние
   git status --short          # пусто = рабочее дерево совпадает с GitHub

   Каталоги .venv и node_modules тоже не переживают перезапуск песочницы —
   при ошибке «модуль не найден» просто пересоздай их:
   cd backend && python -m venv .venv && .venv/bin/pip install -e ".[dev]"
   cd frontend && npm install

4. Напиши мне короткий отчёт (без кода, 5–7 строк):
   - на какой ветке ты работаешь и совпадает ли она с той, что в документации;
   - что сейчас в проекте работает;
   - есть ли незакрытая задача в docs/HANDOVER.md и предлагаешь ли её продолжить;
   - были ли изменения после последней отметки в STATUS.md и какие;
   - что предлагаешь сделать дальше и почему;
   - если видишь риск или незакрытый хвост — назови его.
   И дождись моего ответа, прежде чем менять код.

КАТЕГОРИЧЕСКИЙ ЗАПРЕТ ПО GIT (нарушение = потеря моей работы):

- Работай ТОЛЬКО в текущей ветке <ВЕТКА>. Для тебя она единственная.
- НЕЛЬЗЯ создавать новые ветки: ни git branch, ни git checkout -b,
  ни git switch -c, ни через веб-интерфейс GitHub.
- НЕЛЬЗЯ переключаться на другую ветку (в том числе на ту, что упомянута
  в документации), переименовывать или удалять текущую, менять ветку
  по умолчанию в настройках репозитория.
- НЕЛЬЗЯ пушить куда-либо, кроме origin <ВЕТКА>. В main — никогда.
- НЕЛЬЗЯ переписывать уже отправленную историю: без git push --force,
  --force-with-lease, без rebase и reset --hard по опубликованным коммитам,
  без изменения чужих коммитов.
- НЕЛЬЗЯ удалять удалённые ветки и теги, менять настройки репозитория.
  Старые рабочие ветки не трогай — они остаются страховкой.
- Если задача выглядит так, будто нужна отдельная ветка или pull request, —
  остановись, объясни ситуацию и спроси меня. Сам не решай.
- Разрешено и нормально: git fetch, git log, git diff, git status, git add,
  git commit, git push origin <ВЕТКА>, а также git reset (mixed/soft)
  для восстановления локальной истории по инструкции из шага 3.

ЕСЛИ СЕССИЯ ОБОРВЁТСЯ (у меня закончатся токены, упадёт песочница):

Наш чат следующему агенту недоступен — доступен только репозиторий. Поэтому:

- Коммить часто и мелко, прямо по ходу работы, а не одним куском в конце.
  Закончил осмысленный шаг — сразу commit и push. Обрыв тогда стоит одного
  шага, а не всей сессии.
- Веди docs/HANDOVER.md — записку «что делаю прямо сейчас»: задача, план по
  шагам с отметками, какие файлы трогаешь, наши договорённости из чата, чем
  проверять, какие хвосты. Заводи в начале задачи по шаблону из этого файла,
  обновляй вместе с каждым коммитом. Задача закрыта — итог переносишь
  в docs/STATUS.md, а HANDOVER.md возвращаешь к «Задачи в работе нет».
- Не оставляй репозиторий сломанным: каждый коммит должен проходить проверки
  (ruff, mypy, pytest, tsc -b, npm run build). Незаконченное либо не коммить,
  либо коммить выключенным — чтобы на GitHub всегда лежала рабочая версия.
- Перед большой задачей назови мне план из 3–5 шагов, чтобы каждый шаг стал
  отдельным коммитом и прогресс был виден в истории git.

ПРАВИЛА РАБОТЫ:

- Всё по-русски: комментарии в коде, сообщения об ошибках, коммиты, ответы.
  Комментарии объясняют «почему так», а не пересказывают строку кода.
- Не вносить изменения, которые не можешь проверить. В песочнице нет Docker,
  PostgreSQL, Valkey и прав sudo — проверяй тем, что доступно:
    cd backend && .venv/bin/ruff check . && .venv/bin/mypy app \
      && .venv/bin/python -m pytest
    cd frontend && npx tsc -b && npm run build
  Логику shell-скриптов можно проверять подставными бинарниками в PATH.
- Секреты не коммитить: .env в .gitignore, в примерах — заглушки.
- Наружу публикуется только nginx (порты 80 и 443). Docker обходит UFW,
  поэтому любой ports: у базы сделает её доступной из интернета.
- Миграции Alembic генерируются на SQLite, поэтому сгенерированный файл надо
  править: sa.text("(CURRENT_TIMESTAMP)") → sa.func.now(), а блоки
  with op.batch_alter_table(...) разворачивать в обычные op.create_index /
  op.drop_index. Потом обязательно прогнать upgrade head на пустой базе.
- Мои решения, которые не нужно пересматривать без моего запроса: мониторинг
  с уведомлениями и автоматическую выгрузку бэкапов наружу мы делать не будем
  (я знаю про риск). Вложения храним на томе сервера, не в S3.
- Делать только то, о чём я попросил. Если по пути видишь другую проблему —
  сообщи о ней и спроси, а не чини молча.

В КОНЦЕ КАЖДОЙ СЕССИИ, если что-то менялось:
- обнови docs/STATUS.md: дату, хеш последнего коммита, имя рабочей ветки,
  разделы «Готово» и «В работе»;
- если имя ветки в документации устарело — замени его на актуальное во всех
  файлах и дай мне команду для переключения клона на сервере;
- если наступил на новые грабли — допиши их в раздел 9 docs/PROJECT.md,
  чтобы следующий на них не наступил;
- очисти docs/HANDOVER.md, если задача закрыта, или оставь в нём актуальное
  состояние, если работа продолжается;
- закоммить и запушь в origin <ВЕТКА>.
```

## Почему промт устроен именно так

**Не зависит от имени ветки.** Площадка Arena заводит под каждую сессию свою
рабочую ветку, и пушить в чужую агент не может. Поэтому промт не называет ветку
по имени: агент определяет её командой `git rev-parse --abbrev-ref HEAD`, и
именно она становится основной на всю сессию. Имя в документации при этом
обновляется в конце сессии — так файлы догоняют реальность, а не наоборот.

**Не зависит от давности.** В промте нет списка сделанного — только путь к
документам и процедура сверки. Даже если проект уйдёт вперёд на десятки
коммитов, агент сначала прочитает `STATUS.md`, затем сравнит его отметку с
реальной историей git и сам увидит разницу.

**Не даёт «уплыть» документации.** Ритуал в конце сессии заставляет обновлять
`STATUS.md` и раздел с граблями. Хеш последнего учтённого коммита — якорь,
по которому следующий участник за одну команду видит всё, что произошло после.

**Защищает от повторных ошибок.** Правила про песочницу (пропадающие `.venv`,
откат git-истории), про генерацию миграций на SQLite и про публикацию портов —
это ровно те места, где проект уже спотыкался.

**Бережёт ваше время.** Обязательный короткий отчёт перед работой показывает,
что агент действительно разобрался, а не начал править код наугад.

**Переживает обрыв сессии.** Токены заканчиваются внезапно, и всё, что агент
держал «в голове», пропадает вместе с чатом. Против этого работают три вещи:
частые мелкие коммиты (обрыв стоит одного шага), файл-эстафета
[`HANDOVER.md`](HANDOVER.md) с текущей задачей и договорённостями, и запрет
оставлять репозиторий в нерабочем состоянии.

**Что остаётся на вас.** Один раз за сессию — переключить клон на сервере на
новую ветку командой, которую агент даст в конце. Без этого `deploy.sh` будет
выкатывать старую версию.
