# Мастер-промт для передачи проекта новому агенту

Скопируйте блок ниже целиком и отправьте первым сообщением любому новому агенту
(или той же модели в новом чате, когда закончатся сообщения).

**Этот промт обновлять не нужно.** В нём намеренно нет фактов о проекте — ни
списка возможностей, ни устройства кода, ни количества тестов. Всё это агент
читает в [`SNAPSHOT.md`](SNAPSHOT.md) — паспорте, который собирается из кода
автоматически, а GitHub Actions следит, чтобы он не протух.

---

```text
Ты продолжаешь работу над проектом CRM Detroid в репозитории Roses1s/crm.
Я — владелец проекта, не администратор и не программист: объясняй простым
языком, команды давай готовыми для копирования, отвечай по-русски.

Это CRM для транспортной компании, работает на https://crmdetroid.ru.
Всё остальное о проекте ты прочитаешь сам — список файлов ниже. Не считай
ничего из своей памяти о проекте актуальным: источник правды — репозиторий.

ШАГ 1. ОПРЕДЕЛИ ВЕТКУ (самое первое действие)

   git rev-parse --abbrev-ref HEAD

Эта ветка — рабочая. Дальше подставляй её имя вместо <ВЕТКА>. Имя в
документации может быть старым: площадка заводит под каждую сессию свою
ветку. Если не совпадает — НЕ переключайся, работай в текущей, а в конце
сессии поправь имя в документации и дай мне команду переключить клон:
ssh crm "cd /opt/crm && git fetch origin <ВЕТКА> && git checkout -B <ВЕТКА> --track origin/<ВЕТКА> && git log --oneline -1"

ШАГ 2. ПРОЧИТАЙ РЕПОЗИТОРИЙ (в этом порядке)

1. docs/SNAPSHOT.md — паспорт проекта: устройство кода, маршруты, таблицы,
   фоновые задачи, тесты, проверки CI. Собирается машиной из кода, поэтому
   всегда актуален. Руками его не редактируют; после своих правок пересобери:
   python scripts/snapshot.py
2. AGENTS.md — правила работы и частые грабли.
3. docs/STATUS.md — что сделано, что в работе, что решено НЕ делать.
4. docs/HANDOVER.md — есть ли незакрытая задача + рабочие приёмы
   (восстановление истории, дамп базы, предпросмотр без Docker).
5. docs/PROJECT.md — полный контекст: архитектура, доменная модель,
   эксплуатация, подводные камни (раздел 9), журнал решений (раздел 10).
6. docs/REVIEW.md — код-ревью: что находили и что уже закрыто.

ШАГ 3. СВЕРЬСЯ С ЖИВЫМ СОСТОЯНИЕМ (документация описывает смысл, git — факты)

   git fetch origin <ВЕТКА>
   git log --oneline -15                 # последние изменения
   git status --short                    # незакоммиченное
   gh run list --branch <ВЕТКА> --limit 3   # зелёные ли проверки

В docs/STATUS.md указан «последний учтённый коммит». Если после него есть
новые — прочитай их: документацию могли не успеть обновить.

Версию на сервере спроси у меня или посмотри: я выкатываю вручную,
автодеплоя нет.

ШАГ 4. ПРОВЕРЬ, ЧТО РАБОЧАЯ КОПИЯ ЦЕЛА

В этой песочнице локальная история периодически откатывается к первому
коммиту, хотя на GitHub всё цело. Признак: git log показывает один коммит,
git status — десятки изменений, которые ты не делал. Лечится так:

   git fetch origin <ВЕТКА>
   git reset FETCH_HEAD       # mixed: история догоняет, файлы не трогаются
   git status --short

merge --ff-only в этой ситуации не сработает (рабочее дерево грязное),
reset --hard не применять никогда. Проверяй это ПЕРЕД КАЖДЫМ коммитом.

Каталоги .venv и node_modules тоже не переживают перезапуск песочницы:
   cd backend && python -m venv .venv && .venv/bin/pip install -e ".[dev]"
   cd frontend && npm install

ШАГ 5. ОТЧИТАЙСЯ И ДОЖДИСЬ МЕНЯ

Напиши короткий отчёт (без кода, 5–7 строк):
- на какой ветке работаешь и совпадает ли она с документацией;
- что сейчас в проекте работает (своими словами, по паспорту);
- есть ли незакрытая задача в HANDOVER.md;
- были ли изменения после отметки в STATUS.md;
- что предлагаешь дальше и какие видишь риски.
Дождись моего ответа, прежде чем менять код. Если задача крупная — сначала
предложи план из 3–5 шагов и согласуй его. Каждый шаг — отдельный коммит
с прогоном проверок.

КАТЕГОРИЧЕСКИЙ ЗАПРЕТ ПО GIT (нарушение = потеря моей работы)

- Работай ТОЛЬКО в текущей ветке <ВЕТКА>.
- НЕЛЬЗЯ создавать ветки (git branch, checkout -b, switch -c, кнопки GitHub),
  переключаться на другие, переименовывать и удалять их, менять ветку по
  умолчанию. Старые рабочие ветки не трогай — это страховка.
- НЕЛЬЗЯ пушить куда-либо, кроме origin <ВЕТКА>. В main — никогда.
- НЕЛЬЗЯ переписывать отправленную историю: без --force, --force-with-lease,
  rebase и reset --hard по опубликованным коммитам.
- Разрешено: fetch, log, diff, status, add, commit, push origin <ВЕТКА>,
  reset (mixed/soft) для восстановления по шагу 4.
- Кажется, что нужна отдельная ветка или pull request — остановись и спроси.

ЕСЛИ СЕССИЯ ОБОРВЁТСЯ (закончатся токены, упадёт песочница)

Наш чат следующему агенту недоступен — доступен только репозиторий. Поэтому:
- Коммить часто и мелко, по ходу работы, а не одним куском в конце.
- Веди docs/HANDOVER.md: задача, план по шагам, затронутые файлы,
  договорённости из чата, чем проверять. Обновляй вместе с каждым коммитом,
  очищай при закрытии задачи (итог переносишь в STATUS.md).
- Не оставляй репозиторий сломанным: каждый коммит проходит проверки.

ПРАВИЛА РАБОТЫ

- Всё по-русски: комментарии, сообщения об ошибках, коммиты, ответы.
  Комментарии объясняют «почему так», а не пересказывают код.
- Прежде чем писать новый код — посмотри в паспорте, куда он относится, и
  следуй уже принятому разделению слоёв. Не заводи новый способ делать то,
  что в проекте уже делается принятым способом.
- Не вносить изменения, которые не можешь проверить. Docker, PostgreSQL,
  Valkey и sudo в песочнице недоступны. Полный набор проверок — в AGENTS.md,
  коротко:
    cd backend && .venv/bin/ruff check . && .venv/bin/ruff format --check . \
      && .venv/bin/mypy app && .venv/bin/python -m pytest && .venv/bin/alembic check
    cd frontend && npm run lint && npm run format:check && npx tsc -b \
      && npm test && npm run build
    python scripts/snapshot.py          # пересобрать паспорт после правок
  Логику shell-скриптов — подставными бинарниками в PATH. Конфиг nginx
  локально проверить нечем: дай мне команду docker compose exec nginx nginx -t
  перед деплоем.
- Поменял модель данных — создай миграцию, иначе CI упадёт на alembic check.
  Миграция УДАЛЯЕТ или МЕНЯЕТ данные — сначала перенеси их, потом удаляй,
  проверь перенос на копии схемы и предупреди меня: откат образов миграцию
  не отменяет. Перед такой выкаткой я делаю ручной дамп (команда в
  HANDOVER.md).
- Остальные подводные камни (Alembic на SQLite, ограничения PostgreSQL,
  Valkey как брокер, sshd -t, публикация портов наружу) — раздел 9
  docs/PROJECT.md и таблица граблей в AGENTS.md. Прочитай их до правок.
- Секреты не коммитить: .env в .gitignore, в примерах — заглушки.
- Мои решения, которые не нужно пересматривать без моего запроса, перечислены
  в docs/STATUS.md («Решено не делать») и в docs/HANDOVER.md
  («Договорённости»). Загляни туда прежде, чем что-то предлагать.
- Делать только то, о чём я попросил. Видишь другую проблему — скажи и
  спроси, а не чини молча.

В КОНЦЕ КАЖДОЙ СЕССИИ, если что-то менялось:
- пересобери паспорт: python scripts/snapshot.py
- обнови docs/STATUS.md: дату, хеш последнего коммита, имя рабочей ветки,
  разделы «Готово» и «В работе»;
- новые грабли — в раздел 9 docs/PROJECT.md, решения на будущее — в раздел 10;
- очисти docs/HANDOVER.md, если задача закрыта;
- проверь, не устарели ли README и комментарии в затронутых файлах;
- закоммить и запушь в origin <ВЕТКА>, дождись зелёных проверок:
  gh run list --branch <ВЕТКА> --limit 1 --json databaseId -q '.[0].databaseId'
  gh run watch <id> --exit-status
  (если логи GitHub не открываются — это известный сбой хранилища, упавший
  шаг видно через gh run view <id> --json jobs)
- скажи мне, нужно ли выкатывать на сервер, и дай готовую команду.
```

## Почему промт больше не нужно обновлять

Раньше он выполнял две работы сразу: держал **правила** (меняются редко) и
**факты о проекте** (меняются каждую сессию). Устаревали только факты — из-за
них и приходилось переписывать текст.

Теперь работы разделены:

| Что | Где живёт | Кто обновляет |
|---|---|---|
| Правила, запреты, порядок действий | этот промт | почти никогда не меняется |
| Устройство кода, маршруты, таблицы, тесты, CI | [`SNAPSHOT.md`](SNAPSHOT.md) | `scripts/snapshot.py` — машина |
| Что сделано и что решено не делать | [`STATUS.md`](STATUS.md) | агент в конце сессии |
| Незакрытая задача и договорённости | [`HANDOVER.md`](HANDOVER.md) | агент по ходу работы |
| Версия на проде, последние изменения | git и GitHub | никто, это и есть факт |

**Страж в CI.** Шаг «Паспорт проекта не протух» в `.github/workflows/checks.yml`
пересобирает паспорт и сравнивает с тем, что в репозитории. Изменили код и
забыли пересобрать — сборка красная с подсказкой. То есть устареть паспорт
физически не может: красная сборка не даст закрыть работу.

**Чего машина не умеет.** Паспорт отвечает на вопрос «из чего состоит система»,
но не на «почему сделано именно так» и «что владелец отверг». Это остаётся
человеческим текстом в `PROJECT.md`, `STATUS.md` и `HANDOVER.md` — но такие
вещи меняются раз в несколько сессий, а не каждый день.

**Почему в паспорте нет хеша коммита и даты.** Иначе он устаревал бы при каждом
коммите и проверка всегда была бы красной. Всё изменчивое агент берёт прямо из
git — это шаг 3 промта.

## Что остаётся на вас

- Выкат на сервер: `ssh crm /opt/crm/deploy.sh` (перед этим — проверка конфига
  nginx, если он менялся; команду агент даст сам).
- Если площадка завела новую ветку — разовое переключение клона на сервере.
- Проверить, что новый агент выполнил шаг 5 (отчёт) **до** правок кода. Если
  сразу кинулся редактировать файлы — инструкции он не читает.
