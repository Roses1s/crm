# Мастер-промт для передачи проекта новому агенту

Скопируйте блок ниже целиком и отправьте первым сообщением любому новому агенту
(или той же модели в новом чате, когда закончатся сообщения). Промт не зависит
ни от имени ветки, ни от того, что менялось в проекте после его написания:
агент сам определит ветку, прочитает документацию и сверит состояние по git.

Обновлён 29.09.2026.

---

```text
Ты продолжаешь работу над проектом CRM Detroid в репозитории Roses1s/crm.
Я — владелец проекта, не администратор и не программист: объясняй простым
языком, команды давай готовыми для копирования, отвечай по-русски.

О ПРОЕКТЕ

CRM для транспортной компании. Продакшен: https://crmdetroid.ru — VPS
SpaceWeb, Ubuntu 26.04, 2 ГБ памяти, 15 ГБ диска. Стек: FastAPI +
PostgreSQL 18 + Valkey + Celery, React 19 + Vite 6 + Tailwind v4, всё в
Docker Compose из семи контейнеров. Каталог /opt/crm на сервере — клон
репозитория, обновление одной командой: ssh crm /opt/crm/deploy.sh

Что работает сегодня:
- Вход: JWT, обновляющий токен в куке HttpOnly, короткий токен доступа
  живёт только в памяти вкладки; журнал попыток входа.
- Две роли: администратор и менеджер. Оператора нет, дашборда нет,
  активностей (звонки/встречи/задачи) нет — всё удалено по решению владельца.
- Личные доски: у каждого менеджера своя воронка. При первом входе
  создаётся набор Новый · Перезвонить · Вышел на ЛПР · Потенциальный клиент ·
  Уехали, ждём заявку. Этапы можно переименовывать, двигать, удалять (с
  переносом карточек). Менеджер видит только свои лиды: чужие отдаются как
  404, чтобы нельзя было узнать об их существовании.
- Продавец лида ставится автоматически при создании. Передача коллеге — по
  щелчку на имени: выбор сотрудника, подтверждение, запись в ленте. Карточка
  переезжает на доску получателя, в этап с тем же названием (нет — в первый).
- Канбан: перетаскивание, поиск по названию, ИНН, контакту логиста и его
  телефону. Панели фильтров нет намеренно. Админ набирает фамилию в поиске и
  открывает доску любого сотрудника.
- Заявки на перевозку с документами, перевозчики, вложения к лидам с
  предпросмотром картинок и PDF, лента изменений и примечаний.
- Админка: пользователи (при удалении лиды переходят администратору),
  перевозчики, бэкапы, журнал попыток входа.
- Фоновые задачи: дамп базы в 03:00 (хранение 14 дней), архив вложений и
  чистка осиротевших файлов по воскресеньям.
- Автопроверки GitHub Actions при каждой отправке: ruff, mypy, pytest,
  миграции, tsc, vitest, сборка.

ГЛАВНОЕ ПРО ВЕТКУ (читай первым делом)

Рабочая ветка — ТА, НА КОТОРОЙ ТЫ СЕЙЧАС НАХОДИШЬСЯ. Определи её первой же
командой и дальше подставляй её имя вместо <ВЕТКА>:

   git rev-parse --abbrev-ref HEAD

Имя ветки в документации может быть старым — площадка заводит под каждую
сессию свою. Если не совпадает: НЕ переключайся, работай в текущей, а в конце
сессии замени имя в документации и дай мне команду переключить клон:
ssh crm "cd /opt/crm && git fetch origin <ВЕТКА> && git checkout -B <ВЕТКА> --track origin/<ВЕТКА> && git log --oneline -1"

ПЕРЕД ЛЮБЫМИ ДЕЙСТВИЯМИ выполни пять шагов:

1. Прочитай документацию в таком порядке:
   - AGENTS.md — правила работы и частые грабли
   - docs/PROJECT.md — полный контекст: архитектура, доменная модель, API,
     эксплуатация, подводные камни (раздел 9), журнал решений (раздел 10),
     хранилище файлов и S3 (раздел 10.1)
   - docs/STATUS.md — на каком этапе проект сейчас
   - docs/HANDOVER.md — что делалось прямо перед тобой и не доделано
   - docs/REVIEW.md — код-ревью: что было найдено и что уже закрыто

2. Сверься с GitHub (в STATUS.md указан «последний учтённый коммит»):

   git fetch origin <ВЕТКА>
   git log --oneline <хеш_из_STATUS>..FETCH_HEAD
   git status --short

   Пусто — документация актуальна. Нет — прочитай новые коммиты.

3. Проверь, что рабочая копия совпадает с GitHub. В этой песочнице локальная
   история периодически откатывается к первому коммиту, иногда вместе с
   файлами, хотя на GitHub всё цело. Признак: git log показывает один коммит,
   git status — десятки изменений, которые ты не делал. Лечится так:

   git fetch origin <ВЕТКА>
   git merge --ff-only FETCH_HEAD   # если файлы тоже откатились
   git reset FETCH_HEAD             # если файлы целы, а история отстала
   git status --short

   ВАЖНО: проверяй это перед каждым коммитом. Если сделать коммит на
   откатившейся истории, push уйдёт с ошибкой non-fast-forward — тогда
   git reset FETCH_HEAD и закоммить заново, проверив, что в diff только твои
   файлы.

   Каталоги .venv и node_modules тоже не переживают перезапуск песочницы:
   cd backend && python -m venv .venv && .venv/bin/pip install -e ".[dev]"
   cd frontend && npm install

4. Напиши мне короткий отчёт (без кода, 5–7 строк):
   - на какой ветке работаешь и совпадает ли она с документацией;
   - что сейчас в проекте работает;
   - есть ли незакрытая задача в HANDOVER.md;
   - были ли изменения после отметки в STATUS.md;
   - что предлагаешь дальше и какие видишь риски.
   Дождись моего ответа, прежде чем менять код.

5. Если задача крупная — сначала предложи план из 3–5 шагов и согласуй его.
   Каждый шаг — отдельный коммит с прогоном проверок.

КАТЕГОРИЧЕСКИЙ ЗАПРЕТ ПО GIT (нарушение = потеря моей работы)

- Работай ТОЛЬКО в текущей ветке <ВЕТКА>.
- НЕЛЬЗЯ создавать ветки (git branch, checkout -b, switch -c, кнопки GitHub),
  переключаться на другие, переименовывать и удалять их, менять ветку по
  умолчанию. Старые рабочие ветки не трогай — это страховка.
- НЕЛЬЗЯ пушить куда-либо, кроме origin <ВЕТКА>. В main — никогда.
- НЕЛЬЗЯ переписывать отправленную историю: без --force, --force-with-lease,
  rebase и reset --hard по опубликованным коммитам.
- Разрешено: fetch, log, diff, status, add, commit, push origin <ВЕТКА>,
  reset (mixed/soft) и merge --ff-only для восстановления по шагу 3.
- Кажется, что нужна отдельная ветка или pull request — остановись и спроси.

ЕСЛИ СЕССИЯ ОБОРВЁТСЯ (закончатся токены, упадёт песочница)

Наш чат следующему агенту недоступен — доступен только репозиторий. Поэтому:
- Коммить часто и мелко, по ходу работы, а не одним куском в конце.
- Веди docs/HANDOVER.md: задача, план по шагам, затронутые файлы,
  договорённости из чата, чем проверять. Обновляй вместе с каждым коммитом,
  очищай при закрытии задачи (итог переносишь в STATUS.md).
- Не оставляй репозиторий сломанным: каждый коммит проходит проверки.

ПРАВИЛА РАБОТЫ

- Всё по-русски: комментарии, сообщения об ошибках, коммиты, ответы.
  Комментарии объясняют «почему так», а не пересказывают код.
- Не вносить изменения, которые не можешь проверить. Docker, PostgreSQL,
  Valkey и sudo в песочнице недоступны. Проверяй тем, что есть:
    cd backend && .venv/bin/ruff check . && .venv/bin/ruff format --check . \
      && .venv/bin/mypy app && .venv/bin/python -m pytest
    cd frontend && npx tsc -b && npm test && npm run build
  Логику shell-скриптов — подставными бинарниками в PATH.
- Миграции Alembic генерируются на SQLite, сгенерированный файл надо править:
  sa.text("(CURRENT_TIMESTAMP)") → sa.func.now(); batch_alter_table
  разворачивать в обычные операции, кроме случаев, где SQLite иначе не умеет
  (менять ограничения и удалять колонки). Всегда прогоняй upgrade head,
  downgrade -1, upgrade head на пустой базе.
- Ограничения в PostgreSQL не удаляй по угаданному имени: ищи его в
  pg_constraint. Один такой промах уже ронял деплой.
- Секреты не коммитить: .env в .gitignore, в примерах — заглушки.
- Наружу публикуется только nginx (80/443). Docker обходит UFW, поэтому любой
  ports: у базы сделает её доступной из интернета.
- Перед каждым systemctl restart ssh на сервере — sshd -t. Опечатка в
  настройках выключает доступ, и вернуться можно только через консоль
  хостинга.
- Мои решения, которые не нужно пересматривать без моего запроса: мониторинг
  с уведомлениями, автоматическая выгрузка бэкапов наружу и S3 для вложений —
  не делаем (объёмы крошечные, разбор в разделе 10.1 PROJECT.md); экспорт
  лидов в Excel/CSV и дашборд по активностям — не нужны.
- Делать только то, о чём я попросил. Видишь другую проблему — скажи и
  спроси, а не чини молча.

В КОНЦЕ КАЖДОЙ СЕССИИ, если что-то менялось:
- обнови docs/STATUS.md: дату, хеш последнего коммита, имя рабочей ветки,
  разделы «Готово» и «В работе»;
- новые грабли — в раздел 9 docs/PROJECT.md;
- решения, которые повлияют на будущее, — в раздел 10;
- очисти docs/HANDOVER.md, если задача закрыта;
- проверь, не устарели ли README и комментарии в затронутых файлах;
- закоммить и запушь в origin <ВЕТКА>, дождись зелёных проверок GitHub
  (gh run list --limit 1) и скажи мне, нужно ли выкатывать на сервер.
```

## Почему промт устроен именно так

**Не зависит от имени ветки.** Площадка заводит под каждую сессию свою рабочую
ветку. Агент определяет её командой `git rev-parse --abbrev-ref HEAD`, и именно
она становится основной; имя в документации догоняет реальность в конце сессии.

**Не зависит от давности.** Список возможностей в промте — это слепок «что есть
сейчас», но проверяется он всегда по документации и git. Даже если проект уйдёт
вперёд, агент прочитает `STATUS.md`, сравнит отметку с историей и увидит разницу.

**Переживает обрыв сессии.** Частые мелкие коммиты, файл-эстафета
[`HANDOVER.md`](HANDOVER.md) и запрет оставлять репозиторий в нерабочем
состоянии: чат пропадает, репозиторий остаётся.

**Защищает от повторных ошибок.** Правила про откат истории в песочнице,
удаление ограничений в PostgreSQL по имени, проверку `sshd -t` и генерацию
миграций на SQLite — это ровно те места, где проект уже спотыкался и терял время.

**Бережёт ваше время.** Обязательный отчёт перед работой и план из нескольких
шагов для крупных задач показывают, что агент действительно разобрался.

**Что остаётся на вас.** Выкат на сервер (`ssh crm /opt/crm/deploy.sh`) и, если
сменилась ветка, разовое переключение клона — команду агент даст сам.
