## 2. Быстрый старт (локально, без Docker)

```bash
# бэкенд на SQLite — Postgres не нужен
cd backend
python -m venv .venv && .venv/bin/pip install -e ".[dev]"
export DATABASE_URL="sqlite+aiosqlite:///./crm.db"
.venv/bin/alembic upgrade head
.venv/bin/python -m app.cli createsuperuser --email admin@crmdetroid.ru --password DemoPass12345
.venv/bin/python -m app.cli seed          # этапы, теги, демо-лиды
.venv/bin/uvicorn app.main:app --reload   # http://localhost:8000/docs

# фронтенд (в другом терминале)
cd frontend && npm install && npm run dev  # http://localhost:5173
```

Vite проксирует `/api` на `http://127.0.0.1:8000` (`VITE_API_TARGET` переопределяет).
В продакшене прокси не нужен: nginx отдаёт фронтенд и `/api/` с одного домена.

Проверки перед коммитом:

```bash
cd backend && .venv/bin/ruff check . && .venv/bin/ruff format --check . \
```

## 3. Архитектура

```
                    интернет
                       │ 80/443
             ┌─────────▼──────────┐
             │   crm-nginx 1.30   │  сеть edge
             │  TLS, редиректы    │
             └───┬────────────┬───┘
        /api/    │            │  /
        crm_proxy│            │ edge
      ┌──────────▼───┐   ┌────▼───────────┐
      │ crm-backend  │   │ crm-frontend   │
      │ Gunicorn+    │   │ nginx + статика│
      │ UvicornWorker│   └────────────────┘
      └───┬──────────┘
          │ сеть internal (порты не опубликованы)
    ┌─────┴─────┬──────────────┬───────────────┐
┌───▼────────┐ ┌▼───────────┐ ┌▼───────────┐ ┌─▼──────────┐
│crm-postgres│ │ crm-valkey │ │ crm-worker │ │  crm-beat  │
│    18      │ │     8      │ │  Celery    │ │ расписание │
└────────────┘ └────────────┘ └────────────┘ └────────────┘
```

**Семь контейнеров, наружу опубликован только nginx (80/443).** Это принципиально:
Docker пишет правила в обход UFW, поэтому любой `ports:` у базы сделал бы её
публичной. Postgres и Valkey не имеют published ports и недоступны из интернета.
Сеть `internal` настроена с `internal: true`: PostgreSQL, Valkey, worker и beat
не имеют выхода в интернет. Backend соединён с PostgreSQL/Valkey через `internal`,
а с nginx — только через выделенную `crm_proxy` (nginx имеет статический IP
`172.31.250.2`, backend — `172.31.250.3`). Другие контейнеры в `crm_proxy` не
подключены. Разные закреплённые адреса не позволяют порядку запуска контейнеров
создать конфликт. В Nginx входной `X-Forwarded-For` заменяется на `$remote_addr`,
а Gunicorn принимает его только от точного IP nginx. Хост с доступом к Docker
по-прежнему может обращаться к контейнерам; из интернета опубликован только nginx.

Тома: `pgdata` (база), `valkeydata`, `backups` (дампы), `attachments` (файлы лидов).

| Компонент | Версия |
|---|---|
| Python | 3.13 (в образе), код совместим с 3.11 |
| FastAPI / SQLAlchemy / Pydantic | 0.115+ / 2.0+ (async) / 2.10+ |
| PostgreSQL / Valkey | 18 / 8 |
| Celery | 5.5+, брокер Valkey (`redis://valkey:6379/1`) |
| React / Vite / Tailwind | 19 / 6 / **4** |
| Nginx | 1.30 (контейнером, не из apt; образ закреплён по digest) |

## 4. Доменная модель

Десять таблиц (`backend/app/models/`):

| Таблица | Смысл | Важные детали |
|---|---|---|
| `users` | сотрудники | роли `admin` / `manager` (администратор и менеджер) |
| `stages` | колонки канбана | своя доска у каждого сотрудника (`owner_id`); `sequence` — порядок, `color` |
| `tags` | свободные метки | общий справочник: любой сотрудник создаёт/красит (любой HEX)/переименовывает/удаляет; имя уникально без учёта регистра (01.10.2026, было — фиксированная палитра и права manager+) |
| `leads` | потенциальные клиенты | ИНН с контрольной суммой, `priority` 0–3, `is_archived`; nullable `accountant_name` отдельно от продавца `assigned_to_id` |
| `lead_tags` / `shipment_tags` | связь лид/заявка ↔ тег | две отдельные many-to-many таблицы — тег один общий справочник, но проставляется независимо на обеих сущностях |
| `timeline_entries` | лента чаттера | примечания и история изменений полей |
| `attachments` | файлы | на диске в томе, в базе только карточка; `shipment_id` — документ заявки |
| `shipments` | заявки на перевозку | статус, маршрут, груз; перевозчик — просто текстовые поля `carrier_name`/`carrier_inn`/`carrier_contact` прямо в заявке, без отдельного справочника и без проверки на пересечение с другими записями (02.10.2026, было — отдельная таблица `carriers` с админской вкладкой) |
| `login_attempts` | журнал входов | для раздела «Безопасность» |

**Бизнес-правила, зашитые в код:**

- **ИНН** — 10 или 12 цифр **с проверкой контрольной суммы ФНС**
  (`backend/app/schemas/crm.py::_inn_checksum_ok`). Придуманные «красивые» номера
  вроде `7451234567` её не проходят — в тестах и демо-данных используйте
  пересчитанные значения.
- **Назначенный бухгалтер** (`accountant_name`) — nullable-строка из фиксированного
  списка в полной карточке. Это отдельное поле, не связь с CRM-пользователем и
  не продавец (`assigned_to_id`); старые лиды остаются без выбора.
- **При создании лида этап должен принадлежать доске итогового ответственного**.
  Менеджер всегда назначает лид себе, администратор может выбрать сотрудника;
  в обоих случаях `stage_id` сверяется с `stages.owner_id` этого сотрудника.
  Иначе карточка могла бы сохраниться, но исчезнуть из канбана.
- **Проигранная карточка и её лента доступны только для чтения до восстановления** —
  в том числе прежнему ответственному и администратору. Изменение полей,
  примечаний и вложений самого лида отвечает 409 `lead_lost`. Восстановление и
  передача — отдельные разрешённые действия; только после восстановления
  карточка снова редактируется.
- **PATCH карточки лида проверяет версию `updated_at`**: клиент передаёт
  `expected_updated_at`, которую получил при чтении. Если кто-то уже сохранил
  карточку, ответ — 409 `lead_conflict`; поля не меняются, интерфейс предлагает
  загрузить свежую карточку. Проверка и смена версии выполняются атомарно.
- **Смена этапа лида** автоматически пишет запись в `timeline_entries`
  (`field_label="Этапы лидов"`), поэтому история движения видна в чаттере.
- **Системная history неизменяема**: API и интерфейс разрешают edit/delete
  только пользовательским notes. Статус заявки меняется только через
  `PATCH /shipments/{id}/status`, который пишет history; общий PATCH поле
  `status` отвергает.
- **Заявка переносится целиком**: целевой лид проходит строгую проверку прав, а
  `shipments`, `timeline_entries` и `attachments` меняют `lead_id` одной
  транзакцией. Составные внешние ключи `(shipment_id, lead_id)` не позволяют
  снова рассинхронизировать дочерние данные.
- **Номер заявки уникален**: ограничение `uq_shipments_number` обеспечивает это
  в базе, а создание или изменение занятого номера отвечает 409
  `shipment_number_conflict`. Если номер не указан, сервис берёт ID заявки;
  при совпадении добавляет суффикс. Миграция `a7c9e2d4f681` сначала проверяет
  повторы и останавливается без изменения номеров и схемы, если они найдены.
- **Удаление лида** = архивация (`is_archived=True`), физически ничего не удаляется.
- **`activity_state` лида** (`overdue` / `today` / `planned` / `null`) вычисляется
  из ближайшего незакрытого действия и отдаётся **вместе с лидом** — на нём
  строятся цветные часики на канбане. Связь грузится `selectin`: один
  дополнительный запрос на страницу, а не по запросу на карточку.

## 5. API

Префикс `/api/v1`. Документация `/docs` доступна только когда `ENVIRONMENT != production`.

**Соглашения:**

- **Авторизация** — JWT в заголовке `Authorization: Bearer <access>`.
  `access` живёт 30 минут, `refresh` — 14 дней (`POST /auth/refresh`).
- **Роли** проверяются зависимостью `AdminUser` из
  `app/api/deps.py` — права видно прямо в сигнатуре обработчика.
- **Списки** отдаются как `{count, next, previous, results}` — формат выбран
  так, чтобы фронтенд читал одинаково все ручки.
- **Ошибки** всегда `{detail, code, request_id}`; у 422 добавляется `errors[]`.
  Обработчики в `app/core/errors.py`.
- **Каждый ответ** несёт `X-Request-ID`, он же попадает в структурные логи.

**Карта маршрутов:**

## 6. Фронтенд

Маршруты (`frontend/src/app/router.tsx`) повторяют исходный проект-образец
**один в один**: `/login`, `/` (лаунчер), `/crm` (канбан + список),
`/crm/leads/:id`, `/shipments`, `/shipments/:id`, `/admin` (+ `users`,
`security`), `*` → редирект на `/`.

**Организация по фичам:** `features/auth`, `features/launcher`, `features/crm`
(+ `board`, `list`, `lead-form`), `features/shipments`, `features/admin`,
общее — в `shared/{api,ui,lib,types}`.

**Работа с данными.** Компоненты не знают про `fetch` и адреса — только про хуки
из `shared/api/hooks.ts`. Этот файл — публичный barrel; реализации разнесены
по модулям в `shared/api/hooks/` по областям. Ключи кеша собраны в объекте
`keys`; мутации обновляют списки CRM и клиентов, подсказки по ИНН, листалку и
связанные заявки. На logout и перед новой авторизацией Query/Mutation cache
синхронно отменяется и очищается; также отменяется очередь загрузки вложений и
очищается кеш blob-ссылок. Поэтому данные и файлы сотрудника не переживают
смену сессии, а поколение сессии блокирует запоздалый refresh.
`shared/api/client.ts` подставляет токен, проверяет JSON Zod-схемами, разбирает
единый формат ошибок и при 401 завершает сессию и уводит на `/login`.

**Переходы из форм.** Приложение использует React Router Data Router, чтобы
карточки лида и заявки могли удержать внутренний переход до решения пользователя.
Есть три действия: сохранить и перейти, уйти без сохранения или остаться; при
закрытии вкладки браузер показывает отдельное предупреждение. Новые записи тоже
считаются изменёнными после ввода любого поля, даже если обязательный номер или
название ещё не заполнены.

**Дизайн-система.** Перенесена из референсного проекта (Odoo-подобный интерфейс)
и переведена на Tailwind v4:

- все токены — в `src/index.css`: `@theme inline` даёт имена утилит
  (`bg-odoo-surface`, `text-odoo-text-muted`), значения лежат в `:root` и `.dark`;
- тёмная тема — класс `.dark` на `<html>`, объявлена через
  `@custom-variant dark (&:where(.dark, .dark *))`; `public/theme.js` применяет
  её до первой отрисовки, иначе тёмный пользователь видит белую вспышку;
- шрифт — системный стек, как в Odoo (на Windows Segoe UI); собственный шрифт не
  подгружаем, чтобы на одной ОС совпадать с образцом; базовый размер 13px.

**Состояние интерфейса в адресной строке.** Фильтры канбана, режим (канбан/список),
группировка и фильтр заявок живут в query-параметрах: ссылкой на отфильтрованную
доску можно поделиться, и она переживает перезагрузку.

## 7. Эксплуатация

**Обновление продакшена — одна команда:**

```bash
ssh crm /opt/crm/deploy.sh      # или deploy-crm, если настроена функция PowerShell
```

`deploy.sh` (в корне репозитория): блокировка от параллельного запуска, проверка
чистоты каталога, `git pull --ff-only`, проверка свободного места с запасом 2 ГБ,
пометка образов `:previous`, сборка, свежий проверяемый `crm-pre-deploy-*.dump`,
остановка пишущих процессов, отдельный migration step новым backend-образом,
`up -d`, ожидание `healthy` до 180 с и внешняя проверка
`https://crmdetroid.ru/health`. Флаги: `--status`, `--no-build`, `--skip-pull`,
`--rollback`, `--help`. Журнал: `/opt/crm/.deploy.log`.

**Миграции** не запускаются обычным стартом/restart контейнера. После изменения
схемы автоматический и ручной rollback сравнивают ревизию БД с Alembic head
предыдущего backend-образа и отказываются запускать старый код при различии.
Если схема не менялась, прежние образы можно вернуть автоматически.

**Автозапуск** — systemd-юнит `crm.service` (`deploy/systemd/crm.service`),
он надёжнее, чем `restart: unless-stopped` (см. подводные камни).

**Сертификат** — Let's Encrypt, certbot **на хосте** в режиме `--webroot`
(`/opt/crm/certbot/www`), `/etc/letsencrypt` монтируется в nginx только на чтение.
Автопродление — штатный `certbot.timer` + deploy-hook
`/etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh`, который шлёт контейнеру

## 8. Соглашения разработки

**Язык.** Русский везде: комментарии, docstring'и, сообщения ошибок, коммиты,
документация. Комментарии объясняют **почему**, а не что делает строка.

**Бэкенд:** ruff (line-length 100, правила `E,F,I,B,UP,SIM,C4,RUF`; `RUF001-003`
отключены — проект на кириллице), mypy `strict`, pytest с `asyncio_mode=auto`.

**Фронтенд:** TypeScript strict + `noUnusedLocals`, сборка `tsc -b && vite build`.

**Обычные тесты бэкенда** идут на SQLite в памяти — Postgres и Valkey не
нужны. Схема создаётся из моделей (`Base.metadata.create_all`), миграции
проверяются отдельно. В CI дополнительный набор гоняет параллельные запросы
на PostgreSQL и интеграции с настоящими Valkey/Celery; его запускает только
отдельный шаг, не обычный `pytest`.

**Миграции Alembic.** Автогенерация выполняется на SQLite (Postgres в песочнице
нет), поэтому **сгенерированный файл всегда нужно причесать**:

1. `sa.text("(CURRENT_TIMESTAMP)")` → `sa.func.now()` (иначе в Postgres будет
   несовпадение server_default, а `CURRENT_TIMESTAMP` в тексте ломает SQLite);
2. блоки `with op.batch_alter_table(...)` (обходной приём для SQLite) развернуть
   в обычные `op.create_index(..., "таблица", ...)` / `op.drop_index(..., table_name=...)`.

После правки обязательно прогнать `alembic upgrade head` на пустой базе.

**Коммиты** — осмысленные, по-русски, одно изменение = один коммит. Коммитить
и пушить **по ходу работы**, после каждого завершённого шага: сессия агента
может оборваться в любой момент (кончились токены, упала песочница), и всё
незакоммиченное пропадает. Каждый коммит должен проходить проверки — на GitHub
всегда лежит версия, готовая к выкатке.

**Файл-эстафета [`HANDOVER.md`](HANDOVER.md).** Пока задача в работе, в нём
живёт её состояние: план по шагам, затронутые файлы, договорённости из чата,
чем проверять. Чат следующему участнику недоступен — репозиторий доступен.
Задача закрыта — итог переезжает в [`STATUS.md`](STATUS.md), записка
очищается.

**Ветка — жёсткое ограничение.** В этой сессии рабочая ветка
`arena/de9052a9-crm` (предыдущая сессия шла в `arena/6d4bde73-crm`, до неё —
в `arena/2749a700-crm`, `arena/01a0fe2c-crm`, `arena/01a0fd83-crm` и
`arena/01a0f5c2-crm`; площадка Arena привязывает каждую сессию агента к своей
ветке, поэтому пушить в старую из новой сессии нельзя). Текущая ветка началась
с коммита `f1d31ae`; старые ветки остаются в репозитории как страховка и не
трогаются.

Общее правило, чтобы это не повторялось: **рабочая ветка — та, на которой
запущена сессия**. Первой командой агент выполняет
`git rev-parse --abbrev-ref HEAD`, работает в этой ветке, а если имя не
совпадает с записанным в документации — в конце сессии заменяет имя во всех
файлах и даёт владельцу команду переключить клон `/opt/crm` на сервере. Запрещено: создавать новые ветки любым способом,
переключаться на другие, переименовывать или удалять текущую, менять ветку по
умолчанию, пушить в `main`, переписывать отправленную историю (`--force`,
`rebase`, `reset --hard` по опубликованным коммитам), удалять удалённые ветки
и теги. Если задача выглядит так, будто нужна отдельная ветка или pull
request — сначала спросить владельца.

Разрешённый набор: `fetch`, `log`, `diff`, `status`, `add`, `commit`,
`push origin arena/de9052a9-crm`, а также `reset` (mixed/soft) для
восстановления локальной истории — см. раздел 9, блок про песочницу.

| Проигранную карточку меняет прежний ответственный | Проверка видимости не запрещала владельцу менять проигранный лид; в интерфейсе форма тоже оставалась активной | Для изменений карточки используется `get_editable_lead`: ответ 409 `lead_lost` до восстановления; интерфейс блокирует поля, записи ленты и вложения |
| Позднее сохранение стирает правки другого сотрудника | Форма, канбан и быстрый приоритет отправляли PATCH без версии карточки | Каждый PATCH передаёт `expected_updated_at`; условное обновление версии срабатывает только один раз, устаревший запрос получает 409 `lead_conflict` и не меняет поля |
| Теги с одинаковым названием появляются в разном регистре | `POST` проверял имя, но `PATCH` — нет; параллельные запросы могли пройти проверку одновременно | Сравнивать имена через Python `casefold()`, при переименовании проверять другое имя и сериализовать создание/переименование advisory-блокировкой PostgreSQL |
| Одновременное понижение или удаление двух последних администраторов оставляет систему без админа | Два запроса без блокировки успевают посчитать друг друга и оба пройти проверку | Транзакционная PostgreSQL advisory-блокировка удерживается от свежего подсчёта до коммита изменения/удаления; создание доски при переносе лидов не коммитит эту транзакцию раньше времени |
| Входной `X-Forwarded-For` подменяет IP клиента в лимите входа и журнале аудита | Gunicorn доверял любому адресу, а Nginx добавлял присланный клиентом заголовок к своей цепочке | Выделенная сеть `crm_proxy` содержит только backend и nginx; Gunicorn доверяет точному статическому IP nginx, а Nginx полностью заменяет `X-Forwarded-For` на `$remote_addr` |
| Поиск «50%» возвращает всё подряд | `%` и `_` — служебные символы LIKE | Шаблон собирает `app/services/search.py` с экранированием и `escape=` |
| Воркер Celery падает при старте | В задачах синхронный движок SQLAlchemy, а стоит только `asyncpg` (асинхронный) | `psycopg[binary]`, отдельный `settings.sync_dsn`; движок создавать **лениво** |
| `pg_dump` получает DSN с `+asyncpg` | Один DSN на все случаи | Три свойства в настройках: `sqlalchemy_dsn` (async), `sync_dsn` (psycopg), `plain_dsn` (для pg_dump/psql) |
| Ответ 422 падает с `Object of type ValueError is not JSON serializable` | В `exc.errors()` лежат объекты исключений (`ctx`) | Приводить ошибки к `{loc, msg, type}` вручную |
| После PATCH в ответе старые данные | SQLAlchemy отдаёт объект из identity map | `.execution_options(populate_existing=True)` в запросе после мутации |
| `MissingGreenlet` при присваивании `lead.tags` | Присваивание коллекции после `flush()` тянет старое значение из БД синхронно | Задавать связь **до** `add()/flush()`, либо на уже загруженном (`selectinload`) объекте |
| `passlib` падает с `AttributeError: module 'bcrypt' has no attribute '__about__'` | bcrypt 5.0 несовместим с passlib 1.7.4 | Пин `bcrypt>=4.0,<5` |
| Конфликт зависимостей при установке | extra `fastapi-cache2[redis]` требует `redis<5` | Ставить `fastapi-cache2` без extra + `redis>=5.2`; плюс нужен `jinja2` |
| В тестах `You must call init first!` | lifespan приложения в тестах не выполняется, кеш не инициализирован | Инициализировать `FastAPICache` фикстурой (autouse) |
| Тестовый прогон засорён предупреждениями Starlette, PyJWT, httpx и SQLAlchemy (Т-07) | Устаревшие коды статусов, слишком короткий тестовый ключ, cookie в каждом запросе и `noload()` | Использовать актуальные коды, тестовый ключ от 32 байт, cookie jar клиента и явную загрузку нужных связей с `raiseload()` для неиспользуемых |

| Передача лида другому продавцу обязана менять и этап | Этапы личные: с чужим `stage_id` карточка не попала бы ни в одну колонку новой доски и пропала бы из интерфейса | Отдельная операция `POST /crm/leads/{id}/transfer` + `board_stage_for()`; менять продавца обычным сохранением формы нельзя — поле убрано из `LeadUpdate` |

| Поля лида (КПП, часовой пояс, лимит, даты звонков, email и телефон компании) удалены | Владелец не заполнял их 29.09.2026; вместе с ними удалена задача напоминаний о звонках, работавшая по `next_call_date` | Прятать поля в интерфейсе, оставив колонки (отклонено — база копила мусор) |
| Листая карточки под администратором, переключатель «N / M» перескакивал на лида другого менеджера (баг, 01.10.2026) | `visible_only()` для администратора не фильтрует по `assigned_to_id` — это осознанно (админ должен видеть все лиды в списке), но `lead_pager` использовал тот же запрос как диапазон для «соседней карточки», поэтому сосед мог оказаться с чужой доски | `lead_pager` дополнительно сужает диапазон до `assigned_to_id` открытого лида — для менеджера не меняет ничего (он и так видит только своё), для админа ограничивает листание той доской, с которой он зашёл |

### Фронтенд

| Симптом | Причина | Решение |
|---|---|---|
| Предупреждения React `act(...)` и «Not implemented: navigation» в тестах | Асинхронный хук завершался после действия теста; jsdom не выполняет переход на другой документ | Проверять async-мутацию внутри `act`, а `window.location.assign` подменять в тесте и проверять вызов |
| Позднее сохранение формы перетирает правку коллеги, а канбан отправляет устаревший этап/приоритет | Несколько экранов меняют одну карточку отдельными PATCH | Передавать `expected_updated_at`; при 409 `lead_conflict` блокировать старую форму, предложить загрузить свежую карточку и обновлять доску после конфликта |
| После ошибки сохранения браузер шлёт один и тот же запрос каждые 3 секунды | Автосохранение перезапускалось из-за флага «идёт сохранение» в зависимостях эффекта, а форма оставалась «грязной» | Флаг `autoSaveBlocked`: после ошибки автосохранение ждёт правки руками или кнопки «Сохранить» |
| Людей выбрасывает на страницу входа при нескольких вкладках | Сервер отзывает прежний токен при продлении, а вкладки продлевали сессию одновременно | Один общий «полёт» `refreshSession` на вкладку; серверное окно снисхождения 15 секунд и PostgreSQL advisory-блокировка по `jti` сериализуют запросы из разных вкладок |
| Утилиты Tailwind выглядят не так, как в исходнике | v4 переименовал шкалу: v3 `shadow-sm`→v4 `shadow-xs`, v3 `rounded`→v4 `rounded-sm` | Использовать `shadow-xs` и явные `rounded-[4px]` |
| Тема не переключается | В v4 нет `darkMode: "class"` | `@custom-variant dark (&:where(.dark, .dark *))` + значения в `:root`/`.dark`, имена — через `@theme inline` |
| Поля формы пустые после загрузки данных | `defaultValue` не обновляется после прихода ответа | Либо контролируемые поля, либо `key={id}` на контейнере для пересоздания |
| Сохранённый логин на экране входа почти не виден: голубая заливка, светлые буквы | При тёмной теме браузера `:-webkit-autofill` красится по-своему | `color-scheme: light` на контейнере экрана + `-webkit-text-fill-color` и `box-shadow: 0 0 0 1000px #fff inset` для автозаполнения (см. `.login-screen` в `index.css`) |
| Карточка прыгает в начало колонки после переноса | Сервер сортирует лиды по `updated_at`, и перенос обновляет это время | На канбане сортировать колонку по `id` (порядок не зависит от правок), сортировку по свежести оставить списку |
| При масштабе браузера меньше 100% карточка лида оставляет широкие поля по бокам | Пиксельные пределы ширины у пары «форма + лента» и у фона формы не дают занять всё окно | Не ограничивать эту рабочую область в пикселях; чаттер задавать долей рабочей области |
| На широком мониторе чаттер заметно уже образца Odoo | Постоянные 420px занимают лишь около 22% экрана 1920px | На `lg` задавать чаттеру `34.3%`, карточке остаётся примерно `65.7%`; ниже `lg` чаттер уходит под форму |
| Многострочное примечание показывается одной строкой | HTML по умолчанию склеивает переводы строк в обычном тексте | Для обычного текста примечаний применять `whitespace-pre-wrap`; HTML не принимать и не хранить, чтобы не создать XSS |
| Большое примечание прокручивается внутри поля, а не расширяет его | У `textarea` задана начальная высота, но браузер сам не меняет её по содержимому | В `useLayoutEffect` сбрасывать высоту в `auto`, затем задавать `scrollHeight`; отключить `resize` и `overflow`, чтобы после удаления текста поле тоже уменьшалось |
| Данные всё равно перечитываются, хотя у запроса задан большой `staleTime` | У TanStack Query есть второй срок — `gcTime` (по умолчанию 5 минут): пока экран закрыт, запись успевает удалиться из кеша, и при возврате запрос уходит заново | Для справочников задавать оба срока: `staleTime` (сколько верим данным) и `gcTime` ≥ его (сколько храним) |
| Чаттер скачивал оригинал изображения целиком, а миниатюры нельзя было показывать напрямую из-за токена | До запроса миниатюры сервер проверяет доступ к исходному вложению; кеш должен переживать просмотр, но не смешивать уменьшенную и полноразмерную версии | Защищённая ручка `/crm/attachments/{id}/thumbnail` создаёт рядом `.thumbnail.webp` до 480 px с лимитом размера изображения; чаттер грузит её лениво через отдельный ключ кеша. Просмотр и скачивание остаются на ручке оригинала. Уборка сохраняет миниатюру живого оригинала, архив файлов включает обе версии; blob-кеш ограничен 12 записями/48 МБ и очищается на границе сессии |
| Переход с формы теряет ещё не сохранённые правки | Обычный `BrowserRouter` не умеет удерживать внутренний переход, а автосохранение может ещё выполняться | React Router Data Router + `useBlocker`: сохранить и продолжить, уйти без сохранения или остаться; `beforeunload` предупреждает при закрытии вкладки |
| После создания лида список клиентов или подсказка по ИНН показывает старое | Инвалидировался список CRM, но не все потребители одной записи и не связанные заявки после удаления | Общие помощники инвалидируют списки лидов/клиентов, поиск по ИНН и пейджер; удаление убирает детали лида из кеша и обновляет связанные заявки |
| Надпись вылезает за края кнопки, когда та меняет текст | У кнопки «Лог» в чаттере была жёсткая ширина под три буквы, а на время отправки текст становился «Сохранение…» | Кнопке с меняющимся текстом задавать `min-w-[…]` и `whitespace-nowrap`, а не постоянную ширину |
| Бросок карточки не срабатывает у заголовка колонки | `useDroppable` стоял только на списке карточек | Зона приёма — вся колонка; определение цели через `pointerWithin` с запасным `closestCorners` |
| Тест не находит сумму денег, хотя она видна на экране | `toLocaleString("ru-RU")` ставит между разрядами неразрывный пробел U+00A0; testing-library сворачивает пробелы в тексте элемента, но искомую строку сравнивает буквально | В ожиданиях теста заменять U+00A0 обычным пробелом — см. helper `formatMoney` в `shipments-flow.test.tsx` |
| Клик по «…» в ленте этапов «ничего не делает» | Выпадающий список жил внутри полосы с `overflow-x-auto` — такая полоса режет и по вертикали, и меню обрезалось; jsdom разметку не считает, тест этого не видел | Меню выносить за прокручиваемую полосу; тест проверяет, что меню не внутри контейнера с прокруткой |

### Окружение разработки (песочница Arena)

- **Нет Docker, Postgres, Valkey и прав `sudo`.** Проверять можно только тем, что
  работает локально: pytest на SQLite, `tsc`, `vite build`, запуск uvicorn с
  `DATABASE_URL=sqlite+aiosqlite:...`.
- **`.venv` и `node_modules` не переживают перезапуск песочницы** — при «модуль
  не найден» просто пересоздайте их.
- **npm 10.9.8 может упасть при крупном обновлении Vitest** с внутренней ошибкой
  `Cannot read properties of null (reading 'edgesOut')`. Это сбой Arborist, а
  не конфликт проекта: одноразово выполнить команду обновления через
  `npx --yes npm@12.2.0 ...`, затем обязательно проверить обычным `npm ci`.
- **GitHub показывает не все однотипные предупреждения ESLint**: в этой сессии
  одиннадцатое предупреждение Fast Refresh не попало в аннотации. Источник
  правды — полный локальный вывод `npm run lint`, он должен быть без warnings.
- **Локальная git-история может откатиться** к базовому коммиту, хотя на GitHub
  всё на месте. Признак: `git log` показывает один коммит, а `git status` —
  десятки чужих изменений. Лечится так (ветка подставляется сама, чтобы
  команда не протухала вместе с именем ветки):
  ```bash
  git fetch origin "$(git rev-parse --abbrev-ref HEAD)"
  git reset FETCH_HEAD          # индекс и HEAD на удалённое состояние, файлы не трогаются
  git status --short            # пусто = рабочее дерево совпадает с GitHub
  ```
  Если рабочее дерево содержит новую работу — `git reset --soft FETCH_HEAD`,
  затем обычный коммит поверх.
- **Клон песочницы может оказаться «обрезанным» (shallow).** Тогда `git log`
  тоже показывает один коммит, но `git status` чист и `git reset FETCH_HEAD`
  не помогает. Проверка: `git rev-list --count HEAD` и наличие файла
  `.git/shallow`. Лечится полным забором истории текущей ветки:
  `git fetch --unshallow origin "$(git rev-parse --abbrev-ref HEAD)"`.
  Команда ничего не переписывает — только докачивает недостающие коммиты.
  Нюанс: если ветка сессии в GitHub ещё не создана (первый пуш впереди),
  забирать историю нужно из ветки, от которой сессия отпочковалась.
- **`alembic check` в песочнице падает на DNS, даже когда схема в порядке.**
  Без переменной `DATABASE_URL` команда берёт адрес PostgreSQL из настроек
  (`postgres:5432`) и не может его разрешить — в выводе `socket.gaierror:
  [Errno -2] Name or service not known`, а не настоящая проблема со схемой.
  CI подставляет SQLite; локально нужно повторить то же:
  ```bash
  cd backend && rm -f /tmp/checks.db \
    && DATABASE_URL=sqlite+aiosqlite:////tmp/checks.db .venv/bin/alembic upgrade head \
    && DATABASE_URL=sqlite+aiosqlite:////tmp/checks.db .venv/bin/alembic check
  ```
  «No new upgrade operations detected.» — это успех. Проверять `server_default`
  на настоящем PostgreSQL умеет только второй CI-набор.
- **CI может покраснеть на шаге «Аудит зависимостей на уязвимости» без
  изменений в коде**: база уязвимостей npm обновляется на стороне GitHub
  ежедневно. Лечится `npm audit fix` (обновляет lock-файл точечно), полным
  прогоном проверок фронтенда и отдельным коммитом. Случилось 06.10.2026 с
  `source-map-js` (GHSA-68fv-2mgg-jv7q), закрыто патчем 1.2.2.
- **Ruff (isort) требует `import ... as ...` отдельным блоком** от обычного
  импорта того же модуля: `from x import y as z` + `from x import a` — это ДВА
  оператора, «слитый» вариант он сам и разбивает. Не бороться, просто принять
  `ruff check --fix`.
- **В тестах jsdom селекты ищем по содержимому опций, а не по порядку**: на
  странице несколько `<select>`, и `getAllByRole("combobox")[1]` — не второй
  налоговый список. Рабочий приём: `getAllByRole("option", { name: "…" })[1].closest("select")`.
- **`toLocaleString("ru-RU")` ставит неразрывный пробел (U+00A0)** в разрядах —
  `getByText("15 000,00")` с обычным пробелом элемент не находит. Сравнивать
  самим: `el.textContent?.replace(/\u00A0/g, " ")`.
- **Округление `round(X, 2)` в SQLite различается между сборками**: 3.40 на
  значении 500.025 отвечает 500.03 (printf-стиль), 3.45+ (Ubuntu 24.04,
  свежие pysqlite3) — 500.02 — по настоящему значению double. Локальный прогон
  мог пройти, а CI — упасть на одном и том же тесте итогов заявок. Правило:
  в тестах, где SQL-округление сверяется с Python-Decimal, не использовать
  цены, дающие маржу ровно на границе X.XX5 (поймано 06.10.2026: граница
  500.025 в `test_shipments_totals_match_row_margins`; на проде PostgreSQL
  с numeric-арифметикой границ не бывает).
- **Скачивание браузеров Playwright из песочницы заблокировано.** Поэтому
  Chromium не запускается локально; для настоящей браузерной проверки есть
  отдельная CI-джоба с временными PostgreSQL/Valkey и безопасным тестовым seed.
  Проверять результат нужно по джобе `browser-e2e` и её артефакту, а не считать
  прохождение Vitest заменой браузерного прогона.
- Полезный приём: подставные бинарники в `PATH` (например, фальшивый `docker`)
  позволяют прогнать логику скриптов вроде `deploy.sh` целиком, включая ветку отката.

## 10. Почему сделано именно так

| Решение | Причина | Что отвергнуто |
|---|---|---|
| Nginx контейнером, с 06.10 — 1.30, закреплён digest-ом | Нужна фиксированная версия и обращение к бэкенду по имени сервиса; digest не даёт образу молча обновиться (И-02/И-03) | apt-пакет Ubuntu (там другая версия), репозиторий nginx.org (нет сборок под `resolute`), плавающие теги |

## 10.1. Хранилище файлов: когда и как переезжать на S3

Обсуждалось 29.09.2026, решение — **оставить как есть**. Раздел написан, чтобы
не обдумывать вопрос заново.

**Замеры на тот момент:** вложения 3,2 МБ, бэкапы 40 КБ, свободно на диске
5,7 ГБ из 14,7 ГБ. Запас по месту — примерно в тысячу раз.

**Что сказано «нет» и почему.** Вложения остаются на томе сервера: том быстрее,
проще и не требует внешнего аккаунта с ключами, которые можно потерять или
случайно выставить наружу. Выгрузка бэкапов в S3 тоже отложена, хотя именно она
закрывает главный принятый риск — копии лежат на одном диске с базой, и при
гибели сервера пропадёт всё сразу.

**Когда вернуться к вопросу:**

- свободного места на диске стало меньше 3 ГБ;
- вложения выросли примерно до гигабайта;
- появилась потребность в копиях за пределами сервера (например, выросло число
  клиентов и цена простоя).

**Как переносить накопленные файлы, ничего не потеряв.** Путь к файлу хранится
в поле `attachments.storage_path`, то есть место хранения — это данные, а не
зашитая в код логика. Порядок такой:

1. Научить приложение читать из двух мест сразу: новые файлы пишутся в S3,
   старые продолжают отдаваться с диска. Этот шаг ничего не ломает сам по себе.
2. Скрипт копирует накопленные файлы в S3 и сверяет каждый по размеру и
   контрольной сумме; несовпавшие остаются на диске и попадают в отчёт.
3. Только для успешно скопированных обновляется `storage_path`.
4. Локальные файлы удаляются не сразу, а через одну-две недели — после того,
   как убедились, что всё открывается.

Перед началом — свежий бэкап базы и архив вложений. Перенос всегда копирование,
а не перемещение: оригинал жив до последнего шага.

**Оценка работ:** поддержка второго хранилища — примерно полдня вместе с
тестами; само копирование при нынешних объёмах занимает секунды.

## 12. Как проект развивался

Работа шла этапами, каждый закрывался проверкой на живом сервере:

1. **Сервер с нуля** — SSH-ключи, UFW, fail2ban, автообновления, swap, Docker,
   Nginx 1.27, TLS Let's Encrypt с автопродлением. Подробности:
   [`docs/deploy/01-server-setup.md`](deploy/01-server-setup.md).
2. **Фронтенд-макет** — вся визуальная система и страницы, полностью на моках.
3. **Скелет бэкенда** — модели, API, JWT, Alembic, Celery, тесты.
4. **Деплой** — полный `docker-compose.yml`, фронтенд подключён к API.
   Подробности: [`docs/deploy/02-deploy.md`](deploy/02-deploy.md).
5. **Мутации** — формы, drag-and-drop, CRUD справочников.
6. **Вложения** — файлы на томе сервера.
7. **Активности** — действия по лидам (удалены 29.09.2026 по решению владельца).
8. **`deploy.sh`** — деплой одной командой с автооткатом.

Три поломки нашлись только в продакшене (Postgres 18, драйвер Celery, права
`/app`) — все три описаны в разделе 9 и закрыты тестами или правками образа.
