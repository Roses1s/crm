# Фронтенд CRM Detroid

React 19 · Vite 6 · Tailwind CSS v4 · TypeScript 5.7 · TanStack Query v5

Приложение работает с настоящим API: данные, формы и действия ходят
в FastAPI-бэкенд (`backend/`). Моков не осталось.

## Запуск

```bash
npm install
npm run dev      # http://localhost:5173 (запросы /api проксируются на :8000)
npm run build    # сборка в dist/
npm run preview  # предпросмотр собранной версии
```

Бэкенд должен быть запущен на `http://127.0.0.1:8000` — адрес меняется
переменной `VITE_API_TARGET`. В продакшене прокси не нужен: nginx отдаёт
и статику, и `/api/` с одного домена.

## Страницы и маршруты

| Маршрут           | Экран                                                                     |
| ----------------- | ------------------------------------------------------------------------- |
| `/login`          | Вход                                                                      |
| `/`               | Лаунчер приложений                                                        |
| `/crm`            | Канбан лидов + переключение в список                                      |
| `/crm/leads/:id`  | Карточка лида: статусбар этапов, форма, вкладка «Заявки», чаттер          |
| `/customers`      | Клиенты: все лиды компании плиткой, фильтр «Все / Активные / Проигранные» |
| `/shipments`      | Список заявок (поиск и фильтр по статусу)                                 |
| `/shipments/:id`  | Карточка заявки                                                           |
| `/accounting`     | Бухгалтерия — заготовка раздела                                           |
| `/admin`          | Редирект на `/admin/users`                                                |
| `/admin/users`    | Пользователи (создание и правка в модальном окне)                         |
| `/admin/security` | Бэкапы и попытки входа                                                    |
| `*`               | Редирект на `/`                                                           |

Всё, кроме входа, канбана и карточки лида, грузится отдельными кусками
(`lazy` + `Suspense`): начальная загрузка не тянет админку и заявки.

## Дизайн-система

Все токены живут в `src/index.css`:

- `@theme inline` объявляет имена утилит (`bg-odoo-surface`, `text-odoo-text-muted`, …);
- значения — CSS-переменные в `:root` (светлая тема) и `.dark` (тёмная), перенесены
  из исходника **без изменений**;
- тема переключается классом `.dark` на `<html>` (`@custom-variant dark`),
  скрипт `public/theme.js` применяет её до первой отрисовки;
- шрифт — системный стек, тот же, что использует Odoo (на Windows это Segoe UI);
  свой шрифт не подгружаем, поэтому на одной ОС интерфейс совпадает с образцом;
  базовый размер 13px, заголовки h1–h4 и скроллбар — как в оригинале.

Отличия синтаксиса от исходника (Tailwind v3 → v4):

| v3                                              | v4                                                |
| ----------------------------------------------- | ------------------------------------------------- |
| `tailwind.config.ts` + `postcss.config.js`      | `@theme` в CSS + плагин `@tailwindcss/vite`       |
| `colors.odoo.* = rgb(var(--x) / <alpha-value>)` | `--color-odoo-*: rgb(var(--x))` в `@theme inline` |
| `darkMode: ["class"]`                           | `@custom-variant dark (&:where(.dark, .dark *))`  |
| `shadow-sm`, `rounded`                          | `shadow-xs`, `rounded-[4px]` (переименования v4)  |

## Работа с данными

Компоненты не знают про `fetch` и адреса — только про хуки из
`src/shared/api/hooks.ts`:

```tsx
const { data: leads = [] } = useLeads({ search, stage, archived });
const moveLead = useMoveLead(); // перетаскивание карточки
const save = useUpdateLead(id); // сохранение карточки
```

- `client.ts` — обёртка над fetch: подставляет токен, разбирает единый формат
  ошибок `{detail, code, request_id}`, при 401 один раз пробует продлить сессию
  и только потом уводит на `/login`;
- `auth.ts` — токен доступа в памяти вкладки, продление по куке `HttpOnly`
  (`refreshSession`), `useIsAuthenticated()` и `useSessionRestored()`;
- `hooks.ts` — общий вход и публичный barrel-файл для прежних импортов;
  реализации разделены по областям в папке `hooks/`: `shared.ts`, `auth.ts`,
  `reference.ts`, `leads.ts`, `attachments.ts`, `shipments.ts` и `admin.ts`.
  Общие ключи кеша, типы и вспомогательные функции находятся в `hooks/shared.ts`.

Что подключено к API: вход и выход, лаунчер, канбан (поиск, перетаскивание
карточек, перестановка этапов, создание/переименование/удаление этапов с
переносом карточек, быстрое создание лида), список лидов, карточка лида (поля,
теги, приоритет, смена этапа, примечания, архивация, проигрыш с причиной,
безвозвратное удаление у администратора), клиенты, заявки (номер, создание,
правка, смена статуса, позиции заказа, документы), теги лидов, пользователи,
безопасность (бэкапы и журнал попыток входа).

При выходе и при входе другим пользователем кеш TanStack Query полностью
очищается (`shared/api/query-client.ts`), а запоздавший ответ прежней сессии
отбрасывается. Там же отменяется очередь скачивания вложений и очищается кеш
blob-ссылок — иначе следующий сотрудник мог бы увидеть файлы прежней учётной записи.

Продление сессии — одно на всю вкладку: когда токен истёк и 401 прилетает
сразу нескольким запросам, они ждут общего «полёта» (`refreshSession`), а не
шлют каждый своё продление. Сервер при выдаче нового токена отзывает прежний,
поэтому пачка одновременных продлений выбрасывала бы человека на вход.

Большие списки загружаются с сервера порциями: лиды — по 80 строк, клиенты —
по 60 плиток, заявки — по 80 строк. В Канбане каждая колонка отдельно загружает
по 20 лидов. Кнопка «Показать ещё» добавляет следующую порцию; поиск и отборы
повторяются в запросе. Счётчик показывает и уже загруженное, и общее количество
(например, `1-80 / 161`), поэтому больше нет жёсткого потолка в 200 или 500
записей и скрытых результатов. Сортировка API дополняется ID записи, чтобы
одинаковое время изменения не приводило к пропускам между страницами.

**Личные доски.** Менеджер видит только свои карточки и свои этапы.
Администратор набирает фамилию в строке поиска — под ней появляется список
сотрудников (`BoardSuggestions`), после выбора доска переключается, а сверху
висит плашка `BoardBanner` с именем владельца и ссылкой вернуться к своей.

Вложения: загрузка из панели «скрепка» и вместе с примечанием, миниатюры картинок
прямо в ленте, модальный предпросмотр картинок и PDF, скачивание и удаление.
Файлы отдаются закрытой ручкой, поэтому картинка скачивается с токеном. Миниатюры
начинают загружаться рядом с видимой областью, одновременно выполняется не больше
трёх скачиваний. Готовые ссылки хранятся в кеше вкладки (до 12 файлов и 48 МБ),
а при выходе или смене сотрудника очередь отменяется и кеш очищается. Это
ограничивает повторные и одновременные загрузки, но не уменьшает исходную
картинку: серверные миниатюры остаются незакрытой частью Ф-05.

## Мелочи, о которых стоит знать

- Панели фильтров нет: доска у каждого своя, отбор делается поиском. В адресной
  строке живут `?search=`, `?view=list` и `?board=<id>` (чужая доска) — ссылкой
  можно поделиться.
- Поиск отправляется на сервер с задержкой 300 мс.
- При переносе карточки между этапами доска ждёт ответа сервера, затем заново
  загружает затронутые колонки. Так карточка не исчезает и не дублируется,
  даже если находится на границе уже загруженных страниц.
- Формы лида и заявки отслеживают несохранённые правки. При переходе внутри
  приложения можно сохранить и продолжить, уйти без сохранения или остаться;
  при закрытии вкладки браузер показывает своё предупреждение.
- Карточка лида и форма заявки сохраняются сами через 3 секунды простоя;
  у ещё не созданной записи автосохранения нет — её создаёт только кнопка.
- Каждый PATCH лида отправляет время версии, которую видел пользователь;
  при конфликте форма не сохраняет старые данные и предлагает загрузить свежую карточку.
- Если автосохранение не удалось, оно останавливается до следующей правки
  руками (или нажатия «Сохранить»): иначе неудачный запрос повторялся бы
  каждые три секунды, пока открыта вкладка.
- После успешного сохранения справа сверху всплывает зелёная плашка
  «Сохранено» (`shared/ui/toast.tsx`), она исчезает сама через 2,5 секунды.
- При вводе ИНН, который уже есть у другого лида, под полем появляется жёлтое
  предупреждение — сохранить запись оно не мешает.
- Свёрнутые колонки хранят настройки отдельно для вошедшего пользователя и
  владельца выбранной доски; некорректное значение в `localStorage` не ломает
  страницу (Ф-08).
- `api<T>()` и `apiUpload<T>()` проверяют JSON-ответы Zod-схемами во время
  работы программы; типы и проверка берутся из одних схем (Ф-09). Ответы 204
  обрабатываются отдельно, загрузка файлов остаётся бинарной.
- Все запросы уходят с `cache: "no-store"`: иначе браузер отдавал бы из
  своего HTTP-кеша устаревшие справочники (например, старый цвет тега).

## Тесты

```bash
npm test -- --coverage  # разовый прогон с отчётом и порогами CI
npm test                # обычный прогон без отчёта покрытия
npm run test:watch
```

CI учитывает весь рабочий исходный код, в том числе ещё не импортированный
тестами. Сами тесты, их помощники и файлы только с типами в покрытие не входят.
Минимум: 60% строк и 58% ветвлений. Сейчас Vitest: 120 проверок в 36 файлах,
66,6% строк и 61,84% ветвлений. Витест проверяет компоненты, хуки и путь
«действие → запрос → ответ → экран»; ниже описаны отдельные браузерные тесты.
Два вида:

- **обычные** — проверяют разметку отдельного компонента, сетевые хуки
  подменяются (`vi.mock("@/shared/api/hooks")`);
- **сценарные** (`*-flow.test.tsx`) — подменяется только сеть (`fetch`), всё
  остальное настоящее: хуки, HTTP-клиент и кеш. Тест входа вызывает настоящую
  мутацию `useLogin` внутри `act`; тесты доски и списка заявок проходят путь
  «действие → запрос → ответ → экран». Поддельный сервер — `src/test/fake-api.ts`.
  В тесте 401 навигация `window.location.assign` подменена: jsdom не умеет
  открывать другой документ, поэтому проверяется сам запрос перехода на `/login`.

Обёртка `renderWithProviders` из `src/test/utils.tsx` подставляет обычную
маршрутизацию и кеш запросов. Формы, которые удерживают переход, используют
`renderWithDataRouter` — тестовый Data Router React Router.

Есть отдельные тесты страниц списка лидов, клиентов и заявок, включая сохранение
поиска и фильтров при загрузке следующей страницы. Дополнительно пять сценариев
Playwright проверяют Канбан, списки лидов/клиентов/заявок и перенос карточки.
В CI для них поднимаются временные PostgreSQL и Valkey, применяются миграции,
а отдельный seed-скрипт создаёт тестовые записи только в пустой базе с именем,
содержащим `test`. Он отказывается работать в production и не удаляет данные.

Для запуска браузерных проверок локально нужны такая же тестовая база и Valkey;
сначала подготовьте схему и записи, затем выполните `npx playwright install chromium`
и `npm run test:e2e`. **Не указывайте production-базу.** В этой песочнице загрузка
Chromium заблокирована, поэтому настоящий браузерный запуск отсюда недоступен;
CI job настроена на отдельной тестовой базе и сохраняет отчёт Playwright.

Список остальных замечаний и их статус — в [`docs/STATUS.md`](../docs/STATUS.md).
